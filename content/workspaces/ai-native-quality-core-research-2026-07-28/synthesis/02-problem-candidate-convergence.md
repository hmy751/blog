# 문제 후보에서 실용 후보로 수렴하는 방향

## 왜 문제 후보를 먼저 만드는가

첫 문제 하나의 해결안부터 만들면 그 문제가 전체 작업을 대표하고, 뒤의 source와 하네스 형식도 그 frame 안에서만 읽힐 수 있다.

반대로 기존 52개 원인 가설이나 84개 하네스 요소를 문제 목록으로 그대로 사용하면 다시 원자 수를 늘리는 작업이 된다. 먼저 실제로 서로 다른 결과 실패와 작동 원리를 가진 문제 후보를 source에서 뽑고, 문제 사이의 관계와 우선순위를 본다.

## 첫 산출물: source 기반 문제 후보 지도

문제 후보를 만들 때는 아직 core, skill, agent, workflow 같은 해결 형식을 붙이지 않는다.

각 문제 후보에는 다음을 둔다.

- 무엇이 잘못되거나 개선되지 않았는가
- 실제로 관찰된 장면과 source
- 사용자에게 어떤 손실·마찰·품질 정체를 만들었는가
- 인접 문제와 무엇이 다른가
- 해결됐다고 볼 수 있는 판단·결과의 변화
- 글쓰기 밖에서도 반복되는가
- 확인된 문제인지, 해석 또는 경쟁 가설인지

후보 수를 미리 정하지 않는다. 다음 조건을 만족하는 데 필요한 만큼 만든다.

- 같은 증상을 다른 말로 반복하지 않는다.
- 해결안이나 하네스 형식을 문제처럼 쓰지 않는다.
- source가 없는 추상 문제는 확인이 필요한 가설로 표시한다.
- 하나의 문제로 묶으면 작동 원리나 성공 조건이 달라지는 경우에는 분리한다.

## 문제 사이의 관계

문제 후보를 독립 목록으로만 두지 않는다.

- 원인과 결과
- 상위 문제와 구체적 발생 장면
- 문제를 해결하려다 생긴 2차 문제
- 같은 조건에서 함께 나타나지만 서로 대신하지 않는 문제
- 하나의 작동 방식이 함께 바꿀 수 있는 문제

이 관계를 보고 중복을 합치고, 증상을 별도 근본 문제로 과대평가하지 않는다.

## 우선순위

문제 후보 전체를 본 뒤 다음을 함께 고려한다.

- 여러 실패 장면을 설명하는가
- 해결하면 실제 판단이나 결과가 크게 달라지는가
- 다른 AI-native 작업에도 반복되는가
- 사례로 재생하거나 시험할 수 있는가
- 해결 비용과 운영 부담이 과하지 않은가
- 사용자에게 현재 중요한 문제인가

우선순위는 문제의 철학적 중요도 순위가 아니라, 어떤 문제부터 다루면 실제 학습과 결과 차이를 가장 많이 볼 수 있는지 정하는 순서다.

## 문제 하나를 다룰 때의 수렴 흐름

우선순위가 정해진 문제마다 다음 흐름을 사용한다.

1. 사용자 원문, 실패 장면, 직접 source에서 문제의 인과·제약·품질 신호를 복구한다.
2. 공식 문서, 기존 하네스, 이번 논의가 제공하는 서로 다른 작동 방식을 비교한다.
3. 원자 요소 목록이 아니라 `문제 → 작동 원리 → 발동 → 행동 → 기대 변화 → 관찰 증거 → 한계`가 이어지는 완결 후보를 만든다.
4. 같은 문제에 대한 가정이나 형식이 다른 완결 후보 2~3개를 비교할 수 있게 둔다.
5. Current 사례에서 어느 시점에 발동하고 어떤 다음 행동을 만들었을지 재생한다.
6. 글쓰기 밖의 구현·조사·장기 AI 협업 사례에서도 같은 판단 변화를 만드는지 본다.
7. `채택`, `조정 후 재시험`, `보류`, `기각`을 판단한다.
8. 유효성이 확인된 뒤에만 core, instruction, workflow, skill, agent, state, artifact, 사례 중 실제 owner를 정한다.

한 문제를 다룬 결과는 문제 후보 지도에 다시 반영한다. 하나의 작동 방식이 여러 문제를 함께 해결하면 합치고, 상위 문제가 설명되며 독립성이 사라진 후보는 내린다.

## 기존 산출물의 사용 경계

- `material/`, `sources/`, 사용자 원문: 문제 후보와 실제 인과의 첫 입력
- `candidates/`, `synthesis/01-expanded-landscape.md`: 누락된 문제와 경쟁 설명을 찾는 보조 입력
- `src/`: source 기반 문제 후보 지도와 이후 수렴 결과를 만드는 현재 작업면
- `references/atomic-element-expansion/`: 문제 후보 지도를 만든 뒤 중요한 판단을 빠뜨렸는지 확인하는 과거 확장 기록
- `references/harness-form-catalog/`: 우선순위가 정해진 문제의 서로 다른 작동 후보를 만들고 실제 owner를 고를 때만 여는 형식 참고

두 reference에서 항목을 골라 문제와 해결안을 역으로 만들지 않는다.

## 현재 하지 않는 일

- 첫 문제 하나를 전체 문제로 간주하지 않는다.
- 문제 후보마다 곧바로 해결안 하나를 생산하지 않는다.
- 모든 문제를 같은 깊이와 순서로 처리하지 않는다.
- 문제 수, 하네스 요소 수, 특정 문서 완성을 성과로 삼지 않는다.
- 실제 사례에서 차이를 확인하기 전에 하네스 형식을 채택하지 않는다.

## 바로 다음 작업

기존 17개 실패 장면, 52개 경쟁 원인 가설, 사용자 의도와 품질 신호, 교차 비교를 다시 읽어 `src/`에 문제 후보 지도를 만든다. 이 단계에서는 두 reference를 열지 않는다.

사용자가 문제 후보의 누락·중복·관계와 우선순위를 본 뒤, 첫 문제의 완결 후보 제작으로 넘어간다.
