# AI-native 품질 개선 패턴 후보

이 문서는 Current 한 편을 고치는 규칙이나 원본 workspace의 새 core가 아니다. 이번 실패와 기존 조사에서 구분 가능한 패턴을 먼저 넓게 보존한다. 서로 겹치거나 상하 관계처럼 보이는 후보도 지금은 합치지 않는다.

합의 상태는 다음 의미로만 쓴다.

- `거의 합의`: 현재 대화에서 사용자가 방향에 동의했거나 직접 문제를 짚었고, 원본 기록도 뒷받침한다.
- `일반화 후보`: 사례 근거는 있으나 다른 작업까지 넓힐 범위와 표현은 아직 합의하지 않았다.
- `사용자 판단 필요`: 사용자의 목적·경험 해석이나 core에 둘 해상도를 결정해야 한다.
- `근거 부족 보류`: 흥미로운 설명이지만 현재 자료만으로 반복 원리라고 말하기 이르다.

## 결과와 품질을 보는 후보

### 01. 결과와 그 결과를 만든 판단 체계를 별도 대상으로 본다

- **정의**: 결과의 문장·구조·기능만 보지 않고, 그 결과를 만든 목적, 작업 가설, context와 source 선택, constraints, 평가 질문, 역할과 권한을 별도 판별 대상으로 둔다.
- **AI-native 메커니즘**: AI는 잘못된 frame 안에서도 빠르고 일관되게 완성도를 높일 수 있다. 결과가 매끄러울수록 상위 전제가 맞다는 착시가 커질 수 있다.
- **관찰 근거**: Current는 Material, 완결본, 다수 review가 있었지만 Q1~Q5가 대표 문제라는 전제가 생성과 평가에 함께 유지됐다. A와 B도 서로 다른 수정을 제안했지만 같은 source frame을 공유했다.
- **발동 신호**: 결과가 정교하고 검토도 통과했는데 사용자가 “하려던 일이 아니다”, “계속 같은 틀이다”라고 판정한다.
- **바뀌는 판단·행동**: 곧바로 한 번 더 수정하지 않고, 결과와 판단 체계 가운데 어디를 다시 열지 먼저 판별한다.
- **좋은 적용**: API 구현이 모든 test를 통과했지만 실제 사용자 흐름이 빠졌을 때 test 추가만 하지 않고 acceptance와 slice 경계를 다시 본다.
- **잘못된 적용**: 오탈자 하나에도 goal, 조직 구조, 전체 context를 다시 설계한다.
- **비적용 조건**: 오류 원인이 국소 사실·표현·기계적 결함으로 확인되고 상위 판단과 무관할 때.
- **전이 예**: 조사 보고서의 결론이 자료와 일치해도 조사 질문이 너무 좁았는지 별도로 본다.
- **합의 상태**: 거의 합의.

### 02. 완결된 결과를 현재 판단 체계의 관찰물로 사용한다

- **정의**: 완결 결과는 최종 답 후보인 동시에 현재 goal·context·constraints·evaluation이 무엇을 만들어 내는지 보여 주는 관찰물이다.
- **AI-native 메커니즘**: AI는 여러 요소를 빠르게 통합하므로 조각에서는 보이지 않던 동기·중심·흐름의 어긋남을 실제 결과에서 일찍 드러낼 수 있다.
- **관찰 근거**: 사용자는 작은 기준과 재료를 하나씩 승인하기보다 충분히 온전한 v1을 보고 직관적으로 판단하는 방식을 선호했다. A/B가 완성됐기 때문에 두 결과의 공통 frame도 더 선명하게 드러났다.
- **발동 신호**: 재료와 기준을 오래 논의했지만 이 조합이 전체 결과에서 어떤 느낌인지 판단할 수 없을 때.
- **바뀌는 판단·행동**: 결과를 “통과 아니면 폐기”로만 보지 않고, 어떤 전제와 누락이 재현되는지 읽는다.
- **좋은 적용**: 여러 solution concept를 같은 해상도의 report로 만들어 문제 정의와 평가 기준을 시험한다.
- **잘못된 적용**: 모든 아이디어를 production-ready로 구현한 뒤에야 방향을 비교한다.
- **비적용 조건**: 안전·비용·파괴 위험 때문에 실제 통합 전에 차단해야 하는 경우.
- **전이 예**: 검색 전략을 논의만 하지 않고 작은 결과 묶음을 생성해 누락되는 관점을 본다.
- **Alex 경계**: Alex가 약한 해결책을 판별한 직접 관찰물은 최종 구현물이 아니라 중간 solution report였다.
- **합의 상태**: 방향은 거의 합의, “완결”의 필요한 해상도는 일반화 후보.

### 03. 판단하려는 관계가 보일 만큼만 통합한다

- **정의**: output probe는 반드시 최종본일 필요가 없다. 이번에 판별하려는 품질 관계가 드러날 만큼 충분히 통합되면 된다.
- **AI-native 메커니즘**: AI의 생성 비용이 낮아져 문제 정의 단계에서도 다양한 수준의 통합물을 만들 수 있지만, 무조건 높은 완성도를 요구하면 탐색 비용과 anchor가 커진다.
- **관찰 근거**: 글 전체의 동기와 흐름은 완결 원고에서 드러났고, Alex의 solution 야심은 중간 report만으로도 판별됐다.
- **발동 신호**: “일단 완성해야 하나, 단계별로 봐야 하나”가 양자택일처럼 느껴질 때.
- **바뀌는 판단·행동**: 무엇을 보고 판단하려는지 먼저 적고, 그 관계를 노출하는 최소 통합 단위를 만든다.
- **좋은 적용**: 제품 핵심 변환을 end-to-end로 연결하되 데이터 종류와 UI polish는 줄인다.
- **잘못된 적용**: 작은 산출물이라는 이유로 사용자가 경험할 핵심 관계까지 잘라 낸다.
- **비적용 조건**: 이미 품질 간극이 국소적으로 재현되고 상위 관계를 볼 필요가 없을 때.
- **전이 예**: multi-agent 설계에서는 최종 시스템 대신 실제 handoff 한 번을 끝까지 실행해 권한 충돌을 본다.
- **합의 상태**: 일반화 후보.

### 04. completion과 acceptance를 분리한다

- **정의**: 산출물이 형식상 끝났거나 정해진 검증을 통과한 상태와, 사용자의 목적과 품질 판단에서 받아들일 만한 상태를 구분한다.
- **AI-native 메커니즘**: AI 작업은 명시된 brief를 빠르게 완료하므로 “완료 신호”가 실제 목적 적합성을 대신하기 쉽다.
- **관찰 근거**: A 후보는 구조 충실도와 사실·공개 경계에서 PASS였지만 사용자에게 채택되지 않았다. v3와 `near-final`도 이후 사용자 검토로 다시 열렸다.
- **발동 신호**: PASS, done, final, near-final 같은 상태어가 있는데 사용자의 불만이 해소되지 않는다.
- **바뀌는 판단·행동**: 무엇을 통과한 것인지 판정 범위를 함께 적고, acceptance 권한자를 따로 둔다.
- **좋은 적용**: test pass는 구현 계약 통과로 기록하고 제품 AC와 사용자 가치 판단은 별도로 둔다.
- **잘못된 적용**: 모든 acceptance를 사용자의 막연한 기분에만 맡기고 확인 가능한 계약을 없앤다.
- **비적용 조건**: 기계적으로 정의된 변환이나 파일 생성처럼 completion과 acceptance가 실제로 같은 좁은 작업.
- **전이 예**: 연구자료 수집 완료와 연구 질문에 답할 만큼 충분한 자료 상태를 분리한다.
- **합의 상태**: 거의 합의.

### 05. 검증 통과의 범위를 결과 전체로 확대하지 않는다

- **정의**: 사실 검증, 공개 경계, 회귀 검사, reader-flow 등 한 판정의 PASS는 그 판정 대상만 지원한다.
- **AI-native 메커니즘**: agent별 report와 자동화된 check가 많아질수록 여러 부분 PASS가 전체 품질 보증처럼 합쳐질 위험이 있다.
- **관찰 근거**: Current 재작성은 shaping·evidence·texture·light edit를 거쳤지만 글을 만든 이유와 사용자 판단 논리가 빠졌다. A의 PASS도 brief 안의 판정이었다.
- **발동 신호**: “모든 reviewer가 통과시켰는데 왜 안 좋지?”라는 질문이 생긴다.
- **바뀌는 판단·행동**: 각 PASS 옆에 대상, 입력 경계, 지원하지 않는 것을 기록한다.
- **좋은 적용**: security scan, unit test, usability review를 각각 별도 증거로 유지한다.
- **잘못된 적용**: 부분 판정은 모두 쓸모없다고 보고 검증 자체를 폐기한다.
- **비적용 조건**: 하나의 검증이 실제 acceptance 전체를 완전히 정의하는 좁은 deterministic task.
- **전이 예**: citation verifier의 PASS를 보고서의 질문 적합성 PASS로 확대하지 않는다.
- **합의 상태**: 거의 합의.

### 06. 품질의 서로 다른 축을 합산해 한 등급으로 만들지 않는다

- **정의**: 후보 가치, shaping 상태, 근거 준비도, 주장 상한, 독자 흐름, 구현 완성도처럼 역할이 다른 축을 한 점수로 합치지 않는다.
- **AI-native 메커니즘**: AI는 비교와 ranking 요청을 받으면 측정하기 쉬운 축을 상위 목적의 proxy로 승격시키기 쉽다.
- **관찰 근거**: 근거 준비도가 주제 매력을 대신했고, 주장 상한이 self-check 후보의 매력도 감점으로 쓰였으며, 편집 기준이 후보 탐색을 닫았다.
- **발동 신호**: 한 약점이 발견된 뒤 후보·글·사용자 해석 전체가 자동으로 내려간다.
- **바뀌는 판단·행동**: 부족한 축에 맞는 조치만 취한다. 근거 부족이면 주장을 낮추거나 조사하고, 중심 약점이면 shaping을 다시 연다.
- **좋은 적용**: 구현 가능성은 낮지만 가치가 큰 후보를 탐색 상태로 남긴다.
- **잘못된 적용**: 축을 분리한다는 이유로 최종 선택과 trade-off를 영원히 미룬다.
- **비적용 조건**: 실제 운영상 하나의 hard gate로 결정을 내려야 하고 그 gate의 역할이 합의된 경우.
- **전이 예**: 모델 정확도, latency, 사용자 효용, 유지보수성을 한 평균 점수로 지우지 않는다.
- **합의 상태**: 거의 합의.

### 07. 같은 품질 불만의 반복을 상위 판단 재검사 신호로 본다

- **정의**: 국소 수정 뒤에도 같은 종류의 불만이 반복되면 결과 표면보다 그것을 반복 생성하는 상위 판단을 의심한다.
- **AI-native 메커니즘**: AI는 feedback을 현재 frame 안에서 충실히 반영해 같은 구조의 더 세련된 결과를 만들 수 있다.
- **관찰 근거**: v1~v3, post-sync, near-final, public reshape, Current rewrite, A/B로 이어졌지만 중심 material과 발생 이유가 계속 약해졌다.
- **발동 신호**: 표현은 달라졌는데 “틀을 못 벗어난다”, “전진이 없다”가 반복된다.
- **바뀌는 판단·행동**: 가장 최근 수정 지시가 아니라 반복되는 불만의 공통 원인을 시간순으로 본다.
- **좋은 적용**: 세 번의 UI 수정이 모두 사용자 핵심 행동을 숨기면 디자인 polish보다 정보구조와 product goal을 다시 본다.
- **잘못된 적용**: 서로 다른 세 가지 오류를 같은 근본 원인 하나로 억지로 묶는다.
- **비적용 조건**: 반복이 아니라 서로 독립적인 국소 오류이거나 요구사항이 실제로 바뀐 경우.
- **전이 예**: agent가 세 번 모두 같은 source를 누락하면 prompt 문구보다 source routing을 검사한다.
- **합의 상태**: 거의 합의.

### 08. 품질 개선은 결과뿐 아니라 평가 체계의 학습을 포함한다

- **정의**: 결과를 고정 기준에 맞추는 것뿐 아니라, 결과가 드러낸 약점을 바탕으로 goal·constraints·evaluation criteria를 더 나은 것으로 갱신할 수 있다.
- **AI-native 메커니즘**: 빠른 생성과 반복은 기준을 시험할 표본을 늘리지만, 기준을 고정하면 같은 오판만 더 빠르게 반복한다.
- **관찰 근거**: Alex는 약한 solution report 뒤 자신이 준 시간·범위 제약과 평가 기준, output 조건을 보강해 다시 위임했다. Current 논의에서도 결과를 통해 평가 질문 자체의 한계가 드러났다.
- **발동 신호**: 결과가 기준에는 맞는데 기대한 가치가 나오지 않거나, 결과를 본 뒤 “우리가 애초에 무엇을 좋다고 봤나”가 흔들린다.
- **바뀌는 판단·행동**: result correction과 criteria update를 구분해 기록한다.
- **좋은 적용**: 여러 prototype이 안전하지만 무의미하면 “안전성”을 버리지 않고 가치·야심 기준을 추가하거나 제약을 조정한다.
- **잘못된 적용**: 실패한 결과를 통과시키려고 평가 기준을 사후에 낮춘다.
- **비적용 조건**: 법적·안전 hard constraint처럼 결과에 맞춰 바꾸면 안 되는 기준.
- **Alex 경계**: 확인된 것은 인간이 개입한 solution concept 개선 loop이며 최종 autonomous loop 완료는 확인되지 않았다.
- **합의 상태**: 거의 합의.

## 목적, goal, 제약과 합의를 보는 후보

### 09. 사용자 목적, 현재 작업 goal, 작업 가설, 성공 조건을 구분한다

- **정의**: 비교적 안정적인 사용자 목적, 이번 cycle에서 만들 결과의 goal, 시험 중인 중심·장면·문제 frame, 결과를 판정할 success condition을 같은 `goal`로 뭉치지 않는다.
- **AI-native 메커니즘**: AI는 더 명료하게 문서화된 하위 가설을 모호한 상위 목적보다 권위 있게 취급하기 쉽다.
- **관찰 근거**: “개발자가 AI와 일하며 얻은 판단 감각”과 “Current의 발생 이유”가 상위 목적에 가까웠지만 Q1~Q5 대표 장면과 현재 중심 위계가 사실상 고정 goal처럼 작동했다.
- **발동 신호**: 무엇을 바꾸려는지 말할 때 “goal을 바꾼다”가 사용자 목적 변경인지, 현재 가설 교체인지 불분명하다.
- **바뀌는 판단·행동**: 약한 결과 뒤 어느 수준을 유지하고 어느 수준을 다시 열지 구분한다.
- **좋은 적용**: 제품 목적은 유지하고 이번 prototype의 solution hypothesis만 폐기한다.
- **잘못된 적용**: 용어 층위를 과도하게 만들어 모든 작은 결정마다 문서 상태를 관리한다.
- **비적용 조건**: 한 번으로 끝나는 좁은 작업에서 네 층이 실제로 같은 경우.
- **전이 예**: 조사에서는 연구 목적, 이번 query, 현재 설명 가설, evidence threshold를 나눈다.
- **합의 상태**: 일반화 후보, 명칭과 core 해상도는 사용자 판단 필요.

### 10. 작업 가설은 현재 행동을 이끌 수 있지만 사용자 목적을 대신하지 않는다

- **정의**: 임시 중심과 대표 장면은 작성·구현을 가능하게 하는 working hypothesis지만, 사용자가 승인한 상위 목적처럼 불변 권위를 갖지 않는다.
- **AI-native 메커니즘**: AI는 실행 가능한 명확한 frame을 선호하고, 반복 session에서 임시 선택의 provenance가 사라지면 사실상 요구사항으로 승격한다.
- **관찰 근거**: `한 사건`, `한 artifact`, 특정 article type, Q1~Q5의 주 장면화는 reviewer·main의 편집 선택이었지만 뒤의 작업에서 합의된 중심처럼 보호됐다.
- **발동 신호**: “왜 이 장면이 중심이지?”라는 질문에 현재 문서 외의 사용자 합의 근거를 찾기 어렵다.
- **바뀌는 판단·행동**: working hypothesis에는 변경 가능성과 출처를 남기고 결과 뒤 재판정한다.
- **좋은 적용**: 첫 구현에서 선택한 architecture를 검증 가능한 가설로 명시한다.
- **잘못된 적용**: 모든 합의를 임시라고 취급해 작업이 축적되지 않게 한다.
- **비적용 조건**: 사용자가 명시적으로 확정했고 변경 조건도 없는 결정.
- **전이 예**: 데이터 분석에서 첫 segmentation을 진실이 아니라 분석 가설로 둔다.
- **합의 상태**: 거의 합의.

### 11. 제안, 적용, 사용자 합의, 현재 권위를 구분한다

- **정의**: reviewer 제안, main이 한 version에 적용한 선택, 사용자가 동의한 판단, 현재 반복할 rule은 서로 다른 상태다.
- **AI-native 메커니즘**: agent 산출물이 빠르게 다음 agent의 context가 되면 제안이 provenance 없이 규칙으로 굳는다.
- **관찰 근거**: v1~v3에서 reviewer와 main의 임시 선택이 사용자 합의처럼 굳었다. `채택`도 “다음 version에 적용”과 “사용자가 최종 합의”가 섞였다.
- **발동 신호**: 현재 기준의 출처를 따라가면 사용자 발화가 아니라 review나 build record에 도달한다.
- **바뀌는 판단·행동**: 결정마다 누가 무엇에 대해 어떤 권한으로 결정했는지 남긴다.
- **좋은 적용**: reviewer move를 candidate로 두고 main adjudication 뒤 사용자 승인 여부를 별도 기록한다.
- **잘못된 적용**: 모든 작은 구현 결정을 사용자 승인 없이는 못 하게 만든다.
- **비적용 조건**: main에게 명시적으로 위임된 국소·가역 결정.
- **전이 예**: multi-agent 구현에서 worker의 architectural suggestion을 merged contract로 자동 취급하지 않는다.
- **합의 상태**: 거의 합의.

### 12. 결과를 통해 goal을 개선하되 실패를 정당화하는 방향으로 이동하지 않는다

- **정의**: output이 더 좋은 목표나 질문을 드러낼 수 있지만, 결과가 약하다는 이유만으로 goal을 낮추거나 결과에 맞춰 이동시키지는 않는다.
- **AI-native 메커니즘**: 생성된 output이 구체적일수록 사후 설명과 goal 재서술이 쉬워져 실패가 “새 발견”으로 포장될 수 있다.
- **관찰 근거**: 사용자 논의는 고정 goal 최적화만으로 충분한지 열었고, Alex 사례는 약한 결과 뒤 scope와 criteria를 상향한 예를 제공한다.
- **발동 신호**: output을 본 뒤 기존 goal의 결함이 구체적으로 드러나지만, goal 변경이 진짜 학습인지 사후 합리화인지 애매하다.
- **바뀌는 판단·행동**: goal 변화의 근거, 유지되는 상위 목적, 더 엄격해지거나 명확해지는 부분을 기록한다.
- **좋은 적용**: 사용자가 실제로 읽을 수 없는 dashboard를 보고 “시각적 완성”보다 의사결정 가능성을 success condition에 추가한다.
- **잘못된 적용**: 구현하지 못한 기능을 “원래 필요 없었다”고 goal에서 삭제한다.
- **비적용 조건**: 외부 계약으로 goal이 고정돼 있고 변경 권한이 없는 경우.
- **전이 예**: 연구 중 반례가 나오면 연구 목적은 유지하고 가설을 바꾼다.
- **합의 상태**: 일반화 후보.

### 13. 약한 결과를 만든 제약도 원인 후보에 포함한다

- **정의**: agent의 능력이나 결과만 탓하지 않고 main이 준 시간, 범위, 비용, 형식, 위험 회피 조건이 결과 공간을 어떻게 제한했는지 본다.
- **AI-native 메커니즘**: AI는 주어진 constraints를 충실히 최적화해 “안전하지만 작은” 결과를 다량 만들 수 있다.
- **관찰 근거**: Alex는 3~6시간 제약이 해결책을 작게 만들었다고 판단하고 1~2주 범위와 더 강한 평가 기준으로 재위임했다. 기존 workspace에서도 근거·한 사건·한 artifact 기준이 가능성을 줄였다.
- **발동 신호**: 여러 agent가 모두 비슷하게 작고 무난한 결과를 낸다.
- **바뀌는 판단·행동**: output을 고치기 전에 constraints의 의도와 부작용을 대조한다.
- **좋은 적용**: 비용 guard는 유지하되 탐색용 concept 단계의 시간 horizon을 넓힌다.
- **잘못된 적용**: 결과가 약할 때마다 예산과 범위를 무제한으로 늘린다.
- **비적용 조건**: 제약이 안전·법·실제 일정 때문에 변경 불가능하거나, 제약과 무관한 명백한 실행 오류.
- **전이 예**: 코드 생성에서 “파일 하나만 수정”이 올바른 architecture 변경을 막았는지 본다.
- **합의 상태**: 일반화 후보, Alex에서 확인된 범위는 강함.

### 14. 사용자의 불편함과 직관을 품질 신호로 보되 곧바로 원인 판정으로 올리지 않는다

- **정의**: “공감이 안 된다”, “전진이 없다”, “틀을 못 벗어난다”는 사용자의 반응을 단순 취향으로 버리지 않고 진단을 시작할 신호로 쓴다.
- **AI-native 메커니즘**: 명시적 rubric이 포착하지 못한 목적 적합성, 생생함, 의미 계보를 사용자가 통합적으로 먼저 감지할 수 있다.
- **관찰 근거**: 모든 formal review 뒤 사용자의 거부가 발생 이유·Alex 계보·Q1~Q5 위계 문제를 드러냈다. A 제목이 더 생생하다는 긍정 신호도 별도로 남았다.
- **발동 신호**: 검증 지표는 좋아졌지만 사용자가 결과에 계속 끌리지 않는다.
- **바뀌는 판단·행동**: 반응을 그대로 규칙으로 번역하지 않고, 어떤 관계가 어긋났는지 사례와 source로 조사한다.
- **좋은 적용**: “뭔가 데모 같다”는 반응에서 실제 사용자 상태 변화가 빠졌는지 확인한다.
- **잘못된 적용**: 사용자의 첫 감정을 보편 품질 기준이나 사실 판정으로 선언한다.
- **비적용 조건**: 사용자가 명시적으로 개인 취향이며 목표와 무관하다고 밝힌 부분.
- **전이 예**: 제품 prototype의 신뢰감 저하를 latency, 정보 위계, 설명 부족 중 무엇이 만드는지 후속 조사한다.
- **합의 상태**: 일반화 후보.

### 15. 문제가 생긴 책임 위치만 다시 연다

- **정의**: 결과가 나쁘다고 모든 과정을 처음부터 반복하지 않고, 관찰된 간극을 만든 것으로 보이는 판단 위치를 선별해 다시 연다.
- **AI-native 메커니즘**: 모든 agent와 모든 단계의 재실행은 비용뿐 아니라 새 artifact와 새 anchor를 늘려 원인을 더 흐릴 수 있다.
- **관찰 근거**: Current의 `Material로 돌아간다`는 방향은 source와 motive가 문제일 때 유효하지만, 전체 일반 원리로 삼으면 다른 원인에 과잉 적용된다.
- **발동 신호**: “Material부터 다시?”, “goal부터?”, “평가자를 첫 단계부터?”처럼 전체 restart 후보가 여러 개 떠오른다.
- **바뀌는 판단·행동**: 누락·왜곡이 처음 발생한 위치와 이후 증폭 위치를 구분한 뒤 필요한 책임만 재실행한다.
- **좋은 적용**: source는 충분하지만 중심이 잘못 수렴했다면 Material 수집보다 shaping과 goal 가설을 다시 본다.
- **잘못된 적용**: 첫 원인 하나만 찾고 downstream 손상을 확인하지 않는다.
- **비적용 조건**: source·goal·implementation·evaluation이 모두 오염돼 부분 복구가 더 위험한 경우.
- **전이 예**: failing system에서 전체 rewrite 대신 잘못된 acceptance contract와 그 영향을 받은 test만 다시 연다.
- **합의 상태**: 거의 합의.

### 16. 무거운 loop는 상시 절차가 아니라 발동 조건이 있는 대응이다

- **정의**: goal 재설정, fresh audit, source-first 재탐색, evaluator 재설계 같은 조치는 특정 실패 신호가 있을 때 선택한다.
- **AI-native 메커니즘**: AI 협업은 메타 절차도 쉽게 생산해 본 작업보다 하네스가 커질 수 있다.
- **관찰 근거**: 기존 논의에서 process를 정교한 snapshot system으로 만들려다 사용자가 “러프하게”로 정정했다. self-check도 모든 오독에 발동하면 본 작업을 가린다는 경계가 있었다.
- **발동 신호**: 절차가 품질보다 파일과 agent 수를 늘리고, 무엇을 해결하는지 설명하기 어렵다.
- **바뀌는 판단·행동**: 반복 실패, frame 공유, 목적 불일치 등 발동 근거를 먼저 적고 적절한 강도의 대응을 고른다.
- **좋은 적용**: 첫 국소 오독은 바로 고치고, 같은 판단 위치의 오독이 반복될 때 independent audit로 올린다.
- **잘못된 적용**: 발동 조건이 있다는 이유로 반복 실패에도 계속 국소 수정만 한다.
- **비적용 조건**: 법적·안전상 항상 수행해야 하는 mandatory check.
- **전이 예**: 모든 commit마다 architecture review를 강제하지 않고 boundary 변경 때만 호출한다.
- **합의 상태**: 거의 합의.

- **정의**: 무엇이 있었는지만 아니라 왜 만들었고 어떤 문제·영감·사용자 판단에서 나왔는지 최소 계보를 보존한다.
- **AI-native 메커니즘**: session 요약과 압축은 결과 형태를 남기고 생성 동기와 판단 전환을 먼저 지우기 쉽다.

- **발동 신호**: 결과의 기능은 설명되지만 “왜 이걸 만들었는가”가 현재 참가자의 기억에만 남아 있다.

- **좋은 적용**: architecture decision에 선택한 이유와 버린 대안을 최소한으로 보존한다.
- **잘못된 적용**: 모든 대화와 영감의 시간순 서사를 active-state에 넣는다.
- **비적용 조건**: 기계적 산출물로 생성 이유가 사용 목적과 완전히 동일하고 변동 가능성이 없는 경우.
- **전이 예**: 평가 rubric에 각 기준이 어떤 실패 때문에 생겼는지 연결한다.
- **합의 상태**: 거의 합의.

### 19. source packet을 고르는 행위 자체를 판단으로 본다

- **정의**: reviewer나 writer에게 제공할 source 범위는 중립적 운반이 아니라 가능한 문제 정의와 발견 공간을 만드는 선택이다.
- **AI-native 메커니즘**: 동일 packet을 여러 agent에게 주면 packet 바깥의 원인은 모든 결과에서 동시에 사라질 수 있다.
- **관찰 근거**: A/B 공통 packet은 current, Q1~Q5, 계약 분리, terminal gap 중심이었고 최초 문제와 Alex 발상 계보는 없었다. 두 review는 같은 사건 universe 안에서만 갈렸다.
- **발동 신호**: 서로 다른 agent가 놀랄 만큼 비슷한 문제를 발견하거나, 사용자 기억의 중요한 material이 어떤 packet에도 없다.
- **바뀌는 판단·행동**: packet의 포함·제외 이유와 그것이 열거나 닫는 질문을 명시한다.
- **좋은 적용**: verifier에는 좁은 주장 source를 주고, problem reviewer에는 source index와 질문 수정 권한을 준다.
- **잘못된 적용**: 독립성을 위해 모든 agent에게 전체 저장소를 던진다.
- **비적용 조건**: 판정할 사실과 source가 일대일로 명확한 좁은 검증.
- **전이 예**: incident review에서 최근 logs만 주면 설계 결정 원인이 사라질 수 있음을 점검한다.
- **합의 상태**: 거의 합의.

### 20. 기존 결과를 가린 source-first second pass를 별도 도구로 둔다

- **정의**: 기존 해석이 새 탐색의 prior로 너무 강하게 작동할 때, 기존 후보·원고를 보지 않고 직접 source에서 다시 생성한 뒤 두 결과를 대조한다.
- **AI-native 메커니즘**: AI는 제공된 taxonomy와 기존 artifact를 비판하기보다 확장·정당화하는 방향으로 쉽게 수렴한다.
- **관찰 근거**: 기존 workspace의 source-first 재조사는 기존 다섯 후보를 가리고 fresh 후보를 뽑아 scope control, output-informed selection 등 새 방향을 발견했다.
- **발동 신호**: 새 기준을 추가해도 기존 후보 이름과 구조만 반복된다.
- **바뀌는 판단·행동**: 기존 결과 수정 pass와 source-first regeneration pass를 분리해 비교한다.
- **좋은 적용**: 오래된 architecture 문서를 가리고 requirements와 runtime evidence에서 새 설계를 만든다.
- **잘못된 적용**: 이미 합의한 사실과 사용자 목적까지 숨겨 매번 재학습한다.
- **비적용 조건**: 기존 artifact가 정확한 canonical contract이고 새 생성이 그 계약 준수가 목적인 경우.
- **전이 예**: 문헌 review에서 기존 요약의 분류를 숨기고 논문 abstract에서 다시 theme을 뽑는다.
- **합의 상태**: 일반화 후보, 기존 원본에서 근거 강함.

### 21. 최소 context보다 목적에 맞는 충분한 context를 우선한다

- **정의**: context를 적게 주는 것 자체를 독립성이나 품질로 보지 않고, 역할이 판정할 대상을 이해하는 데 필요한 정보와 anchor 위험을 함께 본다.
- **AI-native 메커니즘**: 과도한 context는 anchor를 만들고 과소 context는 motive·agreement·causal history를 없앤다.
- **관찰 근거**: backlog 전체를 준 review는 과거 기준에 anchoring됐고, draft-only review는 사용자 합의와 source 누락을 판정할 수 없었다. A/B의 최소 packet은 핵심 발생 이유를 제외했다.
- **발동 신호**: “독립성을 위해 가릴수록 좋아진다” 또는 “전체를 주면 다 해결된다”는 단일 해법이 등장한다.
- **바뀌는 판단·행동**: review 목적별로 필요한 context와 의도적으로 제외할 context를 정한다.
- **좋은 적용**: cold reader에는 원고만, evidence checker에는 주장과 source, problem reviewer에는 결과·목표·직접 원천을 준다.
- **잘못된 적용**: 역할별 packet 설계를 거대한 고정 매트릭스로 만든다.
- **비적용 조건**: 입력 계약이 이미 표준화된 deterministic checker.
- **전이 예**: 코드 reviewer에게 ticket 전체는 주되 previous reviewer verdict는 가린다.
- **합의 상태**: 거의 합의.

### 22. 전체 지도와 현재 cursor를 함께 유지한다

- **정의**: 긴 작업에서는 낮은 해상도의 전체 생각 구조와 현재 판단점 하나를 같은 화면에 둔다.
- **AI-native 메커니즘**: AI session은 최근 대화와 최신 구현에 과적합하기 쉽고, 전체 기록을 모두 넣으면 오히려 현재 권위가 흐려진다.
- **관찰 근거**: Current/active-state 구조는 최근 작업이 프로젝트 전체를 덮는 문제를 줄이기 위해 만들어졌다. 전체 지도 없이 `최신만`을 현재 단계만으로 좁혔을 때 완료된 material과 사용자 합의가 사라졌다.
- **발동 신호**: 다음 session이 최근 task는 알지만 프로젝트에서 왜 하는지 다시 추론해야 한다.
- **바뀌는 판단·행동**: 전체 가지의 현재 결론과 정확히 하나의 cursor를 유지하고 세부는 역할 링크로 접는다.
- **좋은 적용**: 장기 연구에서 전체 질문 지도와 현재 실험을 함께 둔다.
- **잘못된 적용**: 모든 상태·이력·세부 contract를 current 한 파일에 넣는다.
- **비적용 조건**: session 간 연속성이 필요 없는 짧고 독립적인 작업.
- **전이 예**: multi-agent program에서 전체 deliverable map과 현재 integration point를 분리하지 않는다.
- **합의 상태**: 기존 workspace에서는 거의 합의, 일반 AI-native core로의 범위는 사용자 판단 필요.

### 23. 좋은 rule이 필요한 결정 순간에 도달하는지 본다

- **정의**: rule의 내용 품질과 activation channel, 즉 어떤 조건에서 누가 읽고 적용하는지를 별도 문제로 본다.
- **AI-native 메커니즘**: 많은 문서와 skill이 있어도 현재 prompt와 routing에서 선택되지 않으면 실제 판단에 작동하지 않는다.
- **관찰 근거**: 기존 원본은 engineering 문서가 있어도 decision 순간에 읽히지 않은 사건과 current를 읽었어도 최근 시간축에 끌린 사건을 기록했다.
- **발동 신호**: “규칙은 이미 있는데 왜 또 어겼지?”가 반복된다.
- **바뀌는 판단·행동**: rule을 더 쓰기 전에 trigger, router, owner, read path를 확인한다.
- **좋은 적용**: boundary 변경 때만 관련 decision guide를 읽도록 root guide에서 연결한다.
- **잘못된 적용**: 모든 rule을 모든 요청에 자동 import한다.
- **비적용 조건**: 사람이 직접 한 번 읽고 수행하는 비반복 작업.
- **전이 예**: CI policy가 존재하는 것과 merge 전에 실제 실행되는 것을 분리한다.
- **합의 상태**: 일반화 후보.

### 24. 판단이 가리키는 시간축을 명시한다

- **정의**: 현재 구현, 프로젝트 전체, 과거 선택 이유, 마지막 외부 사건처럼 서로 다른 시간축을 같은 “현재”로 섞지 않는다.
- **AI-native 메커니즘**: AI는 최신이고 구체적인 사건을 더 중요한 전체 상태로 일반화하기 쉽다.
- **관찰 근거**: Q1~Q5에서 최근 Loop 구현이 프로젝트 전체 답변을 덮었고, active-state의 “최신”도 직전 단계 요약으로 좁혀졌다.
- **발동 신호**: 사실은 맞지만 질문 범위에는 틀린 답이 나온다.
- **바뀌는 판단·행동**: 각 질문과 source가 어느 시간축을 대표하는지 맞춘다.
- **좋은 적용**: “현재 배포 상태”와 “프로젝트가 해결한 전체 문제”를 다른 source로 답한다.
- **잘못된 적용**: 모든 문장에 날짜와 상태 라벨을 붙여 읽기 어려운 관리표를 만든다.
- **비적용 조건**: 대상이 한 시점의 snapshot으로 명확한 경우.
- **전이 예**: incident 분석에서 현재 fix와 시스템 설계의 장기 원인을 분리한다.
- **합의 상태**: 거의 합의.

### 25. history, active contract, source, current result의 권위를 분리한다

- **정의**: 왜 선택했는지, 지금 무엇을 따라야 하는지, 무엇이 사실인지, 현재 어디에 있는지를 서로 다른 수명과 갱신 책임으로 둔다.
- **AI-native 메커니즘**: 모든 문서를 동등한 context로 주면 오래된 이유가 현재 계약을 덮거나 최신 결과가 사실 원천을 대신할 수 있다.
- **관찰 근거**: AX와 workspace context layering은 process, core, active-state, sources, src를 분리했다. 동시에 첫 구현에서 층위를 과도하게 snapshot 체계로 만들려다 정정됐다.
- **발동 신호**: “최신 파일이니 가장 권위 있다”거나 “과거에 이렇게 썼으니 지금도 따라야 한다”가 자동 적용된다.
- **바뀌는 판단·행동**: 문서 역할과 write owner를 정하되, 필요한 수준 이상으로 세분화하지 않는다.
- **좋은 적용**: decision history와 executable config를 별도 owner로 둔다.
- **잘못된 적용**: 작은 프로젝트에도 많은 live 문서와 동기화 의무를 만든다.
- **비적용 조건**: 한 파일이 실제로 유일한 canonical source인 단순 작업.
- **전이 예**: dataset provenance, current schema, experiment log, active hypothesis를 구분한다.
- **합의 상태**: 원본 workspace에는 합의, 일반화 해상도는 사용자 판단 필요.

## 판단 순서와 review를 보는 후보

### 26. 생성·관찰, 주장 판정, 후보 수렴을 다른 판단으로 둔다

- **정의**: 가능성과 가치를 펼치는 판단, 각 후보의 사실·모름·위험을 보는 판단, 전체 후보를 선택·종료하는 판단은 시점과 권한이 다르다.
- **AI-native 메커니즘**: AI는 criteria를 받으면 생성과 탈락 판정을 동시에 수행해 안전하고 비슷한 후보만 남기기 쉽다.
- **관찰 근거**: 좋은 rubric이 후보의 씨앗이 됐고, 주장 상한이 후보 매력도 감점이 됐으며, first shaping cursor가 가치 서열로 읽혔다.
- **발동 신호**: 탐색 단계인데 모든 후보가 “근거 부족”, “한 편으로 안 됨”으로 조기 종료된다.
- **바뀌는 판단·행동**: 발산 중에도 사실과 hard guard는 엄격히 보되 후보 전체의 종료 권한은 나중으로 미룬다.
- **좋은 적용**: 아이디어마다 위험을 표시하면서도 가능한 가치와 형태를 충분히 만든다.
- **잘못된 적용**: 발산을 이유로 사실 오류·안전 위험·비용 한계를 무시한다.
- **비적용 조건**: 한 후보의 명백한 hard constraint 위반.
- **전이 예**: architecture 탐색에서 security violation은 즉시 제거하지만 낯선 설계라는 이유로 조기 탈락시키지 않는다.
- **합의 상태**: 거의 합의.

### 27. criteria의 seed, filter, guard 역할을 구분한다

- **정의**: 가능성을 생성하는 질문, 충분히 펼친 후보를 비교하는 기준, 언제나 지켜야 할 경계를 같은 criteria 목록으로 다루지 않는다.
- **AI-native 메커니즘**: AI는 filter를 생성 prompt에 넣으면 후보가 그 기준을 표면적으로 만족하는 방향으로 동질화된다.
- **관찰 근거**: 제3판별자라는 예시가 탐색 목표가 됐고, 회사 블로그 서사 패턴이 통과 템플릿이 됐으며, rubric이 후보 seed가 됐다.
- **발동 신호**: 후보들이 모두 criteria 문구를 그대로 반영하지만 새로운 문제나 형태가 없다.
- **바뀌는 판단·행동**: criteria마다 지금 생성에 쓰는지, 비교에 쓰는지, hard guard인지 역할을 정한다.
- **좋은 적용**: privacy guard는 항상 유지하고, 독자 매력 기준은 여러 결과를 본 뒤 비교에 사용한다.
- **잘못된 적용**: seed·filter·guard를 정교한 고정 taxonomy로 만들어 다시 생성 공간을 닫는다.
- **비적용 조건**: 출력 schema처럼 생성 시점부터 반드시 적용해야 하는 형식 계약.
- **전이 예**: hiring rubric을 brainstorming prompt의 문구로 그대로 사용하지 않는다.
- **합의 상태**: 거의 합의.

### 28. 좋은 기준도 현재 무엇을 닫을 권한이 있는지 묻는다

- **정의**: 기준의 내용이 옳은지뿐 아니라 적용 시점, 판정 대상, 결과를 폐기하거나 중심을 바꿀 권한을 확인한다.
- **AI-native 메커니즘**: 한 agent에게 많은 기준과 write 권한을 함께 주면 국소 판정이 전체 방향 변경으로 확대되기 쉽다.
- **관찰 근거**: “한 편에는 하나의 중심 질문”은 shaping에는 유효했지만 material 탐색 전 후보 가치를 닫았다. fact correction도 중심 해석까지 바꾸는 데 사용될 위험이 있었다.
- **발동 신호**: 모두가 동의하는 좋은 기준인데 적용 뒤 가능성과 material이 급격히 사라진다.
- **바뀌는 판단·행동**: 기준마다 대상, 시점, 변경 권한, 회수 주체를 붙인다.
- **좋은 적용**: evidence checker는 claim을 낮출 수 있지만 사용자 경험의 가치를 폐기하지 않는다.
- **잘못된 적용**: 권한 구분 때문에 reviewer가 강한 문제를 말하지 못하게 한다.
- **비적용 조건**: hard guard가 전체 작업 중단 권한을 갖는 것이 명시된 경우.
- **전이 예**: linter는 코드 형식을 바꾸지만 architecture를 자동 재설계하지 않는다.
- **합의 상태**: 거의 합의.

### 29. reviewer의 독립성을 여러 조건으로 본다

- **정의**: 독립성은 reviewer 수나 모델 이름이 아니라 입력, raw source 접근, 질문 수정·기각 권한, write 권한, 완료 선언 권한, main 회수 구조의 조합이다.
- **AI-native 메커니즘**: 여러 agent가 같은 frame과 packet을 상속하면 독립 실행이어도 판단 오류는 상관된다.
- **관찰 근거**: 기존 독립 판별 후보와 A/B 실패 모두 reviewer 수보다 입력·질문·권한이 중요함을 보여 줬다.
- **발동 신호**: reviewer를 추가할수록 보고서 수는 늘지만 새로운 문제 정의가 나오지 않는다.
- **바뀌는 판단·행동**: 필요한 독립성 차원을 먼저 고르고 reviewer contract를 만든다.
- **좋은 적용**: problem reviewer가 main 질문을 기각하고 source index에서 추가 원천을 고를 수 있게 한다.
- **잘못된 적용**: 독립성을 위해 사용자 목적, canonical contract, 안전 기준까지 숨긴다.
- **비적용 조건**: 현재 합의 안에서 문장만 고치는 contextual editor.
- **전이 예**: code reviewer에게 구현자의 test만이 아니라 requirement와 runtime evidence 접근을 준다.
- **합의 상태**: 거의 합의.

### 30. 여러 reviewer의 유사한 결론을 독립 합의로 자동 해석하지 않는다

- **정의**: reviewer들이 공유한 goal, packet, 질문, rubric이 크면 유사 결과는 공통 frame의 재현일 수 있다.
- **AI-native 메커니즘**: agent 수를 늘려도 common prompt가 강하면 sampling diversity보다 frame correlation이 크다.
- **관찰 근거**: A와 B는 editorial 기준 여부는 달랐지만 같은 Current 사건 universe를 공유했다. 둘의 갈등은 그 universe 안에서 Q1~Q5의 위계를 어떻게 둘지였다.
- **발동 신호**: 독립 reviewer가 모두 비슷한 단어와 사건을 중심으로 삼는다.
- **바뀌는 판단·행동**: 결론 수보다 어떤 전제와 source가 공유됐는지 먼저 비교한다.
- **좋은 적용**: 같은 packet review와 source-first regeneration을 별도 축으로 대조한다.
- **잘못된 적용**: reviewer들이 동의하면 언제나 공모된 frame이라고 불신한다.
- **비적용 조건**: 서로 다른 source와 질문에서 동일 사실을 독립 재현한 경우.
- **전이 예**: 세 test suite가 같은 mock world를 공유하면 세 번의 독립 검증으로 세지 않는다.
- **합의 상태**: 거의 합의.

### 31. reviewer가 질문과 source frame을 다시 열 수 있어야 하는 경우가 있다

- **정의**: 결과 개선 reviewer는 주어진 결과의 약점뿐 아니라 최소 goal, 대표 문제, 제공 source의 누락을 지적하고 필요한 경우 재설정을 요청할 수 있다.
- **AI-native 메커니즘**: main이 만든 frame 안에서만 최적화하는 reviewer는 main의 상위 오판을 발견할 구조가 없다.
- **관찰 근거**: review-workflow는 reviewer가 문제 정의를 다시 열고 추가 원천을 고를 수 있게 했지만, A/B의 source index와 공통 packet 자체가 이미 현재 frame에 묶여 있었다.
- **발동 신호**: reviewer가 “주어진 범위 안에서는 좋다”고 하지만 사용자 목적과의 연결을 평가하지 못한다.
- **바뀌는 판단·행동**: reviewer에게 `입력으로는 판정 불가`, `질문 자체가 좁음`, `이 역할의 source가 없음`을 반환할 권한을 준다.
- **좋은 적용**: reviewer가 더 많은 content가 아니라 최초 동기를 지원하는 원천의 역할을 요청한다.
- **잘못된 적용**: 모든 reviewer가 사용자 목적을 자유롭게 재작성하게 한다.
- **비적용 조건**: 사실 verifier나 schema checker처럼 질문 변경이 역할 밖인 경우.
- **전이 예**: incident reviewer가 제공 로그만으로 원인을 단정하지 않고 missing telemetry를 보고한다.
- **합의 상태**: 일반화 후보.

### 32. main의 회수도 별도 판별 대상이다

- **정의**: reviewer 결과를 채택·조정·기각하는 main의 판단이 기존 frame을 다시 주입하거나 새 관찰을 과도하게 흡수할 수 있으므로 회수 과정을 별도 본다.
- **AI-native 메커니즘**: main은 전체 context를 가진 장점과 기존 선택에 오염된 단점을 동시에 갖는다.
- **관찰 근거**: 독립 판별의 결과를 main 언어로 즉시 합치면 차이가 사라진다는 기존 정정이 있었다. A/B main adjudication은 active-state의 중심을 현재 합의로 보고 B를 진행했지만, 이후 사용자는 그 중심 자체의 계보를 다시 문제 삼았다.
- **발동 신호**: 독립 review는 새로운 문제를 냈는데 main 회수 후 기존 구조의 국소 수정으로 줄어든다.
- **바뀌는 판단·행동**: reviewer 관찰, main 해석, 사용자 판단을 합치기 전까지 분리해 보존한다.
- **좋은 적용**: main이 review 제안을 적용 범위와 권한으로 분류한 뒤, 중심 변경은 사용자에게 올린다.
- **잘못된 적용**: main을 불신해 adjudication 없이 reviewer 결과를 모두 사용자에게 떠넘긴다.
- **비적용 조건**: 단순 verifier 결과처럼 main의 해석 여지가 거의 없는 경우.
- **전이 예**: benchmark 결과를 제품 결론으로 번역하는 의사결정자를 별도 검토한다.
- **합의 상태**: 일반화 후보.

### 33. evaluation이 실제로 무엇을 평가하는지 먼저 선언한다

- **정의**: artifact quality, brief 충실도, 사용자 목적 적합성, factual correctness, reader experience, system effectiveness를 하나의 “평가”로 부르지 않는다.
- **AI-native 메커니즘**: agent 이름이 `reviewer`, `judge`, `verifier`여도 실제 입력과 rubric이 평가 범위를 결정한다.
- **관찰 근거**: draft-only review, source+result improvement review, fact verifier, editorial review가 서로 다른 관찰을 했지만 일부 PASS가 전체 품질처럼 읽혔다.
- **발동 신호**: reviewer verdict가 왜 사용자 판단과 충돌하는지 설명할 수 없다.
- **바뀌는 판단·행동**: evaluation 전에 target, input boundary, authority, unsupported conclusions를 적는다.
- **좋은 적용**: cold reader는 처음 읽힘만, evidence checker는 claim support만 보고한다.
- **잘못된 적용**: 역할 설명이 너무 길어 실제 review보다 계약 작성이 커진다.
- **비적용 조건**: 이미 표준화되고 오해 가능성이 없는 자동 check.
- **전이 예**: model benchmark score와 업무 성공률을 별개 evaluation으로 둔다.
- **합의 상태**: 거의 합의.

### 34. 완결 결과와 분리된 판단 위치는 양립한다

- **정의**: 사용자가 완결 결과를 보고 전체적으로 판단하는 방식과, exploration·construction·evaluation을 다른 판단 위치에서 수행하는 방식은 서로 반대가 아니다.
- **AI-native 메커니즘**: 산출물을 작은 조각으로 나누지 않아도 agent의 입력·질문·권한을 분리해 frame correlation을 줄일 수 있다.
- **관찰 근거**: post-v3 sync는 충분히 완결된 v1을 선호하면서 Material·Shaping·Texture를 한 v1 안의 다른 책임으로 뒀다. 현재 논의는 완결본 뒤 상위 판단까지 다시 보는 필요를 추가했다.
- **발동 신호**: “단계를 나누면 사용자가 조각마다 승인해야 한다”거나 “완결본을 만들면 판단 분리가 불가능하다”는 오해가 생긴다.
- **바뀌는 판단·행동**: artifact granularity와 judgment-role separation을 별도 설계한다.
- **좋은 적용**: writer는 완결 draft를 만들고 reviewer는 source와 goal을 다른 위치에서 본다.
- **잘못된 적용**: 이름만 다른 agent가 같은 prompt로 완결본을 연속 수정한다.
- **비적용 조건**: 하나의 좁은 deterministic transformation.
- **전이 예**: end-to-end prototype은 한 번 만들되 security와 product-value 판단은 다른 reviewer가 본다.
- **합의 상태**: 거의 합의.

### 35. 같은 결과를 다른 frame으로 재생성해 비교할 수 있다

- **정의**: 하나의 결과를 계속 수정하는 것 외에, source·질문·제약을 다르게 둔 독립 생성 결과를 만들어 frame의 영향을 비교한다.
- **AI-native 메커니즘**: AI는 여러 대안을 빠르게 만들 수 있어 input frame의 인과를 관찰할 기회가 생긴다.
- **관찰 근거**: source-first second pass는 기존 후보를 가린 뒤 새로운 후보군을 만들었다. A/B도 서로 다른 reviewer 기준을 비교했지만 source frame은 같아 변화 범위가 제한됐다.
- **발동 신호**: 수정본이 계속 기존 구조를 보존하고, 무엇이 artifact의 고유 강점인지 frame의 잔재인지 구분하기 어렵다.
- **바뀌는 판단·행동**: 의미 있는 한 축만 달리한 생성 pass를 두고 차이를 해석한다.
- **좋은 적용**: 동일 requirement를 기존 architecture 문서 포함/미포함 두 pass로 설계해 비교한다.
- **잘못된 적용**: 통제할 수 없는 많은 prompt variation을 만들고 결과 수만 늘린다.
- **비적용 조건**: canonical contract를 벗어난 대안 생성이 위험하거나 의미 없는 경우.
- **전이 예**: research synthesis를 기존 taxonomy 기반과 raw-source 기반으로 각각 만든다.
- **합의 상태**: 일반화 후보.

## scope, self-check, scaffolding과 학습을 보는 후보

### 36. 작은 scope에서도 가치가 생기는 책임 경로를 보존한다

- **정의**: 구현 폭은 줄여도 `사용자 입력 → 핵심 변환 → 사용자가 읽는 출력 → 다음 행동`처럼 가치가 실제로 생기는 경로는 끝까지 연결한다.
- **AI-native 메커니즘**: AI는 확실하고 완료로 세기 쉬운 fixture, raw response, UI shell을 내놓고 불확실한 핵심 변환을 후속 spec으로 미루기 쉽다.
- **관찰 근거**: 기존 scope-control 후보에서 “작게”가 제품 흐름을 잘랐고, 사용자는 이를 AI가 확실한 결과를 먼저 내는 경향으로 감지했다.
- **발동 신호**: demo는 돌아가지만 사용자는 핵심 결과를 얻지 못하고 다음 행동도 할 수 없다.
- **바뀌는 판단·행동**: 줄여도 되는 폭과 끝까지 관통해야 하는 causal path를 구분한다.
- **좋은 적용**: 한 종류 데이터만 지원해도 실제 input부터 usable recommendation까지 연결한다.
- **잘못된 적용**: 모든 기능을 end-to-end로 만들라는 이유로 scope를 줄이지 못한다.
- **비적용 조건**: 기술 spike처럼 사용자 가치보다 feasibility 확인이 명시적 목적일 때.
- **전이 예**: 조사 도구에서 검색 UI만 만들지 않고 최소 한 질문의 근거 있는 답까지 연결한다.
- **합의 상태**: 기존 후보로 거의 합의.

### 37. 눈에 보이는 쉬운 완료가 핵심 작용을 대체하는지 본다

- **정의**: 명시적 output이 있다는 사실과 어렵지만 가치 있는 중심 작용을 수행했다는 사실을 분리한다.
- **AI-native 메커니즘**: AI는 평가 가능한 표면 결과를 빠르게 만들며, 모호하고 불확실한 핵심 문제를 주변 artifact로 치환할 수 있다.
- **관찰 근거**: scope-control의 raw response·fixture·spec 대체, ai-note의 하네스·문서층 비대화, Current의 구조 설명이 발생 이유를 대신한 장면이 서로 닮아 있다.
- **발동 신호**: 파일·test·문서 수는 늘지만 사용자가 중요하다고 본 변화는 없다.
- **바뀌는 판단·행동**: output을 세기 전에 그것이 어떤 가치 인과를 완성하는지 묻는다.
- **좋은 적용**: 평가 dashboard가 실제 선택을 바꾸는지 확인한다.
- **잘못된 적용**: 문서·test·scaffolding을 모두 “가짜 일”로 취급한다.
- **비적용 조건**: 문서나 test 자체가 이번 작업의 명시적 최종 결과인 경우.
- **전이 예**: multi-agent orchestration 파일이 실제 task 완료를 돕는지, orchestration만 늘렸는지 본다.
- **합의 상태**: 일반화 후보.

### 38. self-check에서는 AI 자신의 판단과 행동을 원인에 넣는다

- **정의**: 외부 자료나 사용자 표현만 분석하지 않고 main이 만든 문제 정의, 추상화, tool 선택, scope, 다음 행동을 causal model에 포함한다.
- **AI-native 메커니즘**: 같은 판단자가 자신이 만든 frame으로 오류를 설명하면 외부 요인만 정교하게 분석하고 자기 개입은 빠뜨릴 수 있다.
- **관찰 근거**: Material 누락 오진은 실제 material을 확인하지 않은 main의 판단을 드러냈다. 기존 self-check 후보도 frame·전제·다음 행동을 검사 대상으로 정의했다.
- **발동 신호**: 설명은 길어지는데 왜 같은 오독이 반복됐는지 main 행동이 원인 목록에 없다.
- **바뀌는 판단·행동**: “사용자가 무엇을 놓쳤나”와 함께 “내가 무엇을 읽지 않았고 무엇을 고정했나”를 본다.
- **좋은 적용**: 잘못된 source packet을 만든 main의 선택을 review 실패 원인에 포함한다.
- **잘못된 적용**: 모든 실패를 자기 탓으로 돌려 외부 constraint와 실제 도구 한계를 지운다.
- **비적용 조건**: 외부 시스템 장애처럼 main 판단과 인과가 없는 경우.
- **전이 예**: bug triage에서 AI가 선택한 reproduction 범위와 로그 제외 결정을 분석한다.
- **합의 상태**: 거의 합의.

### 39. 정확한 자기진단, 다음 행동 변화, 재발 방지를 다른 결과로 본다

- **정의**: 오류를 잘 설명한 것, 바로 다음 행동이 달라진 것, 비슷한 상황에서 안정적으로 재발하지 않는 것을 서로 다른 완료 조건으로 둔다.
- **AI-native 메커니즘**: 언어 모델은 자기 오류를 설득력 있게 설명하면서도 같은 frame의 다음 action을 생성할 수 있다.
- **관찰 근거**: 기존 self-check 조사에서 정확한 설명 뒤 초안 작업으로 다시 전진하거나 양방향 과교정한 사건이 반복됐다.
- **발동 신호**: 사과와 원인 설명은 정확하지만 바로 다음 tool call이나 산출물이 이전과 같다.
- **바뀌는 판단·행동**: self-check 결과를 설명문이 아니라 행동 diff와 후속 재발 조건으로 확인한다.
- **좋은 적용**: 오독 원인을 설명한 뒤 source를 다시 읽고 plan을 실제로 바꾼다.
- **잘못된 적용**: 한 번의 행동 변화로 장기 재발 방지 효과를 입증했다고 말한다.
- **비적용 조건**: 사용자가 설명만 요청했고 후속 실행이 범위 밖인 경우.
- **전이 예**: coding agent가 root cause를 말한 뒤 같은 patch pattern을 반복하는지 본다.
- **합의 상태**: 거의 합의, 장기 효과는 근거 부족.

### 40. scaffolding과 quality loop를 구분한다

- **정의**: scaffolding은 출력 전후에 작업 구조, context, 역할, 재진입 경로를 제공하고, quality loop는 나온 결과를 보고 결과·goal·constraints·criteria 중 무엇을 바꿀지 판단한다.
- **AI-native 메커니즘**: 좋은 사전 구조도 약한 결과를 보장하지 못하며, 결과 개선 loop도 context가 유실되면 같은 판단을 복원하지 못한다.
- **관찰 근거**: Alex 원본에서 repo·README·역할·공통 절차를 만든 장면과 약한 solution report 뒤 제약·평가를 바꾼 장면은 별개다. Current는 scaffolding 영감의 계보와 품질 loop 논의에서 다른 역할을 갖는다.
- **발동 신호**: “scaffolding이 있으니 품질이 좋아진다” 또는 “loop만 돌리면 context가 필요 없다”는 주장이 나온다.
- **바뀌는 판단·행동**: 구조를 만드는 문제와 결과를 통해 구조를 갱신하는 문제를 따로 평가한다.
- **좋은 적용**: current가 재진입을 돕는지와 그 current의 goal·criteria가 약한 결과 뒤 갱신되는지를 별도로 본다.
- **잘못된 적용**: 둘을 분리한다는 이유로 연결을 끊고 scaffolding을 고정한다.
- **비적용 조건**: 단발성 좁은 task로 재진입 구조나 반복이 필요 없는 경우.
- **Alex 경계**: 최종 autonomous quality loop의 완료는 확인되지 않았다.
- **합의 상태**: 거의 합의.

### 41. output이 scaffolding의 결함을 드러내면 scaffolding도 수정 후보가 된다

- **정의**: context map, role contract, review packet, current 같은 구조는 결과를 만드는 원인이므로 결과에서 반복되는 누락이 구조와 연결되면 갱신할 수 있다.
- **AI-native 메커니즘**: scaffolding이 live context를 선택하고 권위를 배치하므로 품질 오류를 안정적으로 재생산할 수 있다.
- **관찰 근거**: active-state가 Q1~Q5를 주 장면으로 유지했고 A/B packet도 그 frame을 반영했다. review-workflow의 추가 source 권한만으로는 source map 바깥의 최초 동기를 복구하지 못했다.
- **발동 신호**: 다른 agent와 다른 편집 기준에서도 같은 material이 사라진다.
- **바뀌는 판단·행동**: 개별 output을 고친 뒤 scaffolding의 source role, center provenance, reopen condition을 검사한다.
- **좋은 적용**: current의 대표 장면과 열린 판단을 사용자 sync 뒤 갱신한다.
- **잘못된 적용**: 결과가 마음에 들지 않을 때마다 새 문서층과 agent를 추가한다.
- **비적용 조건**: 오류가 scaffolding을 우회한 단발 실행 실수로 확인될 때.
- **전이 예**: CI failure가 반복되면 test뿐 아니라 generated test world와 fixture ownership을 본다.
- **합의 상태**: 일반화 후보.

### 42. 사례를 표면 workflow가 아니라 판단 변화와 적용 경계로 전이한다

- **정의**: 다른 사람의 좋은 사례에서 절차·수치·파일 구조를 복제하기보다 어떤 문제를 보고 어떤 판단을 바꿨는지와 현재 작업의 차이를 함께 본다.
- **AI-native 메커니즘**: AI는 reference의 명시적 형식을 쉽게 복제하지만 암묵적 taste와 맥락 차이는 놓치기 쉽다.
- **관찰 근거**: Alex의 scaffolding을 Current에 그대로 복사하지 않았고, solution loop의 1~2주·virality·visual appeal 같은 세부 기준도 일반 core로 옮기지 않기로 했다.
- **발동 신호**: reference 이름과 단계는 남았는데 현재 문제와 연결되는 판단 이유를 설명할 수 없다.
- **바뀌는 판단·행동**: 확인된 원본 사실, 사용자가 동의한 해석, 현재 적용에서 변형한 점을 분리한다.
- **좋은 적용**: Alex의 제약 재평가 감각을 가져오되 해커톤 평가 항목은 가져오지 않는다.
- **잘못된 적용**: “본질만 남긴다”며 실제 사례의 조건과 유용한 구체성을 모두 지운다.
- **비적용 조건**: 표준 protocol을 정확히 따라야 하는 안전·호환성 작업.
- **전이 예**: 외부 팀의 agent architecture를 역할 수가 아니라 책임과 failure mode로 비교한다.
- **합의 상태**: 거의 합의.

### 43. 학습 기록은 규칙뿐 아니라 판단을 다시 만드는 재료를 남긴다

- **정의**: 나중에 같은 문장을 따르는 것보다 비슷하지만 다른 상황에서 판단축을 복원하도록 정의, 실패 근거, 대비 사례, 발동 신호, 잘못된 적용, 열린 질문을 함께 남긴다.
- **AI-native 메커니즘**: AI와 사람 모두 압축된 rule을 문자 그대로 재사용해 원래 문제와 다른 곳에 과잉 적용할 수 있다.
- **관찰 근거**: 사용자는 이번 논의가 기준 한 줄로 끝나면 배우지 못하고 휘발된다고 우려했고, core를 문제 해결과 추후 역량 구체화에 함께 쓰려 했다.
- **발동 신호**: “다음엔 Material로 돌아가자” 같은 행동 규칙만 남고 왜·언제·언제 아닌지가 없다.
- **바뀌는 판단·행동**: process에는 실제 사건을, core 후보에는 재사용 가능한 판단과 경계를 연결한다.
- **좋은 적용**: `source presence/action`을 Current와 구현 사례의 대비로 남긴다.
- **잘못된 적용**: 학습을 명분으로 모든 대화와 예외를 core에 복사한다.
- **비적용 조건**: 단순 tool syntax나 변하지 않는 기계 절차.
- **전이 예**: postmortem에서 “test 추가”뿐 아니라 왜 기존 test가 같은 세계를 공유했는지 남긴다.
- **합의 상태**: 목적은 거의 합의, 문서 형식은 사용자 판단 필요.

### 44. 보존, 현재 권위, 실행, 교체 범위를 분리한다

- **정의**: 기억해야 하는 사례, 지금 따라야 하는 contract, 매번 실행할 검증, 결과 변경 시 함께 교체할 artifact를 같은 범위로 묶지 않는다.
- **AI-native 메커니즘**: AI가 만든 많은 fixture·문서·review를 모두 live context나 mandatory loop로 승격하면 관리 표면이 급증한다.
- **관찰 근거**: 기존 원본의 diagnostic fixture 보존과 비싼 live 실행 분리, process와 active contract 분리, artifact/core 후보가 이 문제를 서로 다른 사례로 보여 줬다.
- **발동 신호**: 한 번 유용했던 check나 문서가 모든 cycle의 의무가 된다.
- **바뀌는 판단·행동**: `남길까`, `현재 권위인가`, `매번 실행할까`, `무엇과 함께 바꿀까`를 따로 묻는다.
- **좋은 적용**: 실패 fixture는 보존하되 일부만 regression suite에 둔다.
- **잘못된 적용**: 분리 원칙을 명분으로 canonical contract와 evidence의 연결을 끊는다.
- **비적용 조건**: 보존과 매회 실행이 안전상 동일해야 하는 필수 check.
- **전이 예**: research corpus 전체와 매 query에 넣을 active context를 구분한다.
- **합의 상태**: 일반화 후보.

### 45. loop를 계속 돌릴지 멈추고 frame을 바꿀지 구분한다

- **정의**: 반복 생성·평가가 실질적 간극을 줄이는지, 같은 frame 안의 polish만 늘리는지 관찰해 continue·pause·reframe을 다르게 선택한다.
- **AI-native 메커니즘**: 자동 loop는 measurable criterion을 끝없이 최적화하면서 사용자 가치의 정체를 숨길 수 있다.
- **관찰 근거**: 여러 draft/review cycle이 사실과 표현을 개선했지만 중심 material은 회복하지 못했다. Alex의 final autonomous loop는 완료가 확인되지 않아 효과 사례로 쓸 수 없다.
- **발동 신호**: version은 늘고 부분 지표는 좋아지지만 같은 상위 불만이 남는다.
- **바뀌는 판단·행동**: 다음 iteration 전에 무엇이 새롭게 학습됐고 어떤 판단이 바뀌는지 확인한다.
- **좋은 적용**: 두 cycle 연속 같은 frame 문제가 나오면 자동 writer loop를 멈추고 goal/source audit를 한다.
- **잘못된 적용**: 한 번의 약한 결과 뒤 iteration 자체를 포기한다.
- **비적용 조건**: 수렴 가능한 deterministic optimization과 명확한 stopping criterion이 있는 경우.
- **전이 예**: model tuning에서 score improvement와 task definition validity를 별도로 본다.
- **합의 상태**: 일반화 후보.

## 아직 독립 후보로 보존할 약한 설명

다음은 다른 후보와 겹치지만 현재 단계에서 버리지 않는다.

### 46. 압축이 정확성을 높이면서 의미 재료를 줄일 수 있다

- **가설**: AI는 사실 방어, 단일 중심, 짧은 구조를 강화할 때 motive·voice·가능한 value까지 함께 제거할 수 있다.
- **근거**: v3는 더 정확하고 짧아졌지만 Current의 통제력, self-check의 넓은 문제, scope의 AI 판단 경향이 약해졌다.
- **좋은 적용**: 압축 뒤 사실만 아니라 중심 material과 사용자의 문제의식을 reverse trace한다.
- **위험**: 모든 긴 초안을 “풍부하다”고 보호할 수 있다.
- **합의 상태**: 일반화 후보.

### 47. 명료한 artifact가 모호하지만 중요한 사용자 기억을 이길 수 있다

- **가설**: 문서화된 Q1~Q5와 표는 명료했지만 current를 만든 최초 문제와 Alex 영감은 사용자 기억에 더 많이 남아 있어 context 경쟁에서 졌다.
- **근거**: A/B 이후 사용자 기억이 핵심 계보를 복구했다.
- **좋은 적용**: 명료성 자체를 권위로 보지 않고 provenance와 목적을 함께 본다.
- **위험**: 확인되지 않은 기억을 source보다 우선시할 수 있다.
- **합의 상태**: 근거 부족 보류. 기억과 원천 교차 확인이 필요하다.

### 48. frame 다양성은 reviewer 다양성보다 먼저 설계될 수 있다

- **가설**: 다른 reviewer를 부르기 전에 source frame, question, output resolution을 어떻게 다르게 둘지 설계하는 편이 실제 판단 다양성을 더 크게 만들 수 있다.
- **근거**: A/B의 기준 차이보다 공통 packet의 영향이 컸고, source-first second pass는 새로운 후보를 만들었다.
- **좋은 적용**: reviewer A/B를 단순 역할명 차이가 아니라 서로 다른 독립 변수로 둔다.
- **위험**: 인위적 변형이 실제 사용자 목적과 무관한 결과만 늘릴 수 있다.
- **합의 상태**: 일반화 후보.

### 49. 품질 신호의 provenance도 보존한다

- **가설**: “좋다/나쁘다”뿐 아니라 누가 어떤 결과와 비교해 무엇을 감지했는지를 남겨야 다음 판단에서 신호의 역할을 복원할 수 있다.
- **근거**: 사용자는 A의 제목과 생생함은 보존하면서 중심 frame은 거부했다.
- **좋은 적용**: 긍정·부정 신호를 결과 전체 verdict로 합치지 않는다.
- **위험**: 모든 감상을 상태표로 만들어 작업을 무겁게 한다.
- **합의 상태**: 일반화 후보.

### 50. “근본 원인”을 한 개로 닫지 않고 경쟁 설명을 유지한다

- **가설**: Current 실패는 material 전달 실패, goal 계층 혼동, source packet frame, reviewer correlation, criteria 권한, main 회수, 사용자 합의 provenance 등 여러 인과 후보가 함께 만들었을 수 있다.
- **근거**: 각 수정 cycle은 일부 문제를 고쳤지만 다른 문제가 남았고, 한 번의 `Material skipped` 진단은 틀렸다.
- **좋은 적용**: 경쟁 설명마다 반례와 구별 관찰을 둔다.
- **위험**: 원인 후보를 계속 늘려 실제 조치를 못 고른다.
- **합의 상태**: 확장 방식은 거의 합의, 최종 인과는 사용자 판단 필요.

## 현재 보존할 중복 묶음

다음 후보들은 수거 단계에서 합칠 수 있지만 지금은 서로 다른 질문을 보존하기 위해 분리한다.

- `01 결과와 판단 체계 분리`, `08 평가 체계 학습`, `41 scaffolding 갱신`
  - 첫 후보는 평가 대상, 두 번째는 loop가 배우는 대상, 세 번째는 context 구조의 변경 가능성을 본다.
- `02 결과를 관찰물로 사용`, `03 필요한 만큼 통합`, `34 완결 결과와 판단 분리 양립`
  - output의 역할, 해상도, 작업 구조를 각각 본다.
- `09 goal 층위`, `10 작업 가설`, `11 합의 provenance`, `12 goal 개선`
  - 의미 층위, 임시성, 권한, 변화 방식을 각각 본다.
- `17 source 작동`, `18 발생 계보`, `19 packet 선택`, `20 source-first pass`
  - source의 실제 영향, 동기, 입력 설계, anchor 제거를 각각 본다.
- `26 판단 순서`, `27 criteria 역할`, `28 criteria 권한`
  - 판단 행위, 기준 사용 방식, 변경 권한을 각각 본다.
- `29 reviewer 독립성`, `30 correlated review`, `31 질문 재개방`, `32 main 회수`
  - reviewer contract, 결과 해석, 문제 frame 권한, 후속 adjudication을 각각 본다.
- `38 self 원인 포함`, `39 행동 변화`, `43 학습 기록`
  - 진단 대상, 성공 기준, 장기 재사용을 각각 본다.

## 이 문서가 아직 하지 않는 일

- 후보 수를 줄이지 않는다.
- 원본 workspace core에 들어갈 문장으로 다듬지 않는다.
- 모든 후보를 한 workflow로 연결하지 않는다.
- Current 글의 다음 구조를 정하지 않는다.
- Alex의 구체 절차를 일반 규칙으로 올리지 않는다.
- 반복 사례가 약한 후보를 강한 원칙처럼 쓰지 않는다.
