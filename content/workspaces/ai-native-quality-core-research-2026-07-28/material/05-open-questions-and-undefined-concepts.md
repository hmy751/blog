# Open Questions and Undefined Concepts

이 문서는 답을 고르기 전에 무엇이 아직 정의되지 않았는지 보존한다. 비슷해 보이는 질문도 판단 대상이 다르면 합치지 않는다.

## 1. 품질은 무엇이 좋아진 상태인가

- 결과물의 내부 완성도와 사용자가 원한 결과에 가까워진 정도는 어떻게 구분하는가
- 사실 정확성, 구조, 독자 경험, 실제 행동 변화, 사업 가치, 학습 가치가 서로 충돌할 때 무엇이 상위 판단인가
- reviewer의 통과와 사용자의 `좋다`가 갈리면 각각 무엇을 측정한 것인가
- 사용자가 아직 정확히 설명하지 못하지만 결과를 보고 `아니다`라고 느끼는 판단은 어떻게 다루는가
- taste를 단순 취향과 축적된 제품 판단으로 어떻게 구분하는가
- 품질 기준을 언어화하면 판단이 안정되는가, 아니면 언어화 가능한 것만 과대평가하는가
- 하나의 결과가 품질을 증명하는가, 아니면 현재 frame에서의 가능성만 보여주는가
- 결과가 좋아졌지만 사용자가 얻은 이해와 역량이 늘지 않았다면 이번 작업은 성공인가

## 2. Goal이라는 말 안에 무엇이 섞여 있는가

- 사용자가 이 작업을 시작한 이유와 이번 cycle에서 만들 결과의 목표는 같은가
- 상위 목적, 현재 문제 정의, 작업 가설, 성공 조건, output contract, 제약은 어떤 관계인가
- `Current 글을 개선한다`는 goal과 `AI-native 협업 감각을 공개 글로 드러낸다`는 목적은 어떻게 다른가
- 결과가 약할 때 복구해야 할 원래 의도와 수정해야 할 작업 goal을 어떻게 구분하는가
- goal이 실제로 없었던 경우와 있었지만 전달 과정에서 사라진 경우는 어떤 증거로 나누는가
- 사용자가 명시한 goal과 AI가 행동을 통해 사실상 최적화한 goal은 어떻게 대조하는가
- 평가 기준이 goal을 구체화하는가, 아니면 goal과 별개로 결과를 재단하는가
- 결과를 본 뒤 goal을 바꾸는 것이 학습인지, 실패를 정당화하는 goalpost 이동인지 어떻게 판정하는가
- top-level goal을 누가 바꿀 수 있는가
- loop goal과 상위 목적이 충돌할 때 어느 쪽을 유지하는가
- goal은 문장 하나로 충분한가, 아니면 대비 사례와 통과·실패 장면이 필요한가
- goal을 너무 자세히 쓰면 탐색을 잠그고, 너무 느슨하게 쓰면 AI가 쉬운 대체물을 고르는 문제를 어떻게 조절하는가

## 3. Context와 source는 언제 실제로 작동하는가

- AI가 source를 읽었다는 것과 결과가 source의 의미를 보존했다는 것을 어떻게 구분하는가
- source packet을 고른 main의 frame을 reviewer가 어떻게 문제 삼을 수 있는가
- 빠진 material은 양의 부족인가, 역할과 위계가 전달되지 않은 것인가
- source가 결과의 사실, 동기, 중심, 장면, 평가 기준 중 어디에 작동해야 했는지 어떻게 남기는가
- 모든 source를 주지 않고도 중요한 가능성을 닫지 않는 최소 입력은 무엇인가
- 많은 context가 reviewer를 anchoring하고, 적은 context가 사용자 목적을 지우는 긴장을 어떻게 다루는가
- 현재 source가 약한 경우 더 조사할지 claim을 낮출지 후보를 보존할지 누가 판단하는가
- direct source와 사용자의 현재 해석이 충돌할 때 무엇을 수정하고 무엇을 보류하는가
- source의 원문을 보존해야 하는 경우와 재접근 링크만으로 충분한 경우는 어떻게 다르나
- 하나의 source가 여러 후보를 지지할 때 초기 분류가 후속 탐색을 가두지 않게 하려면 어떻게 하는가

## 4. Constraints는 품질을 지키는가, 야심을 줄이는가

- 공개 경계, 사실 상한, 시간, 구현 가능성, 독자 진입성 중 어떤 제약이 hard constraint인가
- constraint가 핵심 위험을 막은 것과 가치 있는 가능성까지 잘라낸 것을 어떻게 대조하는가
- AI가 제약을 문자 그대로 지켜 쉬운 결과를 만들었을 때 문제는 agent, constraint, goal, evaluation 중 어디에 있는가
- 제약을 완화했을 때 좋아진 결과가 실제 품질 향상인지 단순히 더 화려해진 것인지 어떻게 판단하는가
- `작게 시작하라`, `한 질문에 집중하라`, `주장 상한을 지켜라` 같은 좋은 기준이 어떤 시점에 나쁜 생성 압력이 되는가
- 서로 다른 단계에 같은 constraint를 적용해도 되는가
- human의 실제 역량 상한을 AI가 모를 때 scope를 누가 어떻게 정하는가
- 과감한 후보 생성과 public-safe evidence 경계를 동시에 유지할 수 있는가
- constraint가 현재 작업용 임시값인지 반복 core 원칙인지 어떻게 표시하는가

## 5. Criteria는 seed인가 filter인가

- 평가 기준을 후보 생성 전에 주면 후보가 풍부해지는가, 비슷해지는가
- 같은 기준을 생성 압력과 탈락 기준으로 모두 써도 되는가
- impact, creativity, uniqueness처럼 넓은 축을 구체화하지 않고도 유용하게 쓸 수 있는가
- 사실 정확성처럼 처음부터 적용할 기준과 후보 가치처럼 나중에 수렴할 기준을 어떻게 나누는가
- 여러 기준을 합산 점수로 만들지 않아도 비교 결정을 내릴 수 있는가
- 한 축의 실패가 다른 축의 실패로 번지는 것을 어떻게 막는가
- reviewer가 새 criteria를 제안할 권한과 그것이 현재 criteria가 되는 권한은 어떻게 다른가
- 결과가 기존 criteria를 모두 통과했는데도 나쁠 때 criteria가 빠진 것인지 frame이 틀린 것인지 어떻게 구분하는가
- criteria를 더 추가하는 것이 문제를 해결하는 경우와 기존 frame을 더 강하게 보호하는 경우는 어떻게 다른가
- criteria 갱신의 근거는 반복 횟수, 사용자 합의, 다른 사례 전이 중 무엇이어야 하는가

## 6. 결과물은 답인가, probe인가

- 최종 후보와 평가용 관찰물이라는 두 역할이 충돌하는가
- 무엇을 판단하느냐에 따라 필요한 통합 수준이 어떻게 달라지는가
- 글의 전체 흐름, solution의 야심, 구현 feasibility, 사용자 행동 변화는 각각 어떤 artifact가 있어야 보이는가
- 완결본을 만들 비용이 큰 경우 어떤 중간 artifact가 같은 위험을 먼저 드러낼 수 있는가
- 중간 artifact의 형식이 중요한 품질을 보이지 않게 만들 수 있는가
- output-first가 이름과 기능 목록보다 나은 경우는 언제인가
- 보이는 output이 내부 causal path나 보이지 않는 안정성을 밀어내는 경우는 언제인가
- completion과 acceptance를 상태로 어떻게 구분할 것인가
- 읽을 수 있는 결과, 시험 가능한 결과, 수용된 결과, 검증된 결과는 같은가
- 여러 완결본이 같은 frame에서 나왔을 때 더 만들기보다 무엇을 바꿔야 하는가

## 7. 판단 분리는 정확히 무엇을 분리하는가

- material, shaping, texture 같은 책임 분리와 artifact version 분리는 어떻게 다른가
- builder와 reviewer가 같은 사람이어도 판단 위치를 분리할 수 있는가
- 다른 agent를 호출해도 같은 질문과 packet을 주면 무엇이 독립적이지 않은가
- 탐색과 수렴을 시간으로 분리해야 하는가, 권한이나 문서로만 분리해도 되는가
- 결과 판정과 결과를 만든 system 판정을 같은 reviewer가 할 수 있는가
- fact verifier, first reader, source+result reviewer, advisor는 어떤 질문에서 서로 대체되지 않는가
- main adjudication이 독립 관찰을 다시 기존 frame에 흡수할 위험을 어떻게 볼 것인가
- evaluator가 주어진 문제 자체를 열 수 있을 때 사용자 목적까지 바꾸지 않게 하는 경계는 무엇인가
- 여러 독립 판정의 불일치는 오류인가, 탐색해야 할 판단축인가
- 독립 판정이 필요한 시점과 main이 직접 판단하는 편이 나은 시점은 무엇인가

## 8. Frame은 무엇이며 어떻게 보이는가

- frame은 goal, source selection, 대표 사례, 질문, article type, 평가 기준의 조합인가
- 같은 사건 universe 안에서 중심만 바꾸는 것은 frame 전환인가
- A와 B가 다른 구조를 만들었어도 같은 frame이라고 판단한 근거는 무엇인가
- frame을 벗어나라는 지시가 또 다른 무제한 발산 지시가 되지 않게 하려면 무엇을 보존하는가
- reviewer가 frame을 직접 이름 붙이지 못해도 frame 고착을 발견할 수 있는 신호는 무엇인가
- 여러 reviewer의 동의가 공통 frame의 상관된 결과인지 독립된 수렴인지 어떻게 구분하는가
- 사용자의 반복된 `아니다`가 frame 문제라는 증거가 되는 시점은 언제인가
- frame을 바꾸면 이전 결과에서 살아 있는 부분을 어떻게 보존하는가
- frame 변경이 단순한 제목·오프닝 변경과 다른 점은 무엇인가

## 9. 합의 상태와 권한을 어떻게 보존하는가

- 사용자 합의, 사용자 예시, 열린 질문, main의 작업 가설, reviewer 제안, 미채택 후보, 과거 판단을 어떻게 구분하는가
- 말이 명료하고 문서에 적혀 있다는 이유로 더 높은 권위를 얻는 문제를 어떻게 막는가
- active-state가 현재 그림을 압축하면서 판단 출처를 잃지 않으려면 무엇이 필요한가
- 모든 결정에 provenance를 붙이면 문서가 무거워지는 문제를 어떻게 피하는가
- 임시 중심이 몇 cycle 동안 사용됐다고 사용자 합의가 되는가
- reviewer 제안이 반복되면 언제 core 후보로 올라가는가
- 사용자 부재 중 AI가 처리할 수 있는 판단과 반드시 물어야 하는 판단은 어떻게 구분하는가
- AI가 사용자의 거친 생각을 더 명료한 문장으로 바꿀 때 의미 권한도 바뀌는가
- 과거 사용자의 말과 현재 사용자의 판단이 달라졌을 때 무엇을 current로 남기고 무엇을 process로 보낼 것인가

## 10. Loop는 무엇을 갱신하는가

- 한 loop의 대상은 artifact인가, 기준인가, goal인가, 전체 작업 체계인가
- 모든 loop가 같은 구조를 가져야 하는가
- 결과 수정과 criteria update가 동시에 필요한 경우 어느 쪽을 먼저 하는가
- 평가 결과가 다음 구현뿐 아니라 다음 평가 방법을 바꿀 수 있는가
- evaluator 자체가 놓친 문제를 누가 평가하는가
- loop를 몇 번 돌릴지보다 멈출 조건을 어떻게 정하는가
- 같은 문제가 반복될 때 더 강하게 반복할지 상위 판단을 다시 열지 어떻게 정하는가
- autonomous loop와 human-led loop의 적절한 경계는 무엇인가
- 비싼 다음 단계의 human gate와 모든 단계의 승인 병목을 어떻게 구분하는가
- loop가 목표를 향해 수렴하는지 goalpost를 계속 움직이는지 어떻게 본다
- 성공한 결과에서 무엇을 기준으로 남기고 무엇을 우연으로 본다
- 실패한 결과가 여러 원인을 동시에 드러낼 때 한 번에 무엇을 바꿀 것인가

## 11. Scaffolding과 quality loop는 어떻게 연결되는가

- scaffolding은 산출물 전에 무엇을 보존해야 하는가
- 전체 지도, 현재 cursor, source 권위, 역할, 공통 절차 중 어떤 것이 필수인가
- scaffolding이 오래되거나 잘못된 frame을 안정적으로 보존하는 경우는 어떻게 발견하는가
- quality loop 결과가 scaffolding 자체를 갱신할 수 있는가
- scaffolding을 매번 새로 만들지 않고 다른 context에 재사용하려면 무엇을 고정하고 무엇을 분리하는가
- context를 자세히 적는 것과 다음 agent가 중요한 판단을 복원할 수 있는 것은 같은가
- Current는 sync scaffolding이고 core는 operation scaffolding이라고 나눌 수 있는가
- 실행 scaffold와 학습용 설명 scaffold가 같은 문서에 있어야 하는가

## 12. 문제 해결과 학습을 함께 남긴다는 것은 무엇인가

- 다음 AI가 행동할 규칙과 사용자가 사고를 배울 설명은 같은 문장으로 충족되는가
- core에 결론만 남기면 왜 그 판단이 생겼는지 복원할 수 있는가
- 반대로 모든 시행착오를 남기면 현재 판단을 찾기 어려워지지 않는가
- 원리, 대비 사례, 발동 신호, 한계, 열린 질문 중 무엇이 판단 감각 복원에 실제로 필요한가
- process chronology와 core 설명의 적절한 분업은 무엇인가
- 한번의 실패에서 얻은 감각을 core 후보로 남기는 것과 반복 규칙으로 채택하는 것은 어떻게 다른가
- 사용자가 나중에 읽고 배웠는지 확인할 수 있는가
- core가 실제 다음 작업에서 사용되지 않아도 개념을 구체화한 가치가 있는가
- 학습을 위해 남긴 설명이 AI에게 또 다른 고정 template가 되는 위험은 어떻게 줄이는가

## 13. 글쓰기 밖으로 전이할 때

- 코드 구현에서 `문장은 좋지만 중심이 틀림`에 대응하는 현상은 무엇인가
- test가 모두 통과하지만 제품이 원한 행동이 아닌 경우 어느 판단을 다시 여는가
- 조사에서 많은 근거를 모았지만 처음 질문이 틀린 경우 어떤 artifact가 이를 드러내는가
- multi-agent 구현에서 여러 worker가 같은 잘못된 spec을 정확히 구현한 경우 독립 review는 무엇을 봐야 하는가
- 제품 아이디어에서 feasibility guard가 ambition을 죽인 경우와 실제로 무모함을 막은 경우를 어떻게 구분하는가
- 장기 context에서 최신 상태가 전체 목적을 덮는 문제는 글쓰기와 구현에서 같은가
- 사용자 경험을 모르는 AI가 scope와 priority를 자동으로 닫아도 되는 범위는 어디까지인가
- 정량 metric이 있는 작업과 taste 중심 작업에서 evaluation 갱신 방식은 어떻게 다른가
- 되돌리기 쉬운 artifact와 비싼 외부 실행에서 human gate 기준은 어떻게 달라지는가

## 14. 이 workspace 자체에 대한 열린 질문

- 확장 단계가 충분하다고 느낄 기준은 무엇인가
- 후보가 많이 생겼지만 모두 Current의 언어를 바꾼 것뿐인지 어떻게 대조할 것인가
- 어떤 다른 실제 프로젝트 사례를 더 읽어야 범용성을 판단할 수 있는가
- 서로 다른 후보를 상위 원리로 합칠 때 어떤 구체성이 사라지는가
- core 최종본은 실행 계약, 학습 문서, 사례집 중 어느 역할을 얼마나 가져야 하는가
- 원본 workspace core로 옮길 것과 이 독립 조사 workspace에만 남길 것은 무엇인가
- 사용자 판단이 필요한 후보를 한 번에 어떻게 보여줘야 다시 과도한 압축이나 과도한 부담이 되지 않는가
- 필터 단계에서 `최소`를 다시 성공 조건으로 삼지 않으려면 무엇을 평가해야 하는가
