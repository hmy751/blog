# Context와 material ledger

## 작업 목적

이번 작업의 목표는 다섯 후보를 다시 평가하거나 기준을 더 만드는 것이 아니다. 현재 중심을 유지한 채, post-sync v1에서 설명문으로 압축된 실제 사건과 판단 이동을 되살려 사용자가 글 자체로 방향을 판단할 수 있는 near-final v3를 만드는 것이다.

사용자는 낮은 해상도의 초안과 기준 문서를 다시 대조해 후보를 골라야 하는 반복을 원하지 않는다. 따라서 main이 backlog, 기존 초안, review, 직접 원천을 모두 입력으로 종합하고 다섯 편을 같은 깊이까지 구현한다. v3 이후에야 글에서 거꾸로 어떤 재료가 실제로 작동했는지 판단한다.

## 입력 권위

1. [active-state 기준](../../../core/criteria.md)과 [현재 후보 중심](../../context-structure/legacy-active-state/topic-candidates.md)
   - 글의 현재 중심과 이미 닫힌 사용자 합의를 소유한다.
2. 직접 원천, code, test, Git snapshot
   - actor, 시간순서, 수치, 실제 변경, 제안과 구현의 구분, 주장 상한을 소유한다.
3. 기존 v1~v3와 post-sync v1
   - 살아 있는 문장, 장면 후보, 구조 시도와 실패를 보여 준다.
4. 기존 material·shaping·review·main 판정
   - 무엇이 빠졌고 어떤 과교정이 있었는지 보여 주는 판단 재료다.
5. 이번 cycle의 독립 material·source report
   - 원천 누락과 public-safe artifact를 찾는 보조 판단이다. 자체로 중심을 바꾸지 않는다.

## 공통 진단

post-sync v1은 중심과 주장 상한을 회수했지만, 다섯 편 모두 실제 사건보다 운영 언어가 앞섰다. 표면도 `실패 → 개념 구분 → 질문 목록 → 한계 → 운영 기준`으로 수렴했다. 이 상태에서 문장 polish만 하면 사실은 안전해져도 사용자가 말한 “매력”과 “풍부함”은 돌아오지 않는다.

이번 v2에서는 글마다 다음을 실제 본문 장치로 만든다.

- 관찰된 출력이나 artifact가 먼저 차이를 보여 주는 주 장면
- 사용자가 무엇을 보고 멈췄고 AI의 판단이 어디서 이동했는지 보이는 시간축
- 해당 article type에 맞는 서로 다른 전개와 결말
- 한계를 글 끝에서 반복 방어하지 않고 제한할 주장 바로 옆에 두는 구조

## 글별 material 계약

### 1. Current / active-state operation

현재 중심:

- 긴 AI 작업에서 과거를 보존하는 상태와 지금 행동을 제어하는 상태는 같은 갱신 규칙을 가질 수 없다.
- 전체 지도, 한 개의 현재 cursor, active contract, history, 직접 원천은 서로 다른 역할을 가진다.
- 이 구조는 실제로 유용했지만 최근성 편향과 마지막 외부 사건 누락을 자동으로 막지는 않았다.

주 장면:

- 한 구현 loop의 살아 있는 완료 조건과 선택 이유가 process 문서 안에 함께 있던 상태에서 시작한다.
- 사용자의 지적으로 현재 goal·acceptance·evidence는 active contract가, 선택 이유와 실행 이력은 history가 소유하도록 분리한다.

두 번째 장면:

- 프로젝트 전체를 묻는 제출 문항이 직전에 끝낸 구현 사건에 끌린다.
- 이 어긋남을 발견한 것은 문서가 아니라 사용자다.
- 답을 보강하지 않고 질문별 시간축을 나눈 뒤 전체 질문은 조사·문제 정의·출력 비교·사람의 선택으로, 최신 구현 질문은 current cursor와 실행 원천으로 내려간다.

본문 artifact:

1. `분리 전 / 분리 후` 권위 이동 표
2. `프로젝트 전체 질문 / 최신 구현 질문`의 서로 다른 read trace

고유 narrative engine:

- 문서 분류 설명보다 “같은 문장이 서로 다른 수명과 권한을 가져 충돌한 설계 문제”를 따라가는 product-architecture 글.
- 결말은 기록량이 아니라 갱신 ownership과 읽는 시간축으로 닫는다.

주장 상한:

- 18개 current 변경 version과 13회 marker 전환은 실제 운용 흔적이지 품질·생산성 지표가 아니다.
- 설문 복구는 사용자 정정, current map, 직접 원천, 병렬 최신 결과가 함께 만들었다.
- 마지막 사건 누락의 원인을 ownership 하나로 단정하지 않는다.

### 2. 독립 판별 / 제3판별자

현재 중심:

- 독립 판별은 별도 AI의 수가 아니라 구현자와 다른 입력·질문·권한을 가진 판단 위치다.
- 판별 출력은 기존 완료 설명에 흡수되기 전에 별도 상태로 남고, main은 원자료와 재실행으로 회수한다.

주 장면:

- 한 여행 조건 판별 plugin의 첫 checkpoint에서 Python `unittest` test method 9개와 별도 validator·CLI가 통과한다.
- read-only 판별자는 설치형 자연어 E2E 부재, 공개 source와 fixture의 모순, 문자열 `"false"`의 타입 공백, 참여자 범위 누수, 상반된 답변의 배열 순서 의존을 찾는다.
- test는 거짓말하지 않았다. 구현·fixture·기대 결과·완료 설명이 공유한 세계 안의 일관성을 확인했다.

교정과 재실행:

- 기능 폭을 넓히지 않고 첫 제품 경로를 source와 실제 입력 형태에서 다시 닫는다.
- 교정 뒤 같은 runner의 test method 15개, 별도 validator·CLI, 설치한 새 작업의 자연어 E2E, 짧은 회귀 판별을 확인한다.
- 충분한 답변은 관련 상태만 바꾸고 다음 행동을 `추가 확인`에서 `결제 검토`로 이동시킨다. 다른 충돌과 준비 부담은 보존한다.

본문 artifact:

1. 검증 역할별 `9 / 15 / 숫자 밖의 검증` 표
2. 공개용 `"false"` 최소 재현
3. `판별 → 원자료 대조 → 판정 → 교정 → 재실행 → 남은 범위` trace

고유 narrative engine:

- 첫 checkpoint를 법의학적으로 해부하고 같은 checkpoint를 다시 닫는 technical-case-study.
- 결말은 reviewer 수가 아니라 검증 세계의 경계와 완료 선언 권한으로 닫는다.

주장 상한:

- 9→15를 제품 품질이나 사용자 가치 향상으로 쓰지 않는다.
- 첫 판별자와 회귀 판별자는 제출물 하나만 받은 clean-room 재현이 아니다.
- seller 답변은 실제 판매자 발화가 아니라 검증 fixture다.
- 별도 판정 호출도 닫힌 입력 밖을 자동 복구하지 못한 반례는 짧은 경계로만 쓴다.

### 3. 제품 흐름을 보존하는 scope control

현재 중심:

- `작게`, `안전하게`, `빨리 보이게`라는 압력 아래 가치가 생기는 불확실한 변환보다 완료로 세기 쉬운 중간 결과가 먼저 선택될 수 있다.
- 범위를 줄일 때 구현 폭은 줄여도 사용자가 확실성 차이를 읽고 다음 행동을 고르는 작용은 끝까지 남겨야 한다.

주 장면:

- 실제 자료에서 grounded answer를 만드는 첫 slice 대신, 검색 후보인 raw `facts[]`를 화면에 보여 주는 경로가 더 작은 구현으로 제안된다.
- 이것은 배포된 실패 UI가 아니라 구현 전 제안이다.
- 검색 후보는 디버깅에 유용하지만 사용자가 믿고 행동할 답변은 아니다.

후속 구현:

- 사용자 질문 → retrieval 후보 → 원문 grounding → 상태·값·근거가 붙은 답변 → chat 경로를 연결한다.
- source의 시각만 `15:00`에서 `16:00`으로 바꾸면 답도 바뀌는 metamorphic test, `supported` evidence가 실제 원문 부분 문자열인지 보는 grounding test, 실제 route가 답변 변환을 호출하는 routing test를 둔다.
- 호출자가 없던 별도 fact path를 제거한다.

본문 artifact:

1. `중간 결과 표시`와 `근거 상태를 가진 사용자 답변` 경로 대비
2. `15:00 / 16:00 / 원문에 시각 없음`일 때 값·상태·다음 행동이 달라지는 공개용 표

고유 narrative engine:

- 작은 구현안을 놓고 “어디서 제품 작용이 사라졌는가”를 따라가며 code path와 test로 복구하는 product-architecture 글.
- 결말은 UI가 아니라 실제 소비자가 받는 변환으로 닫는다.

주장 상한:

- raw 결과 화면과 deterministic adapter는 제안이지 실제 배포 실패가 아니다.
- `원문에 시각 없음 → missing`은 `15:00→16:00` test의 세 번째 arm이 아니라 별도 계약과 behavior를 합친 공개 설명이다.
- 세 test는 semantic quality 전체나 실제 사용자 의사결정 향상을 증명하지 않는다.
- AI가 의도적으로 쉬운 일을 골랐다고 단정하지 않는다.

### 4. 생성·주장 판정·후보 수렴의 판단 순서

현재 중심:

- 좋은 기준도 가능한 가치와 결과를 만들기 전에 후보 전체를 닫을 권한을 가지면 AI의 노력을 탈락 이유 정교화에 먼저 쓰게 한다.
- 후보와 가능한 성과·통제력을 먼저 펼치고, 그동안 개별 주장은 엄격히 판정하며, 후보 전체의 선택·보류·종료는 충분히 본 뒤 결정한다.

첫 장면:

- 바로 이 글감 조사에서 main AI가 “먼저 shaping할 세 편”이라는 작업 cursor를 가치 순위로 읽는다.
- 완성 글의 중심 질문 기준은 아직 펼치지 않은 후보의 감점이 되고, 장기 효과를 단정하지 않는 claim ceiling은 후보 매력의 감점이 된다.
- 사용자가 사례가 많다는 것이 좋은 개발기 재료일 수 있고 shaping 전 위상을 닫지 말라고 멈춘다.

중심 실험:

- 다른 제품 조사에서 문제 후보 3개를 먼저 고르지 않고 각 문제에서 solution 3개씩, 총 9개를 만든다.
- 같은 9개를 문제 근거·행동 변화·입력·불확실성으로 다시 본다.
- 결합 방향 3개와 같은 형식의 Markdown 출력 3개를 만들고, 각 출력의 세 상태 snapshot을 정적 대화 목업으로 비교한다.
- 전체 데모에는 9개 snapshot이 있고 작업 기록상 세 출력에 걸쳐 총 여덟 번의 상태 전환을 확인했다.
- 마지막에는 명시적으로 한 후보를 선택했다.

본문 artifact:

1. `필요했던 기준 / 잘못 겨눈 대상 / 생긴 왜곡` 표
2. `3 problems → 9 solutions → 3 outputs → 상태 비교 → 선택` trace
3. 세 출력이 사용자에게 준 수정·확인·다음 행동 차이

고유 narrative engine:

- 지금 쓰는 글에서 같은 실수를 다시 한 재귀적 장면으로 시작해, 과거 실험의 실제 output 차이를 다시 보고 잠정 운영 순서를 얻는 learning-experiment.
- 결말은 방법론 성공담이 아니라 “비교 전에 보이는 차이가 달라졌다”는 제한된 발견으로 연다.

주장 상한:

- A1/A2는 첫 후보판에도 있었고 second pass가 처음 발견한 문제가 아니다.
- second pass는 완전 blind가 아니다.
- output-first나 판단 순서 하나가 최종 제품·글 품질을 높였다고 말하지 않는다.
- `3→9→3→8`을 품질 개선 계보처럼 쓰지 않는다.

### 5. AI self-check

현재 중심:

- AI가 자기 frame 안에서 반복 설명하거나 반대 방향으로 과교정할 때, 답만 다시 쓰지 않고 자신의 문제 정의·전제·입력 범위·도구·판단축을 검사 대상으로 옮긴다.
- “더 근본적으로”는 더 큰 일반론이 아니라 방금 결과를 만든 결정 위치로 돌아가는 일이다.

원천 교정된 주 장면:

- 첫 종합은 회사가 중요하게 보는 방향과 현재 사용자 문제를 함께 보되 증명 범위를 나눴다.
- 첫 별도 점검은 회사 직접 자료의 높은 가중치가 목적에 맞고, 외부 근거는 회사 방향을 사용자 전체 문제로 일반화하지 않게 하는 검증 장치라고 판단한다.
- 작업을 조율한 AI는 이 유효한 판정을 적용하며 `회사 방향을 먼저 확정 → 주변 마찰은 나중에 확인`하는 순차 구조로 과교정한다.
- 사용자가 직전 결론이 아니라 앞선 종합과 더 넓은 대화를 다시 보게 한다.
- 두 번째 점검과 main의 재적용 뒤 회사 자료는 회사 방향을, 사용자·독립 자료는 현재 문제의 해결 상태와 반복 여부를 맡고 두 결과의 접점에서 다음 질문을 고르는 관계가 복구된다.

보강 장면:

- 원본 자료 구역이 보이지 않는다는 관찰을 자료가 없다는 전제로 올린 뒤, 재구성 결과에서 입력 자료의 존재 가능성을 역추적하지 않고 탐색을 닫는다.
- 사용자의 정정과 전체 재검색으로 한 누락과 추가 세 곳의 분류를 고친다.
- 이후 사용자는 두 차례 AI 관점에서 “더 근본적으로” 보라고 요구했다. 중간 AI 답변 전문은 없으므로 정확한 일반론 문장을 재구성하지 않는다.

stress test:

- 실행을 기본으로 둔 작업 지침을 재검토하는 대화에서 사용자는 같은 전진 방향을 세 차례 멈춘다.
- 결과적으로 지침 문구는 바뀌었지만 장기 재발 감소는 확인하지 않았다.
- 문제 설명, 바로 다음 행동, 장기 재발 감소는 서로 다른 결과다.

본문 artifact:

- `함께 보되 증명 범위 분리 → 회사 방향 우선 과교정 → 역할 관계 복구` 세 상태

고유 narrative engine:

- 1인칭 했다체로, 유효한 지적을 적용하고도 반대 방향으로 틀린 자기 판단을 추적하는 retrospective.

- assignment 수정은 formal self-check 단독 효과가 아니다.
- self-check가 행동 안정이나 장기 재발 감소를 만들었다고 말하지 않는다.

## 글간 material 소유권

- AX의 9→15 test와 판별·회수 계약은 독립 판별 글이 소유한다.
- AX 조사 과교정의 “왜 자기 판단을 검사 대상으로 옮겼는가”는 Self-check가 소유한다. reviewer의 입력·권한 설계는 이 글에서 길게 설명하지 않는다.
- AX의 3→9→3 output 비교는 판단 순서 글이 소유한다.
- `current`의 survey 복구는 Current 글이 소유한다. 판단 순서 글에서는 현재 blog cursor 오독만 쓴다.
- Tripproof의 raw 결과 제안과 제품행동 test는 Scope 글이 소유한다. 독립 판별 글에서는 닫힌 입력의 한계를 보여 주는 별도 판정 실험만 짧게 쓴다.

이 소유권은 자료를 다른 글에서 금지하는 규칙이 아니라, 같은 사건을 다섯 글이 같은 무게로 반복하지 않게 하는 편집 경계다.

## Material pass가 확정한 글별 움직임

독립 material partner는 새 중심이나 평가 기준을 만들지 않고, 위 ledger에서 각 글을 움직일 서사 엔진을 다음처럼 확인했다.

- Current: 섞인 상태의 불편 → write 권한 분리 → 전체 지도와 cursor의 동시 작동 → 최근성 편향 stress test → stale current의 비용
- 독립 판별: 초록 checkpoint → 이상 입력 하나 확대 → 판별자가 연 검증 경계 → 같은 기능 재실행 → reviewer 자체의 한계
- Scope: 구현 전 두 경로 → 쉬운 경로에서 사라지는 사용자 행동 → 한 값의 state trace → 제품행동 test → 실제 소비자 계약
- 판단 순서: 현재 글감 조사에서 재귀적 오독 → 과거 제품 조사로 되감기 → 세 output 관찰 → claim strictness 유지 → 현재 오독을 다시 명명
- Self-check: 함께 보던 관계 → 유효한 교정이 관계를 단순화 → 사용자 정정 → 더 넓은 범위에서 관계 복구 → 다른 장면이 같은 판단 습관을 비춤

이 움직임은 다섯 글이 같은 `실패 → 개념 정의 → 운영 질문` 표면으로 다시 수렴하지 않게 하는 shaping 입력으로 사용한다.
