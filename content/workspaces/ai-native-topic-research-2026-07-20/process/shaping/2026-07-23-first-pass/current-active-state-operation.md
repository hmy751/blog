# Current와 history의 권위 분리

이 문서는 current 후보를 실제 글의 단위로 한 번 펼쳐 본 결과다. 첫 글, 제목, article type을 확정하지 않는다.

## 1. 첫 장면

현재 가장 강한 첫 장면은 “current를 읽었는데도 최근 작업 하나가 프로젝트 전체가 된 순간”이다.

AX 제출 설문을 작성한 AI는 current와 context를 읽었다. 그런데 답변은 최근의 Loop 01 구현 실패와 교정에 치우쳤다. 앞에서 수행한 넓은 조사, 독립 문제 추출, 여러 문제와 솔루션의 비교, 사용자의 최종 선택은 뒤로 사라졌다. 사용자가 이 편향을 발견한 뒤에야 current의 전체 지도에서 research·problem·solution 원천으로 다시 내려가 설문을 전면 재작성했다.

이 장면은 두 가지를 함께 보여 준다.

- current가 없어서 생긴 실패가 아니다.
- current는 읽는 것만으로 효력이 생기는 요약문도 아니다.

다른 오프닝 후보인 “기록은 충분했지만 현재 작업을 제어하지 못했다”는 문제를 넓게 설명하기 좋다. 다만 첫 문단의 구체성은 설문 사건이 더 강하다. 넓은 문제는 그 장면 뒤에서 회수한다.

## 2. 중심 질문

중심 질문은 “current를 어떻게 잘 쓰는가”가 아니다.

> 긴 AI 작업에서 전체 프로젝트의 계보와 지금 효력이 있는 단 하나의 판단점을 어떻게 함께 유지할 것인가?

이 질문은 세부적으로 다음을 포함한다.

- 작업 log와 decision을 충분히 남겼는데도 왜 다음 AI는 현재 효력을 다시 추론해야 하는가?
- 현재 실행 contract와 그 contract가 생긴 과거 이유를 왜 다른 문서가 소유해야 하는가?
- current가 있어도 최근 작업에 치우치는 이유는 무엇인가?
- current는 무엇을 직접 담고, 무엇은 권위 있는 원천으로 연결해야 하는가?

글의 중심은 문서 폴더 구조가 아니라 “현재 무엇이 유효한지를 작동시키는 권위 배치”다.

## 3. 판단이 바뀐 시간순 사건

1. 작업 과정과 결정은 계속 기록됐지만, 기록만으로 다음 행동과 현재 효력이 자동으로 정해지지는 않았다.
2. AX의 active Loop 계약이 process history에 놓였다. 현재 구현자가 따라야 할 acceptance·evidence contract와 과거 판단 이유가 같은 갱신 규칙을 갖게 됐다.
3. active contract를 engineering 문서로 옮기고, process는 선택 이유와 실행 이력을 보존하게 했다.
4. 제출 설문 작성 session은 current를 읽고도 최근 Loop 01을 프로젝트 전체처럼 서술했다.
5. 사용자가 편향을 발견한 뒤 current의 전체 지도에서 research·problem·solution 원천으로 다시 내려가 설문을 재작성했다.
6. final current는 package·설문·upload 실패 같은 terminal event 일부를 놓쳤다. current가 있다고 자동으로 최신 상태가 되는 것은 아니었다.
7. Cofathon에서는 current가 상태 보고서처럼 커졌다. 완료 이력을 원천 링크로 접고 전체 지도와 현재 cursor 하나를 남기는 방향으로 다시 줄였다.

이 시간축에서 판단은 “더 많이 기록하기”에서 다음 방향으로 바뀐다.

- 현재 효력과 과거 이유의 소유자를 나눈다.
- current에는 전체 지도와 현재 cursor를 둔다.
- 세부 사실은 복제하지 않고 권위 원천으로 연결한다.
- 현재 판단이 바뀌면 current는 덮어쓰고 history는 보존한다.
- current를 읽었다는 사실과 이번 평가의 시간축을 정확히 잡았다는 사실을 구분한다.

## 4. 독자가 볼 공개 가능한 자료

현재 backlog에는 자료의 위치와 감사 결과가 있지만, 공개 글에 그대로 넣을 자료는 아직 만들지 않았다.

우선 만들 가치가 있는 자료는 다음과 같다.

- **축약한 current 전후 비교**
  - 완료 이력과 세부 상태가 길게 누적된 형태
  - 전체 지도, 현재 cursor, 열린 판단, 원천 링크만 남긴 형태
- **문서 역할 비교**
  - 현재 실행 contract
  - 과거 판단 history
  - 세부 사실을 가진 원천
  - 이번 판단점을 가진 current
- **설문 전후의 작은 재현**
  - 최근 구현 사건만 읽은 답변
  - 프로젝트 단계별 원천으로 내려간 뒤 다시 쓴 답변

공개용 자료는 실제 내부 문장을 복사하지 않고, 같은 실패가 드러나는 작은 가상 프로젝트로 다시 구성한다.

추가 확인이 필요한 사실:

- AX의 reachable commit, current 변경 version, cursor 전환 수가 같은 감사 범위를 가리키는지
- Cofathon의 줄 수·byte 감소가 서로 다른 두 정리 시점임을 본문에서 구분할 수 있는지
- terminal event 누락이 일어난 정확한 current version과 이후 처리

## 5. 사용자의 판단이 바뀐 지점

처음에는 기록을 잘 남기면 다음 AI가 작업을 이어 갈 수 있다고 보기 쉬웠다. 실제 경험에서는 기록이 많아질수록 “무슨 일이 있었는가”는 남았지만 “그래서 지금 무엇이 유효한가”는 다시 추론해야 했다.

current를 운영하며 바뀐 판단은 다음과 같다.

- 기록의 양보다 문서가 어떤 효력을 소유하는지가 중요하다.
- 전체 계보와 현재 판단은 하나를 고르는 관계가 아니다. 전체 지도 안에 현재 cursor 하나를 둬야 한다.
- current가 모든 세부를 직접 품으면 다시 상태 보고서가 된다.
- current는 답 자체보다 필요한 원천으로 내려갈 수 있게 해야 한다.
- current의 존재와 갱신 책임은 별개다. 누가 terminal event를 반영하는지 정하지 않으면 stale해진다.

이 변화가 글쓴이의 실제 운영 감각이다. current 하나가 생산성이나 재진입 성공을 만들었다는 주장으로 바꾸지 않는다.

## 6. 다른 개발자가 가져갈 기준

- 이 문서는 지금 실행할 contract를 소유하는가, 과거 판단 이유를 보존하는가?
- 현재 cursor가 하나인가, 여러 완료·진행 상태가 같은 깊이로 놓여 있는가?
- current의 세부 문장은 직접 진실인가, 권위 있는 원천으로 가는 연결인가?
- 이번 평가 대상은 최근 구현인가, 프로젝트 전체 생애주기인가?
- 방향이 바뀌었을 때 무엇을 덮어쓰고 무엇을 보존하는가?
- terminal event와 외부 상태 변화는 누가 current에 반영하는가?

독자가 복사할 대상은 특정 파일명이 아니라 이 질문들이다.

## 7. 이번 자료가 말하지 못하는 한계

- current 하나가 compaction, 재진입, 생산성 향상을 만들었다는 대조군은 없다.
- 작업 연속성은 current, goal, Git, compaction summary, 사용자 정정이 함께 만든 결과다.
- current를 읽었다고 최근 작업에 치우치는 문제가 자동으로 사라지지 않는다.
- final current가 terminal event 일부를 놓친 사례가 있다.
- 문서 줄 수와 byte 감소는 특정 snapshot을 정리한 결과이지 품질 지표가 아니다.
- 여러 session이나 여러 작성자가 동시에 current를 갱신할 때의 ownership은 아직 열려 있다.
- 공개 가능한 작은 예제를 아직 만들지 않았으므로, 현재 상태에서는 내부 문서 운영기처럼 보일 위험이 남아 있다.
