# 테스트 9개가 모두 초록인데 제품은 아직 틀렸다

여행 상품의 판매 조건을 사용자의 일행과 일정에 대입해 결제 전 판단을 돕는 plugin을 만들고 있었습니다. 첫 세로 slice의 목표는 단순한 상품 요약이 아니었습니다.

사용자가 자연어로 상품과 조건을 말하면 원안의 첫 충돌을 찾고, 사용자가 허용한 수정만 다시 적용하고, 판매자 답변이 충분한 범위를 가질 때 관련 상태만 바꿔야 했습니다. 마지막에는 `추가 확인`, `결제 검토`, `다른 상품 검토`처럼 다음 행동이 달라져야 했습니다.

첫 구현에는 구조화 상태 엔진, fixture, 정적 validator와 자동 test 9개가 있었습니다. test는 모두 통과했습니다. CLI에서도 원안의 충돌, 허용 수정 뒤 남은 부담, 범위가 모호한 판매자 답변의 적용 거부, 충분한 답변 뒤의 상태 갱신이 예상대로 재현됐습니다.

구현자 관점에서는 첫 checkpoint를 닫아도 될 것처럼 보였습니다.

그러나 별도의 read-only 판별자가 같은 결과를 보자 결론은 미통과였습니다. 설치된 환경에서 자연어 요청부터 끝까지 이어지는 E2E가 없었고, 공개된 상품 사실과 fixture가 모순됐습니다. 문자열 `"false"`가 boolean 값처럼 흘렀고, 한 사람에게만 적용돼야 할 claim이 다른 사람의 상태까지 바꿀 수 있었습니다. 같은 범위의 상반된 답변은 배열 순서에 따라 결론이 달라졌습니다.

test가 거짓말을 한 것은 아니었습니다. 9개 test는 제가 만든 fixture와 제가 정의한 계약 안에서 구현이 일관된지를 확인했습니다. 빠진 것은 그 세계가 실제 source와 사용자 흐름에도 맞는지 확인하는 일이었습니다.

이 사건 뒤에 질문이 바뀌었습니다.

> 별도 AI를 한 번 더 부르는 것과, 구현자와 판별자가 같은 전제에서 같은 오류를 반복하지 않게 만드는 것은 무엇이 다른가?

## 초록 test가 확인한 세계

첫 구현의 test는 쓸모가 있었습니다. 구조화 입력이 같으면 같은 상태가 나오는지, 사용자가 허용하지 않은 수정이 적용되지 않는지, 판매자 답변이 어느 조건을 바꾸는지 확인했습니다. 여러 turn을 거쳐도 원안과 수정안이 섞이지 않는 상태 엔진의 기본 계약을 고정했습니다.

문제는 test가 보지 않은 범위를 통과 결과에 포함해 읽었다는 데 있었습니다.

대표 fixture에서는 미성년자 티켓 절차를 아직 확인하지 않은 항목으로 두고 판매자에게 다시 묻게 했습니다. 하지만 당시 공개된 상품 정보에는 이미 별도 구매와 사전 메시지 절차가 나와 있었습니다. 엔진은 fixture를 정확히 실행했지만, fixture가 source와 충돌했습니다.

타입과 범위에서도 같은 일이 있었습니다.

- boolean 자리에 문자열이 들어왔을 때 거부하지 않았습니다.
- 한 참여자에게 적용된 claim이 같은 분류의 다른 참여자에게 번질 수 있었습니다.
- 같은 범위의 상반 claim 두 개를 함께 받아 마지막 값으로 결론을 냈습니다.
- 이전 상태를 가리키는 revision이 자기 자신을 기준으로 삼아도 통과했습니다.

happy path와 예상한 예외를 test한 것만으로는 이런 결함이 드러나지 않았습니다. fixture, 구현, 기대 결과가 같은 문제 정의에서 만들어졌기 때문입니다. 셋이 서로 일치한다는 사실은 확인했지만, 그 문제 정의 바깥의 계약은 확인하지 못했습니다.

또 하나의 공백은 실제 실행면이었습니다. CLI에 구조화 JSON을 주면 상태 전이가 재현됐지만, 사용자는 JSON을 작성하지 않습니다. 설치된 plugin을 처음 만난 사용자가 자연어로 상품과 조건을 말하고, live source를 가져오고, 상태를 만들고, 같은 대화에서 수정과 답변을 이어 가는 경로는 아직 실행하지 않았습니다.

“엔진이 동작한다”와 “제품 흐름이 동작한다”를 같은 완료로 읽은 셈이었습니다.

## 판별 입력을 구현자의 설명에서 분리했습니다

별도 판별자에게는 기존 대화와 구현자의 완료 설명을 주지 않았습니다. 현재 목표와 계약, 실제 산출물을 원천으로 주고 test, CLI, validator, 공개 source를 직접 확인하게 했습니다. 수정 권한은 주지 않았고 통과 여부와 결함 범위만 판정하게 했습니다.

이 차이가 중요했습니다. 구현자의 설명에는 이미 무엇을 만들었고 왜 통과했다고 보는지가 들어 있습니다. 다른 AI가 그 설명을 그대로 받으면, 결과물을 새로 판별하기보다 설명의 정합성을 검토하기 쉽습니다.

판별자는 실제 source와 계약을 직접 대조하면서 구현자의 질문 자체를 바꿨습니다. “상태 엔진이 예상한 흐름을 재현하는가”만이 아니라 “fixture가 공개 사실과 맞는가”, “실제 사용자가 들어오는 실행 경로가 존재하는가”, “적대적인 입력에서도 계약이 보존되는가”를 물었습니다.

이후 검증을 한 묶음으로 보지 않게 됐습니다.

```text
fixture consistency
  구현이 설계한 예시를 일관되게 처리하는가

source-to-contract
  예시와 상태 계약이 실제 source와 모순되지 않는가

adversarial schema
  잘못된 타입·범위·순서·lineage를 거부하는가

installed natural-language E2E
  사용자의 실제 입력 형태로 전체 흐름이 이어지는가
```

각 단계는 다른 실패를 봅니다. 하나가 초록이라고 다음 단계까지 통과한 것은 아닙니다.

## 같은 checkpoint를 다시 닫았습니다

교정에서는 기능을 더 붙이지 않았습니다. 첫 세로 slice가 이미 약속한 경로를 실제 source와 실행 환경에서 닫는 데 집중했습니다.

먼저 공개 정보에서 이미 확인된 티켓 절차를 미확정 질문에서 제외했습니다. 이 항목은 `정상`이지만 별도 준비 부담이 있는 상태로 남기고, 판매자에게 물을 변수는 공개 정보로 닫히지 않은 시작 시각 하나로 줄였습니다.

구조화 계약도 바꿨습니다. 문자열 boolean, boolean과 섞인 정수, 잘못된 날짜·시각, 중복 참여자를 계약 오류로 거부했습니다. 한 사람에게 적용되는 claim의 범위를 제한했고, 같은 범위의 중복·상반 claim은 배열 순서와 관계없이 실패하게 했습니다. revision이 가리킬 수 있는 기준도 좁혔습니다.

마지막으로 plugin을 실제 설치한 새 작업에서 아래 흐름을 자연어로 실행했습니다.

```text
사용자 요청
→ 현재 상품 정보 조회
→ 원안 구조화와 첫 충돌 판정
→ 사용자가 허용한 수정 적용
→ 범위가 모호한 답변 적용 거부
→ 범위가 충분한 답변의 관련 상태만 갱신
→ 다음 행동 변경
```

교정 뒤 자동 test는 15개가 됐습니다. 9개에서 15개로 늘어난 것은 같은 세로 slice checkpoint에서 검증 범위가 달라진 사실입니다. 이 숫자를 프로젝트 전체 품질이나 사용자 가치가 여섯 칸 좋아졌다는 지표로 읽을 수는 없습니다. test 수보다 중요한 변화는 source 대조, 적대 입력, 설치형 자연어 E2E가 서로 다른 확인 단계가 됐다는 점입니다.

이전 구현 대화를 받지 않은 짧은 회귀 판별은 이 교정 범위에서 통과했습니다. 다만 판별자는 완전히 외부의 제3자가 제출물 하나만 받아 재현한 것이 아니었습니다. 설치 상태와 실제 E2E artifact도 입력으로 받았습니다. 따라서 이 결과 역시 주어진 판별 범위 안의 checkpoint입니다.

## 판별자를 하나 더 붙여도 입력이 틀리면 실패합니다

이 경험만 보면 구현자와 reviewer를 나누면 문제가 해결되는 것처럼 보일 수 있습니다. 다른 답변 시스템에서 진행한 실험은 그 결론을 막았습니다.

그 시스템에서는 하나의 LLM이 답변 값과 근거를 만들면서 자신의 상태까지 `supported`라고 선언하고 있었습니다. 생성과 검증이 같은 호출에 있었기 때문에, 틀린 답이 근거 문구의 존재만 확인하고 최종 상태로 올라갈 수 있었습니다.

이를 고치기 위해 생성기와 entailment 판별 호출을 분리했습니다. 생성기는 값과 근거를 고르고, 판별자는 그 값과 인용한 source unit만 받아 무조건 성립, 조건부, 불성립을 판단하게 했습니다. 코드가 그 역할과 grounding을 읽어 최종 상태를 정했습니다.

구조상으로는 독립 판별자가 생겼습니다. 하지만 반복 A/B에서 목표한 acceptance는 성립하지 않았습니다. 원래 문제 문항은 안전한 상태로 내려갔지만, 다른 표현에서는 조건 문장이 값처럼 잘못 추출돼 다시 `supported`로 나갔습니다. 깨끗하게 통과해야 할 값이 과도하게 내려간 경우도 있었습니다.

판별자는 받은 입력 안에서는 일관되게 동작했습니다. 문제는 판별 전에 생겼습니다. 추출기가 값을 찾지 못하거나 조건과 값을 뒤바꾸거나 표기를 바꿨고, 닫힌 입력만 받는 판별자는 그 바깥에서 빠진 맥락을 복구할 수 없었습니다.

이 반례에서 독립성은 모델을 두 개로 나누는 것보다 입력 경계를 포함한다는 점이 선명해졌습니다.

- 판별자는 구현자와 다른 원천을 볼 수 있는가?
- 앞 단계가 고른 후보만 받는다면 무엇이 입력 전에 사라지는가?
- raw source와 외부 contract에 직접 접근할 수 있는가?
- 구현자가 붙인 원인 가설을 판별자가 기각할 수 있는가?
- 판별 결과 자체도 A/B, 반례, revert의 대상인가?

다른 모델을 쓴다는 사실도, 별도 호출이라는 구조도 독립성을 자동으로 만들지 않았습니다. 같은 오염된 입력과 같은 문제 정의를 받으면 오류 상관은 그대로 남습니다.

## 판정, 수정, 완료 선언을 한 주체에 모으지 않습니다

판별 결과를 새 정답으로 올리지 않는 것도 중요했습니다.

reviewer가 직접 코드를 수정하면 어떤 지적을 했고 어떤 선택을 적용했는지 섞이기 쉽습니다. 수정한 뒤 스스로 완료까지 선언하면 구현자와 같은 자기인증 구조로 돌아갑니다. 그래서 판별은 가능한 한 read-only 상태로 두고, 수정과 완료 판단을 분리했습니다.

출력도 곧바로 작업을 조율하는 AI의 기존 언어로 합치지 않는 편이 낫습니다. 조율자는 이미 문제 이름, 구현 과정, 이전 정정의 영향을 받은 상태입니다. 서로 다른 판별 결과를 즉시 하나의 요약으로 만들면 일치하지 않는 부분이나 새로 드러난 문제가 사라질 수 있습니다.

제가 사용하게 된 회수 순서는 다음과 같습니다.

1. 판별자가 원자료에서 본 결과를 별도의 판단 상태로 남깁니다.
2. 사용자가 기존 판단과의 일치, 충돌, 새 발견을 먼저 봅니다.
3. 조율자는 사용자 의도, 현재 계약, 실제 artifact를 기준으로 각 항목을 채택·수정·기각합니다.
4. 구현 뒤에는 판별자의 설명이 아니라 다시 실행한 결과로 checkpoint를 닫습니다.

회수 권한은 reviewer를 무시할 권한이 아닙니다. 판별 결과가 어떤 원천과 계약으로 기각되거나 적용됐는지 남기는 책임에 가깝습니다.

## 제3판별자는 세 번째 AI가 아닙니다

이후에는 reviewer를 몇 명 붙일지보다 판별 계약을 먼저 봅니다.

- 구현자와 다른 무엇을 입력으로 받는가?
- fixture의 일관성과 실제 source의 계약을 따로 보는가?
- 실제 사용자의 입력 형태로 실행할 수 있는가?
- 질문과 평가 범위를 스스로 다시 잡을 수 있는가?
- write 권한과 완료 선언 권한이 분리돼 있는가?
- 서로 다른 결과의 충돌이 취합 전에 보이는가?
- 조율자는 어떤 최소 증거로 결과를 채택하거나 기각하는가?
- reviewer 자체도 다시 평가하고 되돌릴 수 있는가?

이 구조가 reviewer 수가 늘수록 품질이 오른다는 것을 증명하지는 않습니다. 앞선 맥락을 주지 않았거나 기존 결과를 가렸다는 사실만으로 독립성이 생기는 것도 아니고, 같은 모델이면 비독립이고 다른 모델이면 독립이라는 규칙도 성립하지 않습니다.

첫 사건에서 9개 test가 모두 초록이었던 이유는 test가 무용해서가 아니었습니다. 구현자, fixture, validator가 같은 세계를 보고 있었기 때문입니다. 독립 판별이 한 일은 정답을 대신 내리는 것이 아니라 그 세계의 경계를 바꾸는 일이었습니다.

AI와 함께 같은 입력과 가정 위에서 빠르게 구현할수록 오류도 같은 방향으로 반복될 수 있습니다. 이때 제가 필요로 한 제3판별자는 세 번째 AI가 아니라, 다른 입력을 보고 다른 질문을 할 수 있으며 자신의 판정까지 다시 검증받는 별도의 판단 상태였습니다.
