# 테스트 9개가 모두 초록인데 제품은 아직 틀렸다

여행 상품의 판매 조건을 사용자의 일행과 일정에 대입해 결제 전 판단을 돕는 plugin을 만들고 있었습니다. 사용자가 자연어로 상품과 조건을 말하면 원안의 첫 충돌을 찾고, 사용자가 허용한 수정만 적용하고, 판매자 답변의 범위가 충분할 때 관련 상태만 바꾸는 제품이었습니다. 마지막에는 `추가 확인`, `결제 검토`, `다른 상품 검토`처럼 다음 행동이 달라져야 했습니다.

첫 checkpoint에서 Python `unittest` runner는 test method 9개를 실행했고 모두 통과했습니다. 여기서 9는 test method의 수이자 그 runner가 실행한 test의 수입니다. plugin·skill 구조 검증기와 미리 만든 입력·기대 결과를 사용한 CLI fixture demo도 통과했지만 이들은 9개에 포함되지 않는 별도 검증이었습니다.

CLI에서는 원안의 충돌, 허용 수정 뒤 남은 부담, 범위가 부족한 판매자 답변의 적용 거부, 충분한 답변 뒤의 상태 갱신이 예상대로 재현됐습니다. 구현자 관점에서는 첫 checkpoint를 닫아도 될 것처럼 보였습니다.

그러나 별도의 read-only 판별자가 같은 산출물을 보고 내린 결론은 미통과였습니다. 당시 plugin은 설치 목록에 없었고, 설치된 새 작업에서 자연어 요청부터 끝까지 실행했다는 증거도 없었습니다. 공개된 상품 사실과 fixture는 한 지점에서 모순됐고, 문자열 `"false"`가 boolean 값처럼 흘렀습니다. 한 참여자에게만 적용돼야 할 판매자 답변 claim이 다른 참여자의 상태까지 바꿀 수 있었고, 같은 범위의 상반된 claim은 배열 순서에 따라 결론을 뒤집었습니다.

test가 거짓말을 한 것은 아니었습니다. 9개 test는 제가 만든 fixture와 제가 정의한 계약 안에서 구현이 일관된지를 확인했습니다. 빠진 것은 그 세계가 실제 source와 사용자의 입력 형태에도 맞는지 확인하는 일이었습니다.

## 9개 test가 보지 않은 범위

첫 구현의 test는 쓸모가 있었습니다. 구조화 입력이 같으면 같은 상태가 나오는지, 허용하지 않은 수정이 적용되지 않는지, 모호한 답변이 상태를 바꾸지 않는지, 같은 답변을 반복해도 결과가 달라지지 않는지를 고정했습니다.

문제는 test가 보지 않은 범위까지 초록으로 읽은 데 있었습니다.

대표 fixture는 미성년자 티켓 절차를 아직 확인하지 않은 변수로 두고 판매자에게 다시 물었습니다. 하지만 당시 공개 source에는 별도 구매와 사전 메시지 절차가 이미 나와 있었습니다. 엔진은 fixture를 정확히 실행했지만, fixture의 질문이 실제 source와 충돌했습니다.

실제 실행면도 숫자 밖에 있었습니다. 구조화 JSON을 CLI에 주면 상태 전이는 재현됐지만 사용자는 JSON을 작성하지 않습니다. 설치된 plugin을 처음 만난 사용자가 자연어로 상품과 조건을 말하고, 현재 상품 정보를 가져오고, 수정과 판매자 답변을 같은 대화에서 이어 가는 경로는 실행되지 않았습니다.

첫 checkpoint와 교정 뒤의 차이를 검증 역할별로 다시 놓으면 다음과 같습니다.

| 검증 역할 | 첫 checkpoint | 교정 뒤 | 9·15에 포함되는가 |
| --- | --- | --- | --- |
| Python `unittest` | test method 9개가 fixture 상태 전이·허용 수정·결정성을 확인 | test method 15개가 엄격한 타입, 중복 참여자, claim 충돌, 수정안의 원안 참조 관계까지 확인 | 포함 |
| plugin·skill validator와 CLI | 별도로 통과 | 별도로 다시 통과 | 포함되지 않음 |
| public source와 계약 대조 | 판별자가 티켓 질문의 모순을 발견 | 공개 source로 닫힌 티켓 절차를 계약에 반영 | 포함되지 않음 |
| 설치형 자연어 E2E | plugin이 설치 목록에 없었고 전체 흐름 증거도 없음 | 설치된 새 작업에서 자연어 입력부터 다음 행동 변경까지 실행 | 포함되지 않음 |

9에서 15로 바뀐 숫자는 한 checkpoint의 test method 구성이 달라졌다는 뜻입니다. 제품 품질이나 사용자 가치가 여섯 칸 좋아졌다는 지표가 아닙니다.

## 판별자에게 구현자의 결론을 주지 않았습니다

첫 판별자는 아무 맥락도 없는 외부 제3자가 아니었습니다. 현재 목표와 상위 계약, 실제 산출물에 접근했고 test, CLI, validator, 공개 source를 직접 확인했습니다. 다만 이전 구현 대화와 구현자의 완료 설명은 받지 않았습니다. 수정 권한도 없이 통과 여부와 결함 범위만 판정했습니다.

이 입력 차이가 질문을 바꿨습니다. 구현자의 설명을 이어받았다면 “상태 엔진이 예상한 흐름을 재현하는가”를 중심으로 보기 쉬웠습니다. 판별자는 실제 source와 실행 환경에서 “fixture가 공개 사실과 맞는가”, “사용자의 입력 형태로 들어오는 경로가 존재하는가”, “예상하지 않은 타입과 범위에서도 계약이 보존되는가”를 다시 물었습니다.

결과적으로 같은 `검증`이라는 말 아래 있던 일이 네 가지로 갈라졌습니다. fixture 내부 일관성, source와 계약의 대조, 의도적으로 잘못 만든 입력 구조, 설치된 환경에서 처음부터 끝까지 잇는 자연어 E2E는 서로 다른 실패를 봤습니다. 하나가 초록이라고 다음 단계까지 통과한 것은 아니었습니다.

## 같은 checkpoint를 다시 닫았습니다

교정에서는 기능을 넓히지 않고 첫 세로 slice가 약속한 경로를 닫았습니다.

먼저 공개 source로 이미 확인된 티켓 절차를 판매자 claim에서 제거했습니다. 티켓은 `정상`이지만 별도 구매와 사전 메시지가 필요한 준비 부담으로 남겼습니다. 판매자에게 물을 변수는 공개 정보로 닫히지 않은 시작 시각 하나로 줄였습니다.

판매자 답변의 범위도 좁게 적용했습니다. 대상 범위를 밝히지 않은 짧은 긍정 답변은 어느 상품, 어느 날짜, 어느 참여 구성, 어느 시각에 대한 것인지 부족해 상태를 바꾸지 않았습니다. 상품·날짜·두 참여자·요청 시각을 모두 포함한 전체 plan scope의 답변만 받아들였고, 그때도 시각 상태만 갱신했습니다. 원안의 충돌, 기본 투어비, 티켓 준비 부담은 그대로 보존했습니다.

구조화 계약에서는 문자열 boolean, boolean 자리에 들어온 정수, 정수 자리에 들어온 boolean, 잘못된 날짜·시각, 중복 참여자를 오류로 거부했습니다. 같은 범위의 중복·상반 claim은 순서와 관계없이 실패하게 했고, 수정안이 원안을 직접 가리키도록 제한했습니다. 선택지를 모두 소진했다는 상태에는 사용자 근거가 있어야 했습니다.

그 뒤 설치된 plugin을 새 작업에서 실제로 실행했습니다. 자연어 요청으로 현재 상품 정보를 가져와 원안의 첫 충돌을 찾고, 사용자가 허용한 참여 구성만 적용하고, 범위가 부족한 답변은 거부하고, 전체 plan scope가 있는 답변은 시각에만 반영했습니다. 마지막 행동은 `추가 확인`에서 `결제 검토`로 바뀌었습니다.

교정 뒤 같은 runner가 실행한 `unittest` test method는 15개였습니다. 별도로 validator와 CLI를 다시 실행했고, 설치형 자연어 E2E도 따로 확인했습니다. 짧은 회귀 판별은 설치 여부, 자연어 E2E, 최종 상태의 정확성, 공개 설명이 현재 동작과 맞는지를 확인했습니다.

회귀 판별은 통과했지만 그 의미에도 상한이 있습니다. 판별자는 코드 산출물뿐 아니라 설치 상태와 실제 E2E 실행 기록을 입력으로 받았습니다. 제출물 하나만 받아 설치부터 독립 재현한 검사는 아니었습니다. 따라서 통과는 주어진 증거와 회귀 범위 안에서 이 checkpoint를 다시 닫았다는 뜻입니다.

## 별도 판별 호출도 앞단에서 사라진 정보를 복구하지 못했습니다

이 사건만 보면 생성기와 판별자를 분리하면 문제가 해결된다고 결론 내리기 쉽습니다. 다른 답변 시스템에서 실행한 entailment A/B가 그 결론의 경계를 보여 줬습니다.

그 시스템은 처음에 하나의 LLM 호출이 답변 값과 근거를 고르면서 자신의 상태까지 `supported`라고 선언했습니다. 이를 값·근거를 추출하는 호출과, 그 값이 인용 source로 무조건 성립하는지·조건부인지·성립하지 않는지를 판정하는 호출로 분리했습니다. 코드는 판정 역할과 추출한 값이 원문에 실제로 있는지 확인하는 grounding을 읽어 최종 상태를 정했고, 사용자 응답의 필드 구조는 유지했습니다.

같은 조건에서 판정만 켜고 끈 세 번의 반복 A/B에는 네 가지 결과가 함께 나왔습니다.

원래 문제였던 특별 요청 질문은 판정 ON에서 세 번 모두 `needs_review`로 내려갔습니다. 그러나 의도한 조건부 판정이 아니었습니다. 추출기가 값을 찾지 못해 `value`가 비었고, 판별자의 `not_established` 안전망이 받은 결과였습니다.

첫 번째로 표현을 바꾼 질문에서는 retrieval candidate에 값과 조건 근거가 들어오지 않았습니다. 추출기가 빈손으로 끝나 판별 호출 자체가 실행되지 않았고 세 번 모두 `missing`으로 남았습니다. 두 번째로 표현을 바꾼 질문에서는 반대 문제가 생겼습니다. 추출기가 숙소 상황에 따라 반영 여부가 달라진다는 조건 문장 자체를 값으로 골랐고, 판별자는 전달받은 그 문장을 무조건 성립하는 값으로 판정했습니다. 결과는 세 번 모두 잘못된 `supported`였습니다.

깨끗하게 `supported`여야 한다고 기대한 대조 문항의 하락도 하나의 과잉강등으로 묶을 수 없었습니다. 예약 확정서 항목은 추출 과정에서 원문 괄호 주변 표기가 바뀌어 value grounding이 실패한 회귀였습니다. 반면 신분증과 결제 카드 항목에는 실제로 적용 조건이 있었고, 판별 결과와 데이터셋의 top-level 기대가 충돌했습니다.

분리된 판정 호출과 사용자 응답 구조의 보존은 확인됐습니다. 하지만 조건부 질문이 `needs_review`로 안정적으로 남고 기존 `supported` 문항은 무너지지 않아야 한다는 목표 acceptance는 성립하지 않았습니다. 세 번의 반복은 상태가 같은 조건에서 안정적인지 보기 위한 실행 조건이지 품질 점수가 아닙니다.

이 A/B에서 별도 호출은 판별 전에 사라지거나 뒤바뀐 정보를 복구하지 못했습니다. 값이 추출되지 않았거나, 조건이 값으로 바뀌었거나, retrieval에서 후보가 빠졌다면 닫힌 입력을 받는 판별자가 그 바깥의 맥락을 다시 열 수 없었습니다. 판별자를 분리했다는 구조만으로는 입력 경계까지 독립적이 되지 않았습니다.

## 판정과 완료 선언을 한곳에 모으지 않습니다

두 사건 뒤에는 판별자를 보편적인 정답 기계로 올리는 대신 운영 경계를 짧게 정했습니다.

판별자는 가능한 한 read-only로 두고, 그 결과를 구현자의 기존 설명과 바로 합치지 않습니다. 사용자가 기존 판단과의 충돌과 새 발견을 먼저 볼 수 있게 남기고, 무엇을 채택하거나 기각할지는 현재 계약과 원자료로 다시 판단합니다. 수정 뒤 checkpoint는 판별자의 문장이 아니라 다시 실행한 test와 실제 흐름으로 닫습니다.

이 방식이 reviewer를 늘리면 품질이 오른다는 것을 증명하지는 않습니다. 앞선 맥락을 숨겼다는 사실만으로 독립성이 생기는 것도 아니고, 같은 모델이면 비독립이고 다른 모델이면 독립이라는 규칙도 성립하지 않습니다. 회귀 판별처럼 입력으로 이미 갖춰진 실행 증거를 받은 검사는 그 증거의 범위 안에서 읽어야 합니다.

첫 사건에서 test method 9개가 모두 초록이었던 이유는 test가 무용해서가 아니었습니다. 구현, fixture, 기대 결과가 같은 세계를 보고 있었기 때문입니다. 판별자가 한 일은 정답을 대신 내리는 것이 아니라 source, 입력 형태, 적대 조건을 보도록 그 세계의 경계를 바꾸는 일이었습니다.

제가 필요로 한 제3판별자는 세 번째 AI가 아니었습니다. 구현자와 다른 입력을 보고 다른 질문을 할 수 있고, 자신의 판정까지 다시 검증받는 별도의 판단 상태였습니다.
