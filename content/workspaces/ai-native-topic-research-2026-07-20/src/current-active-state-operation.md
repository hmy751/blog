# 긴 AI 작업에서 전체 지도와 현재 위치를 함께 둔 이유

여행 상품의 조건을 실제 일행과 일정에 대입해, 결제 전에 충돌과 확인할 내용을 점검하는 plugin을 만들고 있었습니다. 프로젝트를 외부에 제출하면서는 이 제품의 사용자와 문제, 문제를 고른 이유, 작동 방식, AI와 사람의 역할, 검증 결과를 다섯 문항으로 설명해야 했습니다.

AI는 답변을 쓰기 전에 프로젝트의 전체 지도와 현재 위치를 적어 둔 `current`를 읽었습니다. 그런데 프로젝트 전체에서 AI와 사람이 어떤 역할을 맡았는지 묻는 답변이 직전에 끝낸 구현과 검증에 과도하게 끌렸습니다. 최근 test에서 무엇이 실패했고 어떻게 교정했는지는 맞았습니다. 그 사실이 앞선 조사와 문제 정의, 여러 해결안의 출력 비교, 제품 방향을 고른 판단까지 밀어내고 프로젝트 전체의 설명이 된 것이 문제였습니다.

저는 답변 몇 문장을 보강하지 않고, 최근 구현이 프로젝트 전체를 대신하고 있다고 지적한 뒤 `current`의 상위 지도에서 다시 시작하게 했습니다. AI는 Q1~Q5의 역할과 시간축을 다시 나누고 다섯 답변을 전면 재작성했습니다. 최근 구현의 사실은 최신 구현을 묻는 문항에 남기고, 프로젝트 전체를 묻는 문항은 상위 지도에서 다시 시작했습니다.

이 장면은 `current`의 한계이면서도 제가 이를 세션 사이의 sync를 돕는 scaffolding으로 계속 쓰는 이유를 함께 보여 줬습니다. `current`가 어긋남을 발견하거나 판단을 대신하지는 않았습니다. 다만 최근 사건에서 프로젝트 전체로 시선을 되돌려야 할 때, 전체 지도와 단 하나의 현재 위치가 다시 내려갈 원천을 찾는 복구 지점이 됐습니다.

## 최근 구현이 프로젝트 전체가 된 순간

다섯 문항은 모두 같은 시간축을 묻지 않았습니다.

- 사용자와 문제, 문제를 선택한 이유, AI와 사람이 한 일을 설명하려면 조사부터 제품 선택까지의 흐름을 봐야 했습니다.
- 실제 입력과 결과, 예외, 남은 한계를 설명하려면 가장 최근 구현과 검증을 깊게 봐야 했습니다.

첫 답변 묶음은 이 차이를 충분히 나누지 못했습니다. 가장 선명했던 구현 교정이 다른 문항까지 끌어당겼습니다. 프로젝트 전체에서 AI와 사람이 한 일을 묻는 네 번째 답변의 중심은 다음처럼 달라졌습니다. 실제 문장을 복원한 것이 아니라, 답변을 구성한 근거의 범위를 비교한 것입니다.

```text
첫 Q4의 중심
└─ 직전 구현의 타입·범위 결함과 fresh 검증 미통과·교정

재작성한 Q4의 중심
├─ AI: 자료 추출과 반대 근거 탐색, 독립 문제 추출, 해결안 출력 비교, code·test
└─ 사람: 조사 질문과 증명 범위, 최종 사용자와 문제 크기, 해결안 선택, 단계 종료 판단
```

문장 몇 개를 더하는 대신 AI는 다섯 문항이 각각 어느 시간축을 요구하는지 먼저 배정했습니다.

| 문항 | 필요한 시간축 | 재작성 때 내려간 자료 |
| --- | --- | --- |
| Q1. 누가 어떤 상황에서 쓰는가 | 최종 문제와 제품이 만드는 행동 변화 | 선택한 사용자 문제와 제품 방향 |
| Q2. 왜 이 문제를 골랐는가 | 조사부터 문제 선택까지 | 회사 방향, 상품 화면, 사용자 행동, 반대 사례 |
| Q3. 제품은 어떻게 작동하는가 | 현재 제품 계약 | 현행 입력·상태 변화·정보 부족 처리 |
| Q4. AI와 사람은 무엇을 했는가 | 프로젝트 전체 생애주기 | 조사, 독립 문제 추출, 출력 비교, 사람이 한 판단과 기각 |
| Q5. 무엇을 어떻게 검증했는가 | 가장 최근 구현 | 실제 입력, 상태 전이, 적대 test, 설치 환경 실행, 남은 한계 |

최근 구현에 과도하게 끌렸다고 지적하고 전체 지도로 돌아가게 한 것은 저였습니다. Q1~Q5의 역할과 시간축을 구체적으로 다시 나누고 다섯 답변을 전면 재작성한 것은 AI였습니다. 재작성 도중 병렬 작업에서 설치형 실행 검증이 끝나자 AI는 최신 실행 기록을 다시 대조해 검증 답변도 갱신했습니다. 이 회수에는 사용자 정정과 AI의 재작성, `current`의 지도, 과정 기록과 직접 원천이 함께 작동했고, `current`가 맡은 범위는 전체 계보로 돌아갈 경로였습니다.

## 전체 지도와 단일 cursor

이 프로젝트의 `current`는 직전 작업을 요약한 메모가 아니었습니다. 프로젝트 전체를 낮은 해상도로 펼치고, 그 안에서 지금 판단할 단 하나의 위치를 `cursor`로 표시한 문서였습니다. 공개 가능한 수준으로 골격만 줄이면 다음과 같습니다.

```text
전체 지도
├─ 요구사항
├─ 조사와 문제 정의
├─ 해결안 출력 비교
├─ 구현과 검증  ← 현재 cursor
└─ 제출
```

큰 가지에는 현재 판단을 요약하고, 더 자세한 판단과 사실은 그 역할을 소유한 원천으로 연결했습니다. 완료된 과정도 전체 그림을 이해하는 데 필요한 만큼 접어 남겼고, 진행 중인 가지에서 다음 행동과 열린 판단을 더 깊게 적었습니다.

`current`는 프로젝트가 끝난 뒤 만든 설명문도 아니었습니다. 첫 독립 검증이 통과하지 못했을 때는 cursor가 그 실패와 교정 지점을 가리켰고, 교정과 재검증이 끝난 뒤에는 같은 지도에서 통과 상태와 다음 판단을 가리키도록 덮어썼습니다.

현재 위치만 남기면 최근 작업에는 빠르게 들어갈 수 있지만, 그 일이 프로젝트 전체에서 어떤 의미인지 잃기 쉽습니다. 반대로 조사부터 구현까지의 세부를 모두 펼치면 매번 긴 보고서를 다시 읽어야 합니다. 전체 지도와 단일 cursor를 함께 둔 이유는 두 해상도 사이를 오가기 위해서였습니다.

질문의 범위가 바뀌면 지도에서 출발하는 높이와 내려갈 원천도 달라졌습니다. 이 구조에서 `current`는 답을 저장하는 문서보다 필요한 해상도와 원천을 고르는 router에 가까웠습니다.

## 지도와 원천을 나누는 네 가지 갱신 규칙

지도가 원천으로 연결돼도, 연결된 문서가 모두 같은 권위를 가지면 다음 AI는 다시 현재 상태를 추론해야 합니다. 실제로 한 구현 loop의 목표와 완료 조건을 처음에는 그 loop를 선택한 이유, 기각한 대안, 실행 결과와 같은 과정 기록에 두었습니다.

과정 기록은 당시 판단을 보존해야 합니다. 반면 지금 구현자가 따라야 하는 목표와 완료 조건은 방향이 바뀌면 현행판으로 덮어써야 합니다. 그래서 현재 goal·acceptance·evidence는 별도의 실행 계약으로 옮기고, 과정 기록에는 왜 그렇게 정했는지와 그때의 결과를 남겼습니다.

판매자에게 확인할 질문을 교정한 사건에서 이 차이가 구체적으로 드러났습니다. 첫 계약은 희망 시작 시각과 아동 티켓 절차, 두 가지를 판매자에게 묻도록 했습니다. 공개 상품 자료를 다시 대조하니 티켓 절차는 이미 명시돼 있었습니다. 그것은 미확정 질문이 아니라 확인된 준비 부담으로 남아야 했습니다. 현행 계약의 판매자 질문은 실제로 닫히지 않은 시작 시각 하나로 줄었고, 충분한 답변이 들어와도 시간 상태만 바꾸도록 교정됐습니다.

같은 사건을 네 상태가 나눠 소유했습니다.

| 상태 | 이 사건에서 소유한 것 | 갱신 방식 |
| --- | --- | --- |
| history | 처음 두 질문을 잡은 이유와 교정 과정 | 당시 판단을 보존하고 뒤에 결과를 더한다 |
| active contract | 현재 확인할 변수는 시작 시각 하나라는 완료 조건 | 방향이 바뀌면 현행판을 덮어쓴다 |
| source | 티켓 절차가 공개 자료에 이미 명시돼 있다는 사실 | 사실을 가진 원천에서 직접 확인한다 |
| current | 구현 교정이 전체 지도에서 어디에 있고 어느 원천으로 내려갈지 | 지도와 cursor가 바뀔 때 갱신한다 |

이 분리는 제가 `current`를 사용할 때 둔 설계 경계였습니다. `current`는 세부 사실과 계약 전문을 모두 직접 소유하기보다, 전체 그림과 현재 위치에서 해당 원천으로 연결했습니다. 작은 작업이라면 네 파일을 만들 필요는 없습니다. 한 문서 안에서도 보존할 기록, 덮어쓸 계약, 사실의 원천, 현재 위치가 서로 다른 갱신 규칙을 갖게 하면 됩니다.

## 마지막 상태는 저절로 들어오지 않았다

덮어쓰는 현재 상태에는 운영 비용이 있었습니다. 누군가 마지막 변화를 반영해야 합니다.

구현 교정과 설치 환경의 검증 통과까지는 `current`에 들어갔습니다. 그 뒤 다섯 제출 답변을 일단 완성하고, 제출 파일을 실제로 만들고 풀어 구조와 test를 확인했습니다. 이 완료 상태에 맞춰 검증 답변도 다시 교정했습니다. 마감 직전에는 웹 업로드가 실패해 오류 화면과 검증된 파일을 근거로 후속 대응도 준비했습니다.

이 마지막 사건들은 과정 기록과 산출물에는 남았지만 `current`에는 반영되지 않았습니다. 다음 세션이 `current`만 읽었다면 구현 gate를 통과한 지점과 다음 선택까지는 볼 수 있어도, 제출 준비와 외부 업로드의 실제 마지막 상태는 다른 기록에서 다시 추론해야 했습니다.

누락의 원인을 하나로 단정할 수는 없습니다. 병렬 작업이 이어졌고, 업로드 실패는 저장소 밖에서 일어났습니다. 확인할 수 있는 것은 `current`가 앞선 작업에서 유용하게 쓰였어도 스스로 최신이 되지는 않았다는 사실입니다.

그래서 읽을 원천을 나누는 일 다음에는 쓰기 책임을 정해야 했습니다.

- 병렬 작업이 끝난 뒤 누가 전체 cursor를 다시 맞추는가.
- 제출이나 배포처럼 저장소 밖에서 생긴 사건은 누가 반영하는가.
- 작업 종료 조건에 `current`의 마지막 갱신도 포함하는가.

이 책임이 비어 있으면 덮어쓰는 상태의 입구부터 다시 과거가 됩니다.

## 재진입할 때 먼저 맞추는 두 질문

이 사례는 작업 속도나 생산성이 높아졌다는 비교 결과를 말하지 못합니다. 확인할 수 있는 것은 잘못 잡은 시간축을 전체 지도에서 다시 열 수 있었고, 반대로 마지막 외부 상태는 놓치기도 했다는 데까지입니다.

그래도 저는 지금도 비슷한 active-state 방식을 사용합니다. 새 세션을 시작하거나 긴 대화의 맥락이 어긋났을 때, 먼저 두 질문을 맞춥니다.

1. 프로젝트 전체 지도에서 지금 판단할 위치는 어디인가.
2. 이번 질문의 시간축은 어디까지이며, 그 사실과 계약은 어느 원천이 소유하는가.

그 뒤에 병렬 작업과 외부 사건을 누가 현재 상태에 합칠지도 정합니다. `current`는 판단을 대신하지 않습니다. 새 세션에서도 전체 그림, 현재 한 점, 권위 있는 원천을 같은 화면에서 다시 맞추는 데 씁니다.
