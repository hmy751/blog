# 테스트 9개가 모두 초록인데 제품은 아직 틀렸다

여행 상품의 판매 조건을 일행과 일정에 대입해, 결제 전에 무엇을 더 확인해야 하는지 점검하는 plugin을 만들고 있었습니다.

첫 checkpoint의 결과는 모두 초록이었습니다. 같은 Python `unittest` runner가 test method 9개를 실행했고, 별도의 구조 검증기와 CLI도 통과했습니다. 원안의 충돌을 찾고, 사용자가 허용한 수정만 적용하고, 모호한 답변은 거부하고, 충분한 답변이 들어오면 다음 행동을 바꾸는 상태 흐름까지 확인한 상태였습니다.

그런데 구현을 수정할 권한이 없는 별도 판별자는 이 checkpoint를 통과시키지 않았습니다.

문자열 `"false"`가 boolean 계약을 비껴갔고, test fixture 한 항목은 공개된 판매 조건과 모순됐습니다. 한 참여자에게만 적용돼야 할 답변이 다른 참여자의 상태까지 바꿀 수 있었고, 같은 범위의 상반된 답변은 배열 순서에 따라 결론이 달라졌습니다. 설치된 새 작업에서 사용자의 자연어 요청부터 끝까지 실행한 증거도 없었습니다.

저는 checkpoint를 닫지 않았습니다. 판별자의 미통과를 새 정답으로 받는 대신, source와 실제 입력 형태, 참여자 범위, 답변 충돌, 설치된 제품 경로에서 같은 기능을 다시 열었습니다.

9개 test가 답한 질문은 분명했습니다. 그 질문만으로는 제가 닫으려던 세계를 덮지 못했습니다.

## 문자열 `"false"`는 boolean `False`가 아니었다

가장 작게 재현되는 결함은 타입과 분기의 경계에 있었습니다.

첫 구현은 어떤 공개 조건의 값이 `False`일 때만 충돌을 만들었습니다. 예상한 boolean이 들어오면 맞게 동작했습니다. 하지만 입력 타입을 먼저 확인하지 않았기 때문에 문자열 `"false"`는 `False` 분기를 비껴갔고, 충돌이 없는 상태처럼 흘렀습니다.

문자열을 boolean으로 잘못 변환한 버그는 아니었습니다. 변환 자체가 없었습니다. 공개용으로 결함 범주만 줄이면 다음과 같습니다.

```python
class ContractError(ValueError):
    pass


def has_conflict(value):
    return value is False


def validate_boolean(value):
    if type(value) is not bool:
        raise ContractError("boolean value required")
    return value


assert has_conflict(False) is True
assert has_conflict("false") is False  # 충돌 분기를 비껴감

try:
    validate_boolean("false")
except ContractError:
    pass
else:
    raise AssertionError('문자열 "false"를 boolean으로 받아들였습니다.')
```

`has_conflict()`의 두 번째 결과는 Python 동작으로는 맞습니다. 제품 계약에서 잘못된 지점은 문자열이 그 분기까지 들어오도록 허용한 일이었습니다. 교정은 boolean 자리에 들어온 문자열 자체를 계약 오류로 거부하는 쪽이 됐습니다.

기존 test가 이 문제를 놓친 이유도 단순했습니다. fixture가 예상한 boolean만 넣었기 때문입니다.

구현, fixture, 기대 결과와 완료 설명이 같은 AI 협업 문맥에서 만들어졌습니다. 9개 test는 그 안에서 상태 전이가 일관되는지 정확히 확인했습니다. 빠진 질문은 그 입력이 실제 source와 사용자 요청에서 어떤 형태로 들어오는지, fixture가 바깥 사실과 맞는지였습니다.

## 판별자는 다른 source에서 질문을 다시 열었다

별도 판별자에게 이전 구현 대화와 “완료됐다”는 설명을 이어서 주지 않았습니다. 대신 현재 제품 목표와 완료 계약, code와 test, 공개된 상품 정보를 직접 보게 했습니다. 산출물을 고칠 수 없는 read-only 역할로 뒀습니다.

이 차이 때문에 판별자는 구현이 답하고 있던 질문 밖으로 나갈 수 있었습니다.

- fixture 안에서 상태 엔진이 예상대로 움직이는가.
- fixture의 사실이 공개 source와 일치하는가.
- 예상 밖 타입과 참여자 범위에서도 계약이 보존되는가.
- 자연어 요청이 설치된 제품 경로를 거쳐 같은 상태 변화에 도달하는가.

공개 source 대조에서는 이미 안내된 미성년자 티켓 절차를 fixture가 다시 미확정 질문으로 만들고 있다는 모순도 드러났습니다. 이미 확인된 절차를 판매자에게 다시 묻고 있었던 셈입니다. 교정 뒤에는 이 항목을 확인된 준비 부담으로 남기고, 실제로 확인되지 않은 시작 시각만 질문하도록 범위를 줄였습니다.

첫 checkpoint와 교정 뒤를 test 수만으로 비교하면 이 변화는 잘 보이지 않습니다.

| 검증 범위 | 첫 checkpoint | 교정 뒤 | 9·15에 포함되는가 |
| --- | --- | --- | --- |
| Python 상태 계약 | test method 9개가 미리 정한 입력의 상태 변화를 확인 | test method 15개가 타입·참여자 범위·상반 답변·수정 계보까지 확인 | 포함 |
| 구조 검증기와 CLI | 별도로 통과 | 별도로 다시 통과 | 포함되지 않음 |
| 공개 source 대조 | fixture와 source의 모순을 판별자가 발견 | 확인된 절차와 실제 미확정을 다시 나눔 | 포함되지 않음 |
| 설치형 자연어 E2E | 실행 증거가 없음 | 새 작업에서 자연어 요청부터 다음 행동 변경까지 실행 | 포함되지 않음 |

9와 15는 같은 runner가 실행한 test method 수입니다. source 대조와 validator, CLI, 설치형 end-to-end(E2E)는 숫자 밖의 검증입니다. test가 여섯 개 늘었다고 제품 품질이나 사용자 가치가 여섯 칸 좋아졌다는 뜻도 아닙니다.

숫자는 교정 전후의 검증 목록을 보여 줍니다. checkpoint를 다시 닫은 근거에는 그 밖의 source 대조와 제품 경로 재실행까지 필요했습니다.

## 한 항목만 고치지 않고 제품 경로를 다시 열었다

처음 발견된 모순 한 건만 fixture에서 고치면 test는 다시 초록이 될 수 있었습니다. 하지만 그렇게 하면 같은 검증 세계 안에서 기대 결과만 바꾸는 데 그칩니다.

저는 교정 범위를 다음처럼 다시 잡았습니다.

- boolean 자리에 문자열이나 정수가 들어오면 구조화된 계약 오류로 거부합니다.
- 한 참여자에 관한 답변은 그 참여자의 상태만 바꿉니다.
- 같은 범위의 상반된 답변은 배열 순서와 관계없이 실패합니다.
- 수정안은 자신이 바꾸는 원안을 직접 가리켜야 합니다.
- 공개 source로 확인된 사실과 판매자에게 물어야 할 미확정을 다시 나눕니다.
- 설치된 새 작업에서 자연어 요청부터 답변 적용 뒤 다음 행동까지 다시 실행합니다.

이 기준으로 AI와 계약과 상태 엔진을 교정하고, 같은 제품 경로를 새 작업에서 다시 실행했습니다.

첫 자연어 요청에는 상품과 일행, 날짜, 바꿀 수 없는 조건만 들어 있었습니다. plugin은 공개 상품 정보를 확인하고 원안의 첫 충돌을 찾았습니다. 사용자가 대화에서 허용한 일행 변경만 적용한 뒤에는 충돌 하나가 해소됐지만, 가격과 티켓 준비 부담, 확인되지 않은 시작 시각은 그대로 남았습니다.

이어서 짧은 답변과 범위가 충분한 답변을 차례로 적용했습니다. 여기서 사용한 답변은 상태 전이를 검증하기 위한 fixture이며 실제 판매자가 보낸 발화는 아닙니다.

```text
자연어 요청
→ 공개 상품 정보 확인
→ 원안의 첫 충돌 판정
→ 사용자가 허용한 수정만 적용
→ 범위가 모호한 fixture 답변 거부
→ 상품·날짜·참여자·시각이 충분한 fixture 답변 적용
→ 관련 시간 상태와 다음 행동만 변경
```

모호한 답변은 상태를 바꾸지 않았습니다. 범위가 충분한 답변은 확인하던 시각 상태만 갱신했고, 원안의 다른 충돌과 기본 비용, 별도 티켓 준비 부담은 보존했습니다. 다음 행동은 `추가 확인`에서 `결제 검토`로 이동했습니다.

교정 뒤 같은 runner의 test method 15개와 별도 구조 검증기·CLI를 다시 확인했습니다. 설치된 환경의 자연어 E2E와 짧은 회귀 판별도 통과했습니다. 다만 마지막 판별자는 설치 상태와 E2E 기록을 입력으로 받았으므로, 제출물 하나만 받아 설치부터 재현한 완전한 clean-room 검사는 아니었습니다.

checkpoint는 판별이 연 공백을 source와 계약으로 확인하고, AI와 구현을 교정한 뒤 같은 제품 경로를 재실행한 결과로 다시 닫았습니다.

## 판정, 수정, 완료 선언을 한곳에 모으지 않았다

독립 판별의 결과가 유용했다고 해서 판별자를 새 정답으로 올리지는 않았습니다.

reviewer가 직접 수정하고 자기 수정까지 통과시키면 구현자의 자기인증과 비슷한 구조가 됩니다. 반대로 reviewer의 미통과를 이유 없이 받아들이면 그 판정을 검증할 위치가 사라집니다. 그래서 역할을 나눴습니다.

1. 판별자는 구현자와 다른 source와 입력에서 질문을 다시 열되, 산출물을 수정하지 않습니다.
2. 저는 현재 계약과 source를 대조해 교정 범위를 정하고, 판정에서 받아들일 것과 다시 확인할 것을 나눕니다.
3. 완료는 code·test·설치·같은 제품 경로의 재실행으로 닫습니다.

이 구조에도 한계는 있습니다. 다른 답변 시스템에서 생성 호출과 판정 호출을 나눴을 때, 앞 단계가 값을 빠뜨리거나 조건 문장을 잘못 골라 닫힌 입력을 넘기면 판별자는 그 바깥의 원문을 자동으로 다시 열지 못했습니다.

판정 역할을 분리하는 것과 판별자가 볼 입력의 경계를 여는 것은 다른 문제였습니다.

같은 모델인지 다른 모델인지는 이 조건을 자동으로 해결하지 않습니다. 같은 입력, 같은 질문, 같은 완료 설명을 받으면 별도 AI도 같은 frame을 반복할 수 있습니다.

첫 checkpoint의 9개 test는 무용하지 않았습니다. 구현이 만든 상태 계약 안에서 무엇이 일관되는지를 보여 줬습니다. 다만 그 결과로 source, 실제 입력 타입, 참여자 범위와 설치된 자연어 흐름까지 함께 통과시킨 것이 문제였습니다.

제가 필요로 한 제3판별자는 세 번째 AI가 아니었습니다. 다른 검증 세계를 열고, 그 결과를 기존 완료 설명과 분리해 남기며, 자신의 판정까지 source와 재실행으로 다시 검증받는 판단 위치였습니다.
