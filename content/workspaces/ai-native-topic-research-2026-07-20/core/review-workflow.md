# Review workflow

이 문서는 이 작업 단위에서 review의 목적, 역할별 입력 경계, 반환할 결과, main의 회수를 소유한다.

- 현재 중심과 열린 판단은 `active-state/`가 소유한다.
- 반복 판단축은 [criteria.md](./criteria.md)가 소유한다.
- 사실과 사건의 직접 원천은 [sources/index.md](../sources/index.md)가 소유한다.
- 수정 권한과 전체 작업 순서는 [workflow.md](./workflow.md)가 소유한다.
- 개별 review 결과와 채택·조정·기각·보류 과정은 `process/`에 남긴다.

## Review가 필요한 이유

Main은 사용자와 맞춘 현재 그림, 지난 결정, 변경 권한을 들고 작업을 이어가야 한다. 이 context는 연속성을 지키는 데 필요하지만, 동시에 main이 이미 중요하다고 본 장면과 해법 안에서 결과를 읽게 한다. 결과물을 직접 고치는 것도 main이라, 자기가 고른 기준이나 빠뜨린 가능성 자체를 같은 자리에서 판정하기 어렵다.

Review는 이와 다른 판단 위치를 만든다. Reviewer는 현재 합의와 과거 process 대신 결과물, 직접 원천, 이번 review의 최소 frame에서 시작해 다음을 본다.

- main이 작업하며 굳힌 framing 때문에 보이지 않은 문제는 없는가
- 원천에 있는데 결과가 사용하지 못한 동기·장면·대비·판단 논리는 없는가
- main이 제시한 질문이나 현재 중심 자체를 다시 열 근거가 있는가
- 다음 결과를 더 낫다고 판단할 기준과 미통과 조건은 무엇인가

과거 context를 모두 주면 reviewer가 기존 판단에 앵커링될 수 있고, 결과물과 고정 질문만 주면 원천에 남은 가능성을 보지 못한 채 읽힘 점검으로 닫힐 수 있다. 그래서 review의 목적에 맞춰 입력을 분리하고, 결과 개선 review에는 직접 원천 접근과 질문을 다시 열 권한을 함께 준다.

Reviewer의 독립 결과도 새 정답은 아니다. 현재 합의와 사용자 해석을 모르는 대신 main이 놓친 것을 볼 수 있게 한 것이므로, main이 입력 범위와 근거를 확인하고 현재 그림·사용자 판단과 대조해 회수한다. 독립 review와 main 회수는 서로 대신하지 않는 한 쌍이다.

입력을 얼마나 가렸는지만으로 review 역할을 정하지 않는다. 먼저 이번 review가 결과물을 개선하려는지, 처음 읽히는 모습을 보려는지, 사실을 확인하려는지 정한다.

## 결과물을 개선하는 review

목적은 현재 결과의 등급을 붙이는 데서 끝나지 않고, 무엇을 기준으로 보면 더 나은 결과가 되는지 찾아 다음 수정과 다음 판별을 가능하게 하는 것이다.

### 대상과 최소 목표

결과물과 직접 원천은 현재 무엇이 쓰였고 어떤 가능성이 남았는지는 보여 주지만, 누구에게 무엇을 가능하게 해야 더 나은 결과인지까지 정하지는 않는다. 이 경계가 없으면 reviewer가 임의의 독자나 성공 기준을 만들어 완성도, 정보량, 톤처럼 자신이 고른 방향으로 결과를 최적화할 수 있다.

따라서 main은 한 review round에서 사용할 **대상**과 **최소 목표**를 제공한다.

- 대상: 결과물을 읽거나 사용하는 독자·사용자·이해관계자
- 최소 목표: 그 대상이 결과를 통해 이해하거나 판단하거나 할 수 있어야 하는 최소 결과

이 둘은 review의 근거 자료가 아니라 평가 범위를 맞추는 frame이다. 해당 round에서는 고정해 사용하되 영구 기준은 아니다. Reviewer는 대상과 목표가 원천이나 결과물과 충돌하거나 너무 모호하다고 지적할 수 있지만, 말없이 다른 대상으로 바꾸지는 않는다.

고정하지 않는 것은 main이 원하는 중심, 해법, 대표 장면, 구조, 예상 결론이다. 이런 내용을 통과 조건처럼 주면 reviewer가 독립적으로 더 나은 기준과 빠진 가능성을 찾기보다 main의 답을 확인하게 된다. main이 결과물을 읽으며 만든 판단은 대상과 최소 목표에 적지 않고 회수에서 쓴다.

대상이나 최소 목표 자체가 아직 열린 질문이면 improvement review에 임의의 답을 맡기지 않는다. 먼저 사용자와 맞추거나 별도의 탐색·조언으로 후보를 만든 뒤, 이번 review가 사용할 frame을 정한다.

### 입력

- 대상 `src` 결과물
- 이번 review round의 대상과 최소 목표
- [sources/index.md](../sources/index.md)에서 고른 직접 원천

Main은 현재 쟁점에 필요한 최소 원천 묶음을 먼저 제공한다. Reviewer는 그 묶음으로 개선 기준을 세우기 어렵거나 main이 놓친 material을 독립적으로 확인할 수 없다고 판단하면, 부족한 원천의 역할을 밝히고 `sources/index.md`에서 추가 직접 원천을 스스로 고르거나 요청할 수 있다.

원천 묶음에는 결과물의 발생 이유와 발상 계보를 지원하는 원천이 들어 있는지 확인한다. 같은 결과물이 review 통과 뒤 사용자 판정에서 반복해서 미채택되면, reviewer를 늘리기 전에 main이 자른 원천 범위를 먼저 의심한다.

기본적으로 다음은 입력하지 않는다.

- `active-state`
- 이 작업의 `process`
- 이전 원고와 review
- `core/moments.md`
- main이 채택하려는 방향이나 예상 판정

파일을 주지 않아도 같은 내용을 대상·최소 목표나 요청 문장에 적으면 준 것과 같다. 맡기기 전에 packet을 한 번 읽으며, reviewer가 스스로 찾아야 할 것을 main의 문장이 먼저 말해 주고 있지 않은지 본다.

추가 원천을 고를 때도 `active-state`와 `process`를 우회 입력으로 사용하지 않는다.

직접 원천은 결과물의 사실 확인만을 위한 것이 아니다. 원천과 결과를 대조해 빠진 동기, 장면, 대비, 판단 논리, 아직 쓰지 않은 가능성을 발견하는 데도 사용한다. 다만 원천의 모든 내용을 넣는 것을 품질로 삼지 않는다.

### 반환

Reviewer는 다음을 구분해 보고한다.

1. 실제로 본 입력 경계
2. 이 결과를 더 낫게 판단할 개선 기준 후보와 각 기준이 필요한 이유
3. 그 기준으로 본 현재 결과의 강점과 가장 큰 간극
4. 통과가 아니라면 무엇이 채워져야 하는지
5. 이번 결과를 고칠 제안과 이후에도 반복할 기준 후보

Reviewer는 문제 정의나 중심 자체를 다시 열 수 있다. 다만 reviewer가 제안한 기준과 중심 변경은 새 관찰이며 자동 채택되지 않는다.

## 원고만 읽히는지 보는 review

원고만 주는 검토는 처음 보는 독자가 무엇을 이해하고 어디서 막히는지 확인할 때 사용한다.

- 원고 밖의 material이나 직접 원천을 보지 않았다는 입력 경계를 적는다.
- 독자 진입, 중심의 가시성, 내부 맥락 의존, 반복과 흐름을 관찰한다.
- 원천에 있는데 빠진 material, 사실 정확성, 현재 합의까지 판정한 결과처럼 확대하지 않는다.
- 이 검토 하나의 수정 강도나 통과 판정을 전체 개선 상태로 사용하지 않는다.

## 사실을 보는 verifier

- 검증할 주장과 직접 원천 접근점을 제공한다.
- verifier가 필요한 원천 범위와 판정을 정한다.
- 예상 결론이나 main의 채택 방향을 제공하지 않는다.

## 맥락을 포함한 편집·조언

현재 중심을 지키며 대안을 만드는 작업자는 `active-state`, 필요한 `criteria`, 대상 `src`, 필요한 직접 원천을 읽는다. 과거 `process` 전체는 자동 입력이 아니며, 특정 판단의 이유가 필요할 때만 연다.

이 작업은 독립 review와 다르다. 현재 합의 안에서 대안을 만드는 역할이며, 그 결과도 자동으로 현재 판단이 되지는 않는다.

## Main의 회수

Main은 독립 결과를 다음 순서로 회수한다.

1. review가 실제로 본 입력과 판정 범위를 확인한다.
2. reviewer가 제안한 개선 기준을 `active-state`, `criteria`, 사용자 판단과 대조한다.
3. 선택한 개선 기준으로 review의 관찰과 통과 조건을 다시 읽는다.
4. 사실 충돌은 필요한 직접 원천으로 확인한다. 제안이 원고에 없던 사실 주장(시점, 수치, 행위 주체, 인과)을 새로 만들면, 문장 품질 근거가 옳아도 그 사실을 반영 전에 표시하고 직접 원천으로 따로 확인한다.
5. 제안을 다음처럼 구분한다.
   - 현재 그림 안에서 사실을 바로잡는 제안
   - 현재 중심을 유지하며 표현을 고치는 제안
   - 대표 장면이나 구조를 바꾸는 제안
   - 글의 중심이나 사용자의 해석을 바꾸는 제안
   - 이번 결과물만 고칠 조건과 이후에도 반복할 기준
6. [workflow.md](./workflow.md)의 변경 권한에 따라 직접 처리하거나 사용자와 상의한다.
7. 회수 반영으로 원고가 바뀌면 바뀐 문장과 새로 들어간 표현은 사실 확인을 다시 거친다.
8. 채택·조정·기각·보류와 이유를 해당 `process` cycle에 남긴다. 이때 각 review의 실행 주체와 실제 입력 packet 목록, 그 review가 보지 못한 층위 한 줄을 함께 남긴다.
9. 현재 함께 작업할 판단이 바뀌면 `active-state`의 유지 계약에 따라 갱신한다.
10. 여러 cycle에 반복할 기준으로 합의한 경우에만 `core/criteria.md`를 갱신한다.

반복해서 같은 문제가 나타났다는 사실은 현재 중심을 자동 폐기하지 않는다. 다만 기존 중심이나 장면을 다시 열어야 한다는 신호로 올릴 수 있다.

서로 다른 입력 경계의 review가 독립적으로 같은 지점에 닿은 발견은 회수에서 우선 처리하고, 단일 review의 큰 구조 제안은 자동 반영하지 않고 사용자 선택으로 올린다.

## 이 계약을 고칠 때

Review의 목적, 입력 경계, 반환 형식, main의 회수 방식이 실제 작업과 맞지 않으면 사용자와 논의해 이 문서를 고친다. 바뀐 이유와 이전 방식은 `process/context-structure/`에 남긴다.
