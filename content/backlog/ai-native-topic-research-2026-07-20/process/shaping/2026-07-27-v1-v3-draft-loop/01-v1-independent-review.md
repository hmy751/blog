# v1 독립 review report

Blind 조건 고지: backlog 용어를 찾기 위해 실행한 `rg`에서 제외 glob이 제대로 적용되지 않아, 금지된 `process/shaping/2026-07-27-v1-v3-draft-loop/README.md`와 `criteria-evolution.md`의 일부 검색 일치 행이 출력됐습니다. 경로·단계 상태·v1 링크·소제목 수준의 부분 노출이었고, 두 파일을 열거나 연속 본문을 읽지는 않았습니다. 해당 행에서 본 내용은 아래 판단과 제안의 근거로 사용하지 않았습니다. 다만 엄격한 blind 조건상 부분 노출이 발생했다는 사실을 먼저 밝힙니다.

그 밖에는 허용된 backlog, 직접 연결된 원자료, v1 다섯 편만 읽었습니다. 파일 수정이나 커밋은 하지 않았습니다. 이 보고서는 글의 순위, 첫 글, 병합, 발행 여부를 판단하지 않습니다.

## 공통 관찰

다섯 글 모두 v1에서 이미 단순한 AI 사용 팁보다 한 단계 깊은 질문을 잡았습니다. 다음 수정에서 필요한 것은 새 원칙을 더 붙이는 일이 아니라, 각 글이 이미 가진 판단 변화를 하나의 사건과 artifact로 더 단단히 증명하는 일입니다.

현재 공통 위험은 세 가지입니다.

- 구체적인 사건에서 출발한 뒤 여러 운영 원칙과 사례를 계속 더해, 후반이 탐구보다 매뉴얼에 가까워집니다.
- 인과 한계는 결말에서 잘 밝히지만, 중간 문장에는 관찰보다 강한 AI 일반론이 남아 있습니다.
- 제안, 실제 구현, 검증된 결과가 일부 문장에서 같은 사건처럼 이어집니다.

특히 사실 교정이 필요한 곳은 두 군데입니다.

- `product-flow-scope-control.md`의 raw `facts[]` 화면은 원자료상 실제로 만들어진 화면이 아니라 구현 준비 중 제안된 경로입니다. “화면이 생겼다”는 표현은 고쳐야 합니다.
- `independent-review-and-recovery.md`의 Tripproof A/B에서 기대-supported 문항의 하락을 전부 “깨끗한 값의 과잉강등”으로 묶으면 안 됩니다. 하나는 값 표기 열화에 따른 grounding 회귀였지만, 다른 item은 실제 조건 문맥이 있어 데이터셋 기대값 자체와 충돌했습니다.

## 다음 수정에 적용할 독립 기준

### 1. 한 글에는 하나의 사건 척추와 하나의 판단 변화가 있어야 합니다

`active-state/criteria.md`가 요구한 것은 많은 사례가 아니라 시간축 위의 실제 판단 변화입니다. v1은 모두 좋은 첫 장면을 갖고 있지만, 뒤에서 다른 사건들이 같은 무게로 커집니다.

수정할 때 각 사례의 역할을 명시하는 편이 좋습니다.

- 중심 사건: 판단이 실제로 바뀐 장면
- 보조 사건: 같은 메커니즘이 다른 조건에서도 나타난 장면
- 반례: 중심 해석이 만능 규칙이 아님을 보여 주는 장면
- 경계: 언제 그 기준을 적용하지 않을지 보여 주는 장면

보조 사례가 새로운 중심 질문을 요구한다면 더 설명하기보다 이번 글에서는 범위를 줄여야 합니다.

### 2. 원칙보다 먼저 작은 before/after artifact를 보여 줘야 합니다

backlog는 code, test, 상태 변화, 문서 diff처럼 독자가 판단을 복구할 수 있는 artifact를 요구합니다. 현재 v1에는 artifact가 서술로는 존재하지만 실제 변화가 한눈에 보이지 않는 경우가 있습니다.

- current: 최근 구현 중심의 설문 배치와 재작성 뒤 문항별 source/time-axis 배치를 익명화해 비교
- 독립 판별: 9개와 15개가 각각 무엇을 검사했는지 검증 역할 단위로 비교
- 판단 순서: 첫 판의 A1/A2 하위 구간이 두 번째 판에서 별도 후보 2·3으로 놓인 경계 변화
- scope: `FactCandidate[] → raw 화면 제안`과 `FactCandidate[] → ChatAnswer → 실제 소비 경로`의 차이
- self-check: “생각하자”는 정정 뒤 다시 초안을 냈던 다음 한 동작과, 실제 자료 범위를 다시 확인한 동작의 대비

내부 원문을 공개할 필요는 없습니다. 역할과 순서만 남긴 재구성 artifact임을 표시하면 됩니다.

### 3. 사실·경험·해석·운영 규칙·미검증 효과를 문장이 등장한 자리에서 나눠야 합니다

마지막 한계 문단만으로는 중간의 강한 인과 문장을 상쇄하기 어렵습니다.

예를 들면 다음처럼 구분할 수 있습니다.

- 사실: “두 번째 후보판에서는 다섯 경계가 나왔다.”
- 경험: “나는 첫 판에서 하나로 읽었던 문제가 갈라져 보였다.”
- 해석: “기준의 위치가 문제 경계 구성에 영향을 줬을 가능성이 있다.”
- 운영 규칙: “그래서 생성과 수렴을 별도 pass로 남기기로 했다.”
- 미검증 효과: “이 순서가 최종 결과를 더 좋게 만드는지는 확인하지 못했다.”

이 구분은 다음 문장들에 특히 필요합니다.

- “AI는 방어 가능한 답을 만든다.”
- “AI는 작고 확실한 결과로 수렴했다.”
- “같은 오염된 입력이면 오류 상관은 그대로 남는다.”
- “자기진단이 행동을 바꾼 경우도 있었다.”
- “current가 긴 작업을 작동시킨다.”

### 4. 제안, 구현, 실행 결과, 장기 효과를 분리해야 합니다

직접 원자료에는 네 단계가 자주 섞여 있습니다.

- scope의 `facts[]`와 deterministic adapter는 제안·설계 장면
- 제품행동 test와 호출되지 않는 추출 경로 제거는 실제 구현 변경
- Tripproof entailment split은 구현되고 A/B까지 실행됐지만 AC2는 불성립
- current 구조는 실제 운영됐지만 recency bias와 terminal event 누락을 자동으로 막지 못함
- self-check skill과 전역 규칙은 생성됐지만 재발 감소는 측정되지 않음
- 판단 순서의 종료 조건은 현재 운영 계약이지 품질 개선이 증명된 방법론이 아님

“무엇을 만들었다”와 “그것이 효과를 냈다” 사이를 생략하지 않아야 합니다.

### 5. AI-native 특수성은 살리되 모델 일반론으로 넓히지 않아야 합니다

이 글들의 고유한 재료는 일반적인 문서화·테스트·기획 원칙이 아니라 AI와 함께 일할 때 판단 권한이 어떻게 흐려졌는지에 있습니다.

- current: 최근 context의 구체성이 전체 시간축을 대신함
- 독립 판별: 구현, fixture, 기대 결과가 같은 문제 정의에서 생성됨
- 판단 순서: rubric이 평가 도구를 넘어 생성 재료가 됨
- scope: `작게`, `안전하게`, `빨리 보이게`가 확실한 surrogate output으로 번역됨
- self-check: 오류 설명 뒤에도 기본 행동이 같은 대화에서 재현됨

다만 이것을 “AI는 원래 그렇다”로 쓰지 말고 “이 작업에서 이런 입력·권한 배치 아래 관찰됐다”로 제한해야 합니다.

### 6. 살아 있는 판단 장면을 체크리스트보다 보호해야 합니다

다섯 글 모두 후반에 질문 목록이나 운영 순서가 반복됩니다. 전달 가능한 기준은 필요하지만, 목록이 늘수록 글쓴이의 발견이 운영 문서처럼 평평해집니다.

- 목록은 글당 하나의 최종 도구로 모으기
- 중간의 목록은 실제 장면이나 artifact로 바꾸기
- 망설임, 처음의 오해, 판단이 바뀐 순간은 남기기
- 결말의 한계는 유지하되 앞선 내용을 다시 요약하는 문장은 줄이기

특히 `ai-self-check.md`와 `judgment-order.md`의 첫 장면과 마지막 판단 문장은 그대로 보호할 가치가 있습니다.

### 7. 공개 경계와 숫자의 단위를 끝까지 유지해야 합니다

현재 v1은 로컬 경로, task/session ID, 개인 대화의 직접 인용을 피하고 있어 공개 경계가 대체로 잘 지켜졌습니다. 다음 수정에서도 다음을 유지해야 합니다.

- private raw는 발화문이 아니라 익명화된 행동 순서로 재구성
- 내부 코드 경로와 line number는 공개 원고에 넣지 않음
- 합성 예시는 합성·재구성이라고 명시
- 9와 15는 test runner 전체 pass 수인지 test method 수인지 확인해 단위를 표시
- test 수, commit 수, 문서 길이는 품질·생산성·사용자 가치 지표로 사용하지 않음
- 공개 상품 사실을 구체적으로 추가한다면 원문 링크와 현재 상태를 다시 확인

## 글별 review

### `current-active-state-operation.md`

#### 보존할 것

- current를 읽었는데도 최근 구현이 프로젝트 전체를 대신한 첫 장면
- history, active contract, source, current의 갱신 규칙을 분리한 설명
- 전체 지도와 현재 cursor를 함께 두는 구조
- current를 답 저장소가 아니라 source router로 보는 해석
- 실제 내부 문장이 아니라 역할을 재구성한 예시라고 밝힌 점
- terminal event 누락과 갱신 책임을 current의 사용 조건으로 둔 점
- current만으로 연속성이나 생산성 향상을 주장하지 않은 결말

#### 구체적으로 수정할 것

첫 장면 뒤에 작은 before/after를 넣는 것이 가장 효과적입니다. AX의 설문 재작성에서는 current를 다시 요약한 것이 아니라 다섯 문항을 조사, 문제 정의, 솔루션 선택, 구현 검증의 서로 다른 시간축과 원천에 배치했습니다. 이 변화를 익명화한 표나 짧은 block으로 보여 주면 “읽었다”와 “판단에 작동시켰다”의 차이가 바로 보입니다.

현재 중반 이후에는 다음 주제가 각각 큰 절을 차지합니다.

- 기록과 계약의 분리
- 지도와 cursor
- targeted read
- stale와 갱신 책임
- 네 문서 역할

모두 유효하지만 하나의 글에서는 다소 반복됩니다. 네 역할 체계는 결말의 정리로 압축하고, 중간은 설문 재작성 사건이 어떻게 복구됐는지에 더 오래 머무는 편이 좋습니다.

current audit에서는 구현 gate 뒤의 패키징, 문항 정리, 외부 업로드 실패가 마지막 current에 반영되지 않았습니다. 이 반례는 유지하되 “그래서 current가 무용하다”가 아니라 “덮어쓰기 상태에는 terminal event 갱신 주체가 필요하다”는 현재 해석으로 제한해야 합니다.

검증용 agent가 다른 역할의 current/re-entry 규칙 때문에 잘못된 작업 위치로 들어간 사례도 원자료에 있습니다. 이를 넣는다면 새 사례로 확장하지 말고 “current 활성화는 역할에 따라 달라질 수 있다”는 한 문장짜리 경계로만 사용하는 편이 맞습니다.

#### 사실·인과·공개 경계

- 설문 복구는 current 단독 효과가 아닙니다. 사용자 정정, current의 전체 지도, process 문서, research/problem/solution 원천을 함께 사용했습니다.
- “제가 분리했습니다” 같은 문장은 개인 운영 경험으로는 가능하지만, 단독 설계·인과를 뜻하지 않게 해야 합니다.
- current가 21개 reachable commit 중 18개에서 바뀌었다는 audit 숫자는 꼭 필요하지 않습니다. 넣는다면 활동량이지 효용 지표가 아니라고 밝혀야 합니다.
- 합성 current 예시는 현재처럼 재구성 표시를 유지하면 공개 경계상 안전합니다.

### `independent-review-and-recovery.md`

#### 보존할 것

- “test가 거짓말을 한 것은 아니었다”는 중심 문장
- 9개 초록 test와 별도 판별의 미통과가 충돌하는 기술 장면
- fixture consistency, source-to-contract, adversarial schema, installed natural-language E2E의 분리
- source 모순, 문자열 boolean, participant scope, claim order, revision lineage의 구체성
- 같은 checkpoint를 고쳐 15개 test와 설치형 자연어 흐름으로 다시 닫은 과정
- fresh regression이 외부 제출물 단독 재현은 아니었다는 제한
- Tripproof entailment A/B를 “reviewer를 하나 더 두면 된다”는 결론의 반례로 쓴 구성

#### 구체적으로 수정할 것

AX 기술 사건을 끝까지 중심 척추로 두는 편이 좋습니다. Tripproof는 “판별 입력이 이미 오염됐을 때 분리된 judge도 복구하지 못한다”는 한 가지 반례 역할만 맡기면 충분합니다.

후반의 read-only, 결과 분리, 사용자 회수, 완료 선언 분리는 유효한 운영 기준이지만 현재는 별도의 독립 판별 방법론처럼 커집니다. 이 부분을 유지하려면 실제 회수 사건 하나를 붙이거나, “이 사건 이후 선택한 운영 경계”라고 낮춰 써야 합니다. 그렇지 않으면 목록을 줄이는 편이 근거 범위에 맞습니다.

9개와 15개는 원자료에서 test method 기준인지 확인해 단위를 통일해야 합니다. 숫자 증가보다 다음 변화가 보이게 해야 합니다.

- fixture 내부 일관성만 보던 상태
- public source 대조
- 적대 schema와 범위
- 설치된 plugin의 자연어 E2E

Tripproof 반례는 다음 사실을 더 정확히 반영해야 합니다.

- 판정 ON에서 원래 P1-01은 `needs_review` 3회로 내려갔지만, 의도한 `conditional` 판정이 아니라 값 미추출 뒤 `not_established` 안전망이 받은 결과였습니다.
- PARA2에서는 조건 문장 자체가 값으로 추출돼 `supported`가 3회 발생했습니다.
- P0-01 하락은 단일한 과잉강등이 아니었습니다. 한 item은 추출 프롬프트가 원문 표기를 바꿔 value grounding이 실패했고, 다른 item은 실제 조건부 문맥이 있어 데이터셋 기대와 의미가 충돌했습니다.
- 따라서 “판별자는 입력 안에서 일관됐다”는 결론은 유지할 수 있지만 “깨끗한 값이 모두 과잉강등됐다”는 요약은 고쳐야 합니다.
- 판별 분리와 response shape 보존은 확인됐지만, 목표 acceptance인 AC2는 불성립이었습니다.

“같은 오염된 입력과 같은 문제 정의를 받으면 오류 상관은 그대로 남는다”는 문장은 통제된 상관 측정처럼 들립니다. “이번 A/B는 판별 호출을 나눠도 앞단에서 사라진 맥락을 복구할 수 없음을 보여 줬다” 정도가 원자료에 더 가깝습니다.

#### 사실·인과·공개 경계

- 첫 verifier는 이전 대화와 구현자의 완료 설명은 받지 않았지만 목표, 계약, source, test, CLI 등은 받았습니다. “완전히 무맥락”이나 “외부 제3자”라고 부르면 안 됩니다.
- fresh regression도 설치 상태와 E2E artifact를 입력받았습니다. 현재 draft가 이 한계를 잘 밝히므로 보존해야 합니다.
- 버그 종류는 공개 가능한 기술 범주로 재구성돼 있고 내부 경로가 없어 현재 경계는 적절합니다.
- 특정 상품 사실을 더 자세히 넣는다면 공개 listing을 다시 확인하거나 익명화된 source/fixture 차이만 남겨야 합니다.

- A2: 실제 진행 경험 예상

Cofathon 부분의 “AI는 방어 가능한 답을 만든다”, “rubric에 맞는 후보를 선호한다”는 문장은 인과가 강합니다. 확인된 범위는 다음과 같습니다.

- 첫 후보군 15개에 구체적인 사람과 업무 장면이 부족했습니다.

- 최종 품질 개선은 검증하지 않았고, prompt, 입력, 성과 압박, 누적 guard가 함께 달랐습니다.

종료 순서는 현재 운영 규칙으로 표시해야 합니다. “새 관계가 더 나오지 않는다”는 판정도 객관적 측정치가 아니라 현재 목적과 비용 아래의 수렴 신호입니다.

#### 사실·인과·공개 경계

- 두 번째 판은 첫 판보다 옳다고 증명되지 않았고 완전 blind도 아니었습니다.
- 첫 판 역시 A1/A2 경계를 이미 보았으므로 “두 번째 pass가 처음으로 경계를 발견했다”는 문장은 피해야 합니다.
- Cofathon 후보 유사도나 품질을 측정한 실험이 아닙니다.
- 후보 명칭을 공개할 때는 내부 과제·회사 맥락보다 익명화된 경계 변화만 남기는 편이 안전합니다.
- 현재 글은 내부 파일명과 private 발화를 노출하지 않아 공개 경계가 잘 지켜져 있습니다.

### `product-flow-scope-control.md`

#### 보존할 것

- `facts[]`와 사용자 답변의 계약이 다르다는 중심 문제
- 범위의 폭과 제품의 핵심 작용을 구분한 설명
- deterministic 구현이 언제나 가짜는 아니라는 반대 경계
- source 변경에 따라 결과가 바뀌는 metamorphic test
- supported evidence의 원문 substring 확인
- 실제 소비 경로가 composer를 호출하는 routing test
- 호출되지 않는 별도 추출 경로를 제거한 artifact
- slice의 끝을 UI가 아니라 실제 소비자로 정의한 결말
- test가 답변 품질 전체나 사용자 가치를 증명하지 않는다는 한계

#### 구체적으로 수정할 것

첫 장면의 사실 상태부터 고쳐야 합니다. `2026-06-09-spec-driven-product-flow-drift`는 spec-driven 흐름에서 `client가 facts[]를 렌더링`하는 방향이 더 작은 구현처럼 제안됐다고 기록합니다. 실제 화면이 완성됐다는 기록이 아닙니다.

따라서 다음 표현을 바꿔야 합니다.

- “API가 값을 반환하고 화면도 생기니” → “API 값을 화면까지 잇는 안이 제안되니”
- “화면은 생겼지만” → “화면까지 가는 안은 있었지만”
- “raw 배열도 UI까지는 갔다” → “raw 배열을 UI까지 보내는 안도 가능했지만”

June 5 deterministic 사건과 June 9 `facts[]` 사건도 분리해야 합니다. 둘 다 구현 성공·실패가 아니라 제품 위험을 피하면서 확실한 demo output으로 이동한 제안 장면입니다. 같은 종류의 경향으로 해석할 수는 있지만, 두 번의 실제 배포 실패처럼 쓰면 안 됩니다.

반면 제품행동 test와 호출되지 않는 경로 제거는 실제 decision과 구현 변화입니다. 글에서 이 전환점을 명확히 표시하면 좋습니다.

```text
제안에서 관찰한 drift
→ 제품행동 계약으로 재정의
→ test와 routing에 강제
→ 의미 품질과 장기 재발은 별도 검증
```

“AI는 작고 확실하게 완료할 수 있는 쪽으로 수렴했다”는 문장은 사용자와 AI의 자기분석에서 나온 해석입니다. “이 대화에서 나는 그 제안을 불확실한 중심 변환 대신 눈에 보이는 surrogate를 택한 것으로 읽었다” 정도로 제한해야 합니다.

마지막의 라이브러리·배치·데이터 파이프라인 예시는 유효하지만 실제 사례에서 멀어집니다. 중심 사건의 흐름이 약해진다면 예시를 줄이고 소비자 계약이라는 한 문장으로 정리할 수 있습니다.

#### 사실·인과·공개 경계

- `facts[]` 경로는 제안이고, 실제 배포 화면이 아닙니다.
- deterministic adapter도 해당 대화에서 product proof로 제안된 설계이며, 실제 사용자 효과를 측정한 것이 아닙니다.
- 세 test와 경로 제거는 구현 artifact지만 이후 drift 감소나 답변 의미 품질 향상을 증명하지 않습니다.
- “불확실성을 통제 가능한 demo로 바꾸려는 충동”은 사용자가 중요하다고 확인한 해석이지만 보편적 AI 성향으로 쓰면 안 됩니다.
- `facts[]`, `supported`, `missing` 같은 일반 계약명은 공개 가능하지만 내부 파일 경로와 private 대화문은 계속 제외해야 합니다.

### `ai-self-check.md`

#### 보존할 것

- 오류를 정확히 설명한 뒤 같은 행동을 반복한 첫 장면
- “정확한 설명과 다음 행동 변화는 다른 결과”라는 중심 발견
- assignment archive 사건에서 self-check 정의가 생긴 과정
- 진단 정확도, 다음 행동 변화, 재발 방지의 분리
- 전역 규칙 변경 자체를 효과 증거로 사용하지 않은 점
- 한쪽 과교정을 고친 뒤 반대쪽으로 넘어간 AX 사건
- 단순 질문의 self-check 과잉 발동의 경계
- “설명과 행동을 같은 결과로 보지 않게 됐다”는 마지막 문장
- `했다`체와 자기 관찰의 질감

#### 구체적으로 수정할 것

현재는 다섯 사건이 모두 큰 비중을 가집니다.

- forward bias 반복
- assignment archive 원자료 누락
- AX의 양방향 과교정
- 단순 질문의 self-check 과잉 발동
- fresh audit의 역할

중심 척추는 forward bias 사건과 “진단/다음 행동/재발” 구분으로 유지하는 편이 자연스럽습니다. assignment 사건은 self-check 정의의 기원, AX는 과교정 반례, 단순 질문은 종료·발동 경계로 역할을 제한하면 좋습니다.

“바로 다음 행동이 달라진 경우도 있었다”는 문장은 현재 글 안에서 구체적으로 보이지 않습니다. assignment raw에는 사용자 정정 뒤 전체 자료를 다시 찾아 세 곳을 더 고친 행동이 있습니다. 이를 사용할 수는 있지만 다음 경계를 밝혀야 합니다.

- 행동 변화는 사용자의 직접 정정 뒤 일어났습니다.
- formal self-check가 그 변화를 일으켰다고 증명하지 않습니다.
- 이 사건은 “진단 뒤 어떤 다음 행동을 관찰할 것인가”를 보여 주는 예이지 self-check 효과 실험이 아닙니다.

July 9 사건에서 확인되는 것은 최소 세 차례의 실행 회귀와 최종 규칙 문구 변경입니다. 규칙 변경 이후 비슷한 상황에서 재발이 줄었는지는 확인되지 않았습니다. 현재 글이 이 한계를 잘 밝히므로 유지해야 합니다.

AX 과교정에서는 사용자가 두 번 방향을 바로잡았고, 별도 검토가 더 넓은 대화 순서를 읽으며 원래의 두 축을 복구했습니다. fresh audit가 독립적으로 오류를 예방했다기보다 사용자 정정과 더 넓은 입력 범위가 함께 작동했습니다. “fresh audit의 효과”보다 “기존 문제 이름을 그대로 받지 않는 별도 판단 상태”라는 운영 해석으로 제한해야 합니다.

후반의 발동 조건과 종료 조건은 유용하지만 매뉴얼처럼 길어집니다. 다음 세 구분만 남겨도 충분합니다.

- 단순 질문: 설명
- 첫 정정: 바로 반영
- 같은 축 반복: self-check 또는 별도 판별

fresh audit의 read-only·출력 분리까지 자세히 설명하면 독립 판별 글과 동일한 설명면이 커집니다. 여기서는 “자기진단이 같은 이름을 반복할 때 별도 원자료 판별이 필요할 수 있다”는 경계까지만으로도 중심 질문이 유지됩니다.

#### 사실·인과·공개 경계

- AI의 원인 설명이 “정확했다”는 판단은 독립 실험이 아니라 대화 순서와 사용자의 납득에 근거합니다.
- assignment에서 추가 자료가 발견된 것은 확인됐지만, 재구성 산출물이 언제나 별도 원본의 존재를 증명하는 것은 아닙니다.
- fresh audit 결과가 실제 제품 결과를 개선했다는 증거는 없습니다.
- skill·agent·전역 규칙의 생성은 artifact이지 효과가 아닙니다.
- private raw를 직접 인용하지 않고 행동 순서로 재구성한 현재 방식은 적절합니다.
- 기존 초안으로 기록된 `ai-self-check-fundamental.md`는 현재 workspace와 Git history에서 확인되지 않았습니다. 이전 초안의 목소리나 내용을 보존했다고 주장하려면 먼저 원문을 찾아야 하고, 그런 주장을 하지 않는다면 이번 수정에 필수 자료는 아닙니다.
