# 테스트 9개가 모두 초록인데 제품은 아직 틀렸다

여행 상품의 판매 조건을 일행과 일정에 대입해, 결제 전에 무엇을 더 확인할지 판단하는 plugin을 만들고 있었습니다.

첫 완료 판단 지점에서 Python `unittest` runner는 test method 9개를 실행했고 모두 통과했습니다. plugin 구조 검증기와 미리 만든 구조화 입력을 사용한 명령줄 demo도 별도로 통과했습니다. 상태 변화, 허용한 수정, 모호한 답변 거부, 같은 입력의 결정성을 확인했으니 첫 제품 경로는 닫힌 것처럼 보였습니다.

하지만 수정 권한이 없는 별도의 판별자가 같은 산출물을 확인한 결과는 미통과였습니다. plugin은 설치 목록에 없었고, 설치한 새 작업에서 사용자의 자연어 요청부터 끝까지 실행했다는 증거도 없었습니다. test 입력은 공개된 상품 정보와 한 지점에서 모순됐고, 문자열 `"false"`가 boolean처럼 흘렀습니다. 한 참여자에게만 적용돼야 할 판매자 답변이 다른 사람의 상태까지 바꿀 수 있었고, 같은 범위의 상반된 답변은 배열 순서에 따라 결론을 뒤집었습니다.

test가 거짓말을 한 것은 아니었습니다. 구현, test 입력, 기대 결과, 완료 설명이 같은 AI 협업 문맥에서 함께 만들어졌습니다. 9개 test는 그 세계 안에서 구현이 일관된지를 확인했습니다.

문제는 그 세계가 제품이 실제로 만날 입력과 source까지 포함한다고 읽은 데 있었습니다.

이후의 문제는 검증 범위를 넓히는 데서 끝나지 않았습니다. 다른 판단이 기존 완료 설명에 흡수되지 않게 남기고, 원자료와 재실행으로 다시 회수해야 했습니다.

## 같은 결과물을 다시 본 것이 아니라 질문의 경계를 바꿨다

첫 판별자는 아무 맥락도 없는 외부 평가자가 아니었습니다. 현재 목표, 상위 계약, 코드와 문서, test와 demo, 공개된 상품 정보를 직접 볼 수 있었습니다. 다만 이전 구현 대화와 구현자의 완료 설명은 받지 않았고, 산출물을 고칠 권한도 없었습니다.

이 차이가 질문을 바꿨습니다.

구현 문맥 안에서는 “상태 엔진이 예상한 흐름을 재현하는가”를 중심으로 보기 쉬웠습니다. 판별자는 그 질문을 반복하지 않았습니다.

- test 입력이 공개된 상품 사실과 맞는가?
- 사용자가 실제로 들어오는 자연어 경로가 존재하는가?
- 예상하지 않은 타입과 범위에서도 계약이 보존되는가?
- 같은 범위의 상반된 주장에 결과가 순서대로 흔들리지 않는가?
- 구현과 test가 놓친 범위를 완료 설명이 대신 통과시키고 있지는 않은가?

별도 AI를 한 명 더 붙인 것보다, 구현자와 다른 원천과 실행면을 열어 본 일이 중요했습니다. 판별자가 한 일은 새 정답을 대신 내리는 것이 아니라 검증하던 세계의 경계를 바꾸는 일이었습니다.

### 검증마다 보는 실패가 달랐다

첫 checkpoint와 교정 뒤의 검증을 역할별로 놓으면 다음과 같습니다.

| 검증 역할 | 첫 checkpoint | 교정 뒤 | 9·15에 포함되는가 |
| --- | --- | --- | --- |
| Python `unittest` | test method 9개가 미리 정한 입력의 상태 변화를 확인 | test method 15개가 엄격한 타입, 참여자 범위, 답변 충돌, 수정안의 원안 참조까지 확인 | 포함 |
| 구조 검증기와 CLI | 별도로 통과 | 별도로 다시 통과 | 포함되지 않음 |
| 공개 정보와 제품 계약 대조 | 판별자가 test 입력의 모순을 발견 | 공개 정보로 닫힌 절차를 계약에 반영 | 포함되지 않음 |
| 설치형 자연어 E2E | 설치와 전체 흐름 증거가 없음 | 새 작업에서 자연어 입력부터 다음 행동 변경까지 실행 | 포함되지 않음 |

9와 15는 같은 runner가 실행한 test method 수입니다. validator, CLI, 설치형 자연어 end-to-end(E2E)는 그 숫자 밖의 별도 검증입니다. test가 여섯 개 늘었다고 제품 품질이나 사용자 가치가 여섯 칸 좋아진 것은 아닙니다.

각 검증은 서로 다른 실패를 봤습니다. `unittest`는 미리 정한 입력과 상태 계약의 일관성을 봤습니다. 공개 정보 대조는 그 계약 바깥의 사실을 봤고, 설치형 E2E는 사용자가 실제로 들어오는 입력 형태와 전체 실행 경로를 봤습니다. 하나의 초록이 다음 범위까지 자동으로 통과시키지는 않았습니다.

### 같은 checkpoint를 실제 사용자 흐름에서 다시 닫았다

교정에서는 기능의 폭을 넓히기보다 처음 약속한 제품 경로를 source와 실행 환경에서 다시 닫았습니다.

대표 입력은 미성년자 티켓 절차를 아직 확인하지 않은 변수로 두고 판매자에게 다시 묻도록 되어 있었습니다. 하지만 공개 상품 정보에는 별도 구매와 사전 메시지 절차가 이미 나와 있었습니다. 교정에서는 이 절차를 미확정 질문에서 제외하되 별도 준비가 필요한 부담은 남겼고, 판매자에게 다시 물을 변수는 공개 정보로 닫히지 않은 항목으로 줄였습니다.

구조화 계약도 좁혔습니다. boolean 자리에 들어온 문자열이나 정수, 잘못된 날짜·시각, 중복 참여자를 오류로 거부했습니다. 한 사람에 대한 답변은 그 사람의 상태에만 적용했고, 같은 범위의 중복·상반된 답변은 배열 순서와 관계없이 실패하게 했습니다. 수정안이 어느 원안을 바꾸는지도 직접 가리키게 했습니다.

마지막으로 plugin을 설치한 새 작업에서 자연어 요청부터 실행했습니다.

```text
사용자 요청
→ 현재 상품 정보 확인
→ 원안의 첫 충돌 판정
→ 사용자가 허용한 수정 적용
→ 범위가 부족한 판매자 답변 거부
→ 범위가 충분한 답변의 관련 상태만 갱신
→ 다음 행동 변경
```

범위가 충분한 답변을 적용한 뒤에도 원안의 다른 충돌과 준비 부담은 그대로 보존했습니다. 바뀐 것은 관련 상태와 그에 따른 다음 행동이었습니다. 마지막 행동은 `추가 확인`에서 `결제 검토`로 이동했습니다.

교정 뒤 같은 runner의 test method는 15개가 됐고, 구조 검증기와 CLI를 별도로 다시 실행했습니다. 설치형 자연어 E2E도 따로 확인했습니다. 짧은 회귀 판별은 이 교정 범위에서 통과했습니다.

그 결과 역시 주어진 증거 범위 안의 checkpoint입니다. 회귀 판별자는 코드만 받은 것이 아니라 설치 상태와 실제 E2E 기록도 입력으로 받았습니다. 제출물 하나를 받아 설치부터 독립 재현한 clean-room 검사는 아니었습니다.

## 판별 결과가 독립적이려면 출력도 따로 남아야 했다

입력을 다르게 주는 것만으로는 충분하지 않았습니다. 판별 결과를 작업을 조율하는 AI의 기존 설명에 바로 합치면, 서로 다른 판단의 충돌과 새로 발견한 문제가 사라질 수 있었습니다.

그래서 이후에는 판별 결과를 별도의 판단 상태로 남기고 다음 순서로 회수했습니다.

1. 판별자가 어떤 입력과 원천에서 무엇을 봤는지 수정 없이 남깁니다.
2. 사용자가 기존 판단과의 일치, 충돌, 새 발견을 먼저 볼 수 있게 합니다.
3. main은 사용자 의도, 현재 계약, 원자료와 실행 결과를 기준으로 항목을 채택·조정·기각합니다.
4. 구현 뒤에는 판별자의 통과 문장이 아니라 다시 실행한 test와 실제 제품 흐름으로 checkpoint를 닫습니다.

회수는 reviewer의 판단을 무시하는 일이 아닙니다. 어떤 지적을 왜 받아들였고, 무엇은 어느 원천과 실행 결과 때문에 다르게 판정했는지를 남기는 책임에 가깝습니다.

판정, 수정, 완료 선언을 한 주체에 모두 모으지 않는 이유도 여기에 있습니다. reviewer가 직접 수정하고 자신의 수정까지 통과시키면 구현자의 자기인증 구조로 돌아가기 쉽습니다. 반대로 reviewer의 문장을 새 정답으로 올려도 다른 종류의 자기인증이 생깁니다.

다만 입력과 수정 권한을 분리했다고 해서 판별자가 자동으로 바깥의 누락을 복구하는 것은 아니었습니다.

### 별도 판별자도 닫힌 입력 밖을 자동으로 복구하지 못했다

다른 답변 시스템에서는 답을 만드는 호출과 그 답이 인용한 원문에서 성립하는지 판단하는 호출을 분리한 적이 있습니다. 구조상 별도 판별자가 생겼지만, 원하는 통과 조건은 성립하지 않았습니다.

관련 문장을 찾는 앞 단계에서 값이 빠진 경우에는 판별 자체가 실행되지 않았습니다. 조건 문장이 답변 값으로 잘못 선택된 경우에는 판별자가 전달받은 그 문장만 보고 성립한다고 판단했습니다. 원문 표기가 추출 과정에서 바뀌어 grounding 확인이 실패한 경우도 있었습니다.

각 실패는 같은 원인이 아니었습니다. 공통점은 판별자에게 도착하기 전에 값이나 맥락이 사라졌다면, 닫힌 입력만 받는 판별자는 그 바깥을 다시 열 수 없었다는 점입니다.

판정 역할을 분리하는 것과 판별자가 볼 입력의 경계를 여는 것은 같은 일이 아니었습니다. 이 반례는 독립성을 모델 수나 별도 호출 여부로 판단하지 않게 했습니다. 판별자가 raw source와 실제 실행면을 볼 수 있는지, 앞 단계가 고른 후보를 기각하고 질문 자체를 바꿀 수 있는지까지 봐야 했습니다. 판별 결과 자체도 A/B와 반례, revert의 대상이어야 했습니다.

## 제3판별자는 세 번째 AI가 아니다

이후에는 reviewer를 몇 명 붙일지보다 별도 판단 위치의 계약을 먼저 봅니다.

- 구현자와 다른 무엇을 입력으로 받는가?
- 원자료와 실제 사용자 입력 형태를 직접 열 수 있는가?
- 구현자가 붙인 문제 이름과 원인 가설을 바꿀 수 있는가?
- 수정 권한과 완료 선언 권한이 분리돼 있는가?
- 판별 결과의 충돌이 main의 요약 전에 보이는가?
- main은 어떤 원자료와 재실행으로 결과를 회수하는가?
- reviewer 자체도 다시 검증하고 되돌릴 수 있는가?

이 구조가 reviewer 수가 늘수록 품질이 오른다는 것을 증명하지는 않습니다. 같은 모델과 다른 모델의 구분도 독립성의 충분조건이 아닙니다. 같은 입력과 같은 질문, 같은 완료 설명을 받으면 별도 AI도 같은 frame을 반복할 수 있습니다.

첫 사건에서 9개 test가 모두 초록이었던 이유는 test가 무용해서가 아니었습니다. 구현, fixture, 기대 결과와 완료 설명이 같은 세계를 보고 있었기 때문입니다.

제가 필요로 한 제3판별자는 세 번째 AI가 아니었습니다. 다른 입력을 보고 다른 질문을 할 수 있으며, 그 결과가 기존 설명에 흡수되기 전에 별도 상태로 남고, 자신의 판정까지 원자료와 재실행으로 검증받는 판단 위치였습니다.
