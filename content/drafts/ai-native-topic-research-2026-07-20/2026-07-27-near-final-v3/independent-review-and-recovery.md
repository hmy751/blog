# 테스트 9개가 모두 초록인데 제품은 아직 틀렸다

여행 상품의 판매 조건을 일행과 일정에 대입해, 결제 전에 무엇을 더 확인해야 하는지 판단하는 plugin을 만들고 있었습니다.

첫 checkpoint는 나쁘지 않아 보였습니다. Python `unittest` runner가 test method 9개를 실행했고 모두 통과했습니다. plugin 구조 검증기와 미리 만든 JSON 입력을 넣는 CLI demo도 별도로 초록이었습니다. 원안의 충돌을 찾고, 사용자가 허용한 수정만 적용하고, 모호한 답변은 거부하고, 충분한 답변이 들어오면 다음 행동을 바꾸는 흐름까지 test에 있었습니다.

그런데 수정 권한이 없는 별도 판별자는 이 checkpoint를 통과시키지 않았습니다.

설치된 새 작업에서 사용자의 자연어 요청부터 끝까지 실행한 증거가 없었습니다. test에 넣은 상품 정보 한 항목은 공개된 판매 조건과 모순됐습니다. 한 참여자에게만 적용돼야 할 답변이 다른 사람의 상태까지 바꿀 수 있었고, 같은 범위의 상반된 답변은 배열에서 나중에 온 값을 따라갔습니다.

가장 작게 재현되는 문제는 문자열 `"false"`였습니다.

첫 구현은 어떤 조건의 값이 `False`일 때만 충돌을 만들었습니다. 입력 타입을 먼저 확인하지 않았기 때문에 문자열 `"false"`는 `False`가 아니었고, 충돌 분기를 비껴 정상 상태처럼 흘렀습니다. 문자열을 boolean으로 잘못 변환한 버그가 아니었습니다. 변환 자체가 없었습니다.

실패 범주를 최소 코드로 줄이면 다음과 같습니다.

```python
class ContractError(ValueError):
    pass


def validate_boolean(value):
    if type(value) is not bool:
        raise ContractError("boolean value required")
    return value


def test_string_false_is_not_boolean_false():
    try:
        validate_boolean("false")
    except ContractError:
        pass
    else:
        raise AssertionError('문자열 "false"를 boolean으로 받아들였습니다.')
```

왜 기존 test는 이 문제를 놓쳤을까요. 예상한 boolean만 넣었기 때문입니다.

test가 거짓말을 한 것은 아니었습니다. 9개 test는 구현이 미리 정한 fixture와 기대 결과에 일관되는지 정확히 확인했습니다. 다만 구현, fixture, 기대 결과, 완료 설명이 같은 AI 협업 문맥에서 함께 만들어졌습니다.

문제는 그 세계가 제품이 실제로 만날 source와 입력 형태까지 포함한다고 읽은 데 있었습니다.

## 초록 하나가 다음 검증의 세계까지 통과시키지는 않았다

별도 판별자에게는 이전 구현 대화와 구현자의 완료 설명을 주지 않았습니다. 대신 현재 제품 목표, 완료 계약, 코드와 test, 공개된 상품 정보를 직접 열어 줬습니다. 산출물을 고칠 권한은 없었습니다.

아무 맥락도 없는 외부 평가자는 아니었습니다. 그러나 구현자가 이미 붙인 설명을 이어 쓰기보다 다른 원천에서 checkpoint를 다시 묻게 할 수 있었습니다.

구현 문맥에서는 “상태 엔진이 예상한 흐름을 재현하는가”가 중심이었습니다. 판별자는 “그 예상이 공개된 판매 조건과 맞는가”, “사용자는 정말 그 입력 형태로 들어오는가”, “예상 밖 타입과 범위에서도 계약이 보존되는가”를 봤습니다.

첫 checkpoint와 교정 뒤의 차이를 test 수만으로 설명하면 이 변화가 사라집니다.

| 검증 역할 | 첫 checkpoint | 교정 뒤 | 9·15에 포함되는가 |
| --- | --- | --- | --- |
| Python `unittest` | test method 9개가 미리 정한 입력의 상태 변화를 확인 | test method 15개가 엄격한 타입, 참여자 범위, 답변 충돌, 수정안의 원안 참조까지 확인 | 포함 |
| 구조 검증기와 CLI | 별도로 통과 | 별도로 다시 통과 | 포함되지 않음 |
| 공개 정보와 제품 계약 대조 | 판별자가 test 입력의 모순을 발견 | 공개 정보로 닫힌 절차를 계약에 반영 | 포함되지 않음 |
| 설치형 자연어 E2E | 설치와 전체 흐름 증거가 없음 | 새 작업에서 자연어 입력부터 다음 행동 변경까지 실행 | 포함되지 않음 |

9와 15는 같은 runner가 실행한 test method 수입니다. 공개 정보 대조와 설치형 end-to-end(E2E)는 그 숫자 밖의 별도 검증이었습니다. test가 여섯 개 늘었다고 제품 품질이나 사용자 가치가 여섯 칸 좋아졌다는 뜻도 아닙니다.

`unittest`는 구조화된 입력과 상태 계약의 일관성을 봤습니다. 공개 정보 대조는 fixture가 바깥 사실과 충돌하는지 봤고, 설치형 E2E는 자연어 요청이 실제 사용 위치에서 상태 엔진까지 도달하는지 봤습니다.

판별자가 한 일은 새 정답을 대신 내리는 것이 아니라 검증하던 세계의 경계를 바꾸는 일이었습니다.

## 기능을 더 만들지 않고 같은 checkpoint를 다시 닫았다

교정 범위는 새 기능을 추가하는 쪽으로 가지 않았습니다. 처음 약속한 제품 경로를 source와 실제 입력 형태에서 다시 닫는 데 집중했습니다.

한 test fixture에는 미성년자 티켓 절차가 아직 확인하지 않은 변수로 들어 있었습니다. 그래서 판매자에게 다시 묻는 흐름이 생겼습니다. 하지만 공개 상품 정보에는 별도 구매와 사전 메시지 절차가 이미 적혀 있었습니다.

교정 뒤에는 이 절차를 미확정 질문에서 제외했습니다. 그렇다고 티켓 준비 부담까지 없애지는 않았습니다. 공개 정보로 닫힌 사실은 닫고, 판매자에게 물어야 할 변수는 공개 정보로 확인되지 않은 항목으로 줄였습니다.

입력 계약도 좁혔습니다.

- boolean 자리에 문자열이나 정수가 들어오면 거부합니다.
- 한 참여자에 관한 답변은 그 참여자의 상태만 바꿉니다.
- 같은 범위의 상반된 답변은 배열 순서와 관계없이 실패합니다.
- 수정안은 자신이 바꾸는 원안을 직접 가리킵니다.
- 근거 없이 모든 확인이 끝났다고 표시할 수 없습니다.

이후 plugin을 설치한 새 작업에서 자연어 요청부터 전체 흐름을 다시 실행했습니다.

```text
자연어 요청
→ 현재 상품 정보 확인
→ 원안의 첫 충돌 판정
→ 사용자가 허용한 수정 적용
→ 모호한 fixture 답변 거부
→ 범위가 충분한 fixture 답변의 관련 상태만 갱신
→ 다음 행동 변경
```

검증용 fixture 답변을 적용한 뒤에도 원안의 다른 충돌, 기본 비용, 별도 티켓 준비 부담은 그대로 남았습니다. 바뀐 것은 그 답변이 맡은 상태와 다음 행동이었습니다. 마지막 행동은 `추가 확인`에서 `결제 검토`로 이동했습니다.

교정 뒤 같은 runner의 test method 15개와 별도 구조 검증기·CLI를 다시 확인했습니다. 설치형 자연어 E2E와 짧은 회귀 판별도 통과했습니다. 다만 회귀 판별자는 설치 상태와 E2E 기록을 입력으로 받았으므로, 제출물 하나만 건네받아 설치부터 재현한 clean-room 검사는 아니었습니다.

checkpoint를 다시 닫은 것은 판별자의 통과 문장이 아니라, 판별이 연 공백을 source와 계약으로 확인하고 코드를 고친 뒤 같은 제품 경로를 재실행한 결과였습니다.

## 판별 결과도 기존 완료 설명과 분리해야 했다

입력만 다르게 주면 독립성이 완성될 것 같지만, 출력이 어디에 놓이는지도 중요했습니다.

판별 결과를 작업을 조율하는 AI의 기존 설명에 바로 합치면, 구현자의 완료 판단과 판별자의 미통과가 어디에서 충돌했는지 사라집니다. 지적이 몇 개의 수정 항목으로 압축되면 판별자가 바꾼 질문의 경계도 희미해집니다.

그래서 이후에는 판별 결과를 별도 상태로 남기고 다음처럼 회수했습니다.

```text
판별
설치형 자연어 E2E 증거가 없다.

계약 대조
해당 흐름이 완료 조건임을 확인하고 checkpoint를 열어 둔다.

교정·재실행
15개 unittest + 별도 validator·CLI + 설치형 자연어 E2E.

남은 범위
제출물 하나만 받은 clean-room 재현은 아니다.
```

회수는 reviewer를 무시하는 일이 아닙니다. 어떤 지적을 어느 계약 때문에 채택했고, 무엇을 고쳤으며, 어디까지 다시 실행했는지 남기는 일입니다.

reviewer가 직접 수정하고 자기 수정까지 통과시키면 구현자의 자기인증과 비슷한 구조가 될 위험이 있다고 봤습니다. 반대로 reviewer의 문장을 새 정답으로 올려도 판정을 검증할 위치가 사라집니다. 판정, 수정, 완료 선언을 한곳에 모으지 않은 이유입니다.

### 별도 판별자도 닫힌 입력 밖은 볼 수 없었다

다른 답변 시스템에서는 답을 만드는 호출과 그 답이 원문에서 성립하는지 판정하는 호출을 분리했습니다. 그러나 앞 단계에서 값이 빠지거나 조건 문장을 값으로 잘못 고른 경우, 닫힌 입력을 받은 판별자는 그 바깥의 원문과 후보를 다시 열지 못했습니다.

판정 역할을 분리하는 것과 판별자가 볼 입력의 경계를 여는 것은 같은 일이 아니었습니다.

## 제3판별자는 세 번째 AI가 아니었다

이 경험 뒤에는 reviewer 수보다 세 가지를 먼저 봅니다.

구현자가 보지 않은 source와 실제 입력 형태를 열 수 있는가. 수정 권한과 완료 선언 권한이 분리돼 있는가. 마지막으로 판정 자체도 원자료와 재실행의 검사를 받는가.

같은 모델인지 다른 모델인지는 이 조건을 자동으로 해결하지 않습니다. 같은 입력, 같은 질문, 같은 완료 설명을 받으면 별도 AI도 같은 frame을 반복할 수 있습니다.

첫 checkpoint에서 9개 test가 모두 초록이었던 이유는 test가 무용해서가 아니었습니다. 구현과 fixture와 완료 설명이 같은 세계를 보고 있었기 때문입니다.

제가 필요로 한 제3판별자는 세 번째 AI가 아니었습니다. 다른 검증 세계를 열고, 그 결과가 기존 설명에 흡수되기 전에 남으며, 자신의 판정까지 source와 재실행으로 검증받는 판단 위치였습니다.
