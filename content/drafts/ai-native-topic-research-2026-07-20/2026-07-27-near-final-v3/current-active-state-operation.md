# current.md는 작업 로그가 아니다

긴 AI 작업을 이어 가기 위해 한 구현 loop의 목표와 완료 조건을 과정 기록에 적어 둔 적이 있습니다.

문서에는 왜 이 loop를 골랐는지, 무엇을 이번 범위에서 제외했는지, 어떤 test와 실행 증거가 있어야 끝나는지가 함께 있었습니다. 당시 판단을 이해하기에는 좋은 기록이었습니다. 다음 AI도 이 문서를 읽으면 현재 계약을 찾을 수 있을 것처럼 보였습니다.

문제는 계약이 바뀔 때 생겼습니다.

과거에 왜 그런 조건을 골랐는지 보존해야 하는 문장과, 지금 구현자가 따라야 하는 완료 조건이 같은 갱신 규칙을 갖고 있었습니다. 현재 조건을 고치면 당시 판단이 흐려지고, 과거를 그대로 남기면 다음 AI는 여러 시점의 문장 가운데 무엇이 아직 유효한지 다시 추론해야 했습니다.

사용자는 현재 구현 계약은 과정 기록이 아니라 별도의 실행 영역이 소유해야 한다고 지적했습니다.

그 뒤 현재 goal·acceptance·evidence는 active contract로 옮기고, 과정 기록에는 선택 이유와 기각한 대안, 당시 실행 결과를 남겼습니다. 전체 프로젝트를 가리키는 `current.md`에는 계약 전문을 복사하지 않고, 현재 위치와 권위 있는 원천으로 내려가는 경로만 연결했습니다.

바뀐 것은 문서 수가 아니었습니다. 같은 문장이 현재 행동과 과거 설명 중 무엇을 맡는지가 달라졌습니다.

| 정보의 역할 | 분리 전 | 분리 후 |
| --- | --- | --- |
| 지금 실행할 완료 조건 | 선택 이유와 함께 과정 기록 안에 놓임 | active contract가 현재판을 소유하고 방향이 바뀌면 갱신 |
| 왜 이 조건을 택했는가 | 현재 조건과 같은 위치에서 함께 갱신 | history가 당시 선택·기각·실행 결과를 보존 |
| 확인된 사실과 산출물 | 요약문 안에 다시 적힐 수 있음 | 사실과 산출물의 원천이 직접 소유 |
| 지금 어디를 봐야 하는가 | 여러 시점의 문장에서 다시 추론 | `current`가 전체 지도·현재 cursor·권위 원천 경로를 연결 |

목적은 문서를 보기 좋게 나누는 것이 아니라, 서로 다른 수명과 쓰기 권한을 가진 상태가 같은 권위로 경쟁하지 않게 하는 것이었습니다.

## 기록이 부족한 문제와 현재 효력이 흐린 문제는 달랐다

AI와 긴 작업을 하면 먼저 기록을 더 자세히 남기고 싶어집니다. 무엇을 조사했고 어떤 안을 버렸으며 어느 test에서 실패했는지 써 두면 다음 session이 이어질 것처럼 보입니다.

실제로 이 기록은 필요합니다. 과거 선택을 다시 검토하려면 당시 이유가 남아 있어야 하고, 실패한 구현을 지우지 않아야 판단이 어디서 바뀌었는지 복구할 수 있습니다.

하지만 history가 답하는 질문은 “무슨 일이 있었는가”입니다. 현재 작업은 다른 질문에 먼저 답해야 합니다.

- 지금 효력이 있는 계약은 무엇인가.
- 여러 진행 흔적 가운데 실제 현재 판단점은 어디인가.
- 이번 판단은 최근 구현만 보는가, 프로젝트 전체를 다시 보는가.
- 방향이 바뀌면 무엇을 덮어쓰고 무엇을 보존하는가.

append-only 기록만으로 이 질문에 답하려면 다음 AI가 시간순 문장을 다시 읽고 현재 상태를 계산해야 합니다. 최근에 쓰인 문장이 가장 권위 있다고 착각하기도 쉽습니다. 반대로 모든 현재 상태를 한 문서에 복사하면 원천이 바뀔 때 복사본도 함께 stale해집니다.

그래서 네 역할을 다른 상태로 봤습니다.

```text
history
└─ append-only: 선택 이유와 당시 실행 결과

active contract
└─ overwrite: 지금 실행할 goal·acceptance·evidence

current
└─ router: 전체 지도 + 현재 판단점 + 원천 경로

source
└─ authority: 실제 사실·code·test·산출물
```

작은 작업이라면 이 역할을 네 파일로 나눌 필요는 없습니다. 한 문서 안에서 구역만 나눠도 됩니다. 중요한 것은 어떤 문장이 현재 효력을 소유하고, 무엇이 바뀔 때 누가 갱신하는지가 보이는 일입니다.

## 전체 지도와 현재 cursor는 서로 대체할 수 없었다

현재 판단점만 짧게 남기면 최근 작업에는 빨리 들어갈 수 있습니다. 대신 그 일이 프로젝트 전체에서 어떤 위치인지 잃기 쉽습니다. 반대로 프로젝트 이력을 전부 `current` 안에 펼치면 재진입할 때마다 긴 상태 보고서를 읽어야 합니다.

제가 사용한 `current`는 전체 지도와 현재 cursor 하나를 함께 뒀습니다. 아래는 실제 내부 문장을 옮기지 않고 역할만 다시 만든 예시입니다.

```text
[목표]
사용자의 조건 변화가 다음 행동을 바꾸는 흐름을 검증한다.

[전체 지도]
조사 ─ 완료 → 조사 원천
문제 정의 ─ 완료 → 선택 기록
솔루션 비교 ─ 완료 → 비교 결과
구현과 검증 ─ 진행 중
  └ 현재 cursor: 설치 환경에서 자연어 흐름을 다시 실행한다.
제출 ─ 열지 않음

[열린 판단]
현재 검증 범위로 첫 제품 계약을 닫을 수 있는가?
```

완료된 가지에는 무엇이 끝났고 어디에서 근거를 다시 볼 수 있는지만 남겼습니다. 진행 중인 가지에서만 다음 행동과 열린 판단을 조금 더 깊게 적었습니다. 세부 사실은 조사 문서, 결정 기록, active contract, test와 실행 결과가 직접 소유했습니다.

이렇게 보면 `current`는 답 저장소보다 router에 가깝습니다. 전체 지도만 있으면 다음 행동이 흐리고, cursor만 있으면 가장 최근 사건이 프로젝트 전체가 됩니다.

이 구조가 문서에만 있던 것은 아닙니다. 한 프로젝트의 21개 도달 가능한 commit 가운데 18개가 `current`를 바꿨습니다. 18개 committed version마다 사용법 설명과 별개로 실제 활성 cursor가 하나씩 놓여 있었고, 고유한 cursor 문장은 14개, 연속 version 사이에서 cursor가 바뀐 전환은 13번이었습니다.

이 숫자는 작업 품질이나 생산성의 지표가 아닙니다. 다만 `current`가 완성 뒤 남겨 둔 설명문이 아니라, 구현과 판별과 교정 사이에서 실제로 덮어쓴 상태 artifact였다는 것은 보여 줍니다.

## current를 읽어도 잘못된 시간축으로 내려갈 수 있었다

이 구조가 실제로 도움이 됐지만, 자동으로 올바른 판단을 만들어 주지는 않았습니다.

한 프로젝트를 마친 뒤 다섯 문항의 제출 설문을 AI와 작성했습니다. 설문 담당 AI는 시작 전에 전체 지도와 현재 cursor가 있는 문서를 읽었습니다.

그런데 프로젝트 전체 역할을 묻는 문항이 직전에 끝낸 구현과 검증에 과도하게 끌렸습니다. 최근 사건에 관한 사실은 틀리지 않았습니다. 문제는 조사, 문제 후보 재구성, 여러 solution의 출력 비교, 사람이 한 선택을 밀어내고 전체 프로젝트의 의미까지 대신한 데 있었습니다.

이 어긋남을 발견한 것은 문서가 아니라 사용자였습니다.

복구할 때 `current`를 더 길게 요약하지 않았습니다. 질문이 어느 시간축을 요구하는지 먼저 나누고, 지도에서 서로 다른 원천으로 내려갔습니다.

```text
프로젝트 전체의 역할을 묻는 질문
→ current의 상위 지도
→ 조사·문제 정의·출력 비교·선택 기록
→ 프로젝트 전체의 역할과 판단을 복구

최신 구현의 입력·결과·한계를 묻는 질문
→ current의 현재 cursor
→ active contract·test·실행 기록
→ 최신 구현 상태와 미검증 범위를 갱신
```

최근 구현의 사실이 틀렸던 것이 아니라, 전체 질문에까지 같은 해상도로 사용된 것이 문제였습니다. 바뀐 것은 정보량보다 읽는 시간축이었습니다.

> 이번 판단의 시간축은 어디까지인가?

최근 실패를 교정하는 작업이라면 현재 cursor를 깊게 읽으면 됩니다. 프로젝트 전체를 설명하거나 방향을 다시 판단한다면 상위 지도에서 관련 원천으로 내려가야 합니다.

설문을 다시 쓰는 동안 다른 작업에서 구현 상태가 바뀐 일도 있었습니다. 처음에는 설치 환경의 자연어 전체 흐름이 미검증이었지만, 병렬 작업에서 교정과 E2E가 끝났습니다. 설문은 `current`의 시작 상태만 믿지 않고 최신 실행 원천을 다시 확인해 문장을 갱신했습니다.

이 복구에는 사용자의 정정, 전체 지도, 직접 원천이 함께 작동했습니다. `current`는 판단을 대신하지 않았지만 프로젝트 계보로 돌아가는 경로를 제공했습니다.

## 덮어쓰는 상태의 갱신 책임

active state는 오래된 문장이 현재 기준처럼 쌓이는 문제를 줄입니다. 대신 누군가 마지막 상태를 반영해야 합니다.

앞선 프로젝트의 마지막 `current`에는 구현 교정과 검증 통과, 그다음 선택지가 남아 있었습니다. 그러나 이후 설문 완료, 제출 파일 검증, 외부 업로드 실패와 후속 대응은 들어오지 않았습니다. 마지막 세 commit 동안 다른 artifact는 바뀌었지만 `current`는 갱신되지 않았습니다.

누락 원인이 update ownership 하나였다고 단정할 수는 없습니다. 확인할 수 있는 것은 병렬 작업과 저장소 밖 사건을 어느 작업자가 반영할지가 분명하지 않았고, 마지막 외부 상태가 빠졌다는 점입니다. 읽기 권한을 나눈 뒤에는 쓰기 책임이 남았습니다.

같은 문제는 이 글을 준비할 때도 재현됐습니다. 과정 기록의 새 질문이 닫힌 중심을 다시 선택지로 바꾸자, 질문은 재료로 남기고 중심을 바꿀 권한만 현재 상태 영역으로 돌렸습니다.

## 권위와 갱신 경로를 먼저 봤다

이 구조가 작업 속도나 생산성을 높였다는 비교 근거는 없습니다. 실제 재진입에는 Git, 실행 계약, 대화 요약, 사용자의 정정도 함께 작동했습니다. `current`를 읽고도 최근 사건에 치우쳤고, 마지막 외부 상태를 놓치기도 했습니다.

그래도 문제가 생겼을 때 무엇을 고쳐야 하는지는 달라졌습니다.

맥락이 부족하다고 기록을 더 붙이기 전에 한 문장이 무엇을 소유하는지 봤습니다. 지금 효력이 있는 계약인지, 과거 이유를 보존하는 기록인지, 사실을 가진 원천인지, 그 원천으로 내려가는 경로인지 구분했습니다. 질문의 시간축이 바뀌면 다른 원천으로 내려갔고, 병렬 작업과 외부 사건을 누가 반영할지도 함께 봤습니다.

`current`는 긴 context를 짧게 요약한 답안이 아니라, 전체 시간축에서 지금 판단할 위치를 찾고 권위 있는 원천을 다시 작동시키는 active control에 가까웠습니다.
